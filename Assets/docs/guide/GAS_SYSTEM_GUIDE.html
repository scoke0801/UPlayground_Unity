Gameplay Ability(GAS) 시스템 가이드

플레이어와 몬스터의 공격·스킬·버프·자원·쿨다운을 하나의 데이터 구조로 정의하고 실행하는 자체 GAS(Gameplay Ability System). Unreal의 GameplayAbilitySystem을 참고했으나 프로젝트 비의존 Core와 프로젝트 어댑터를 분리한 자체 구현이다. 상세 스펙은 Assets/docs/TODO/GAMEPLAY_ABILITY_SYSTEM_SPEC.md 참조.

1. 개요

  • 단일 데이터 소스 — 공격/스킬 수치의 원본은 오직 AbilitySetSO다. 캐릭터의 모든 공격·콤보·차지·연계가 이 한 에셋에서 파생된다. PlayerSkillSlot은 입력 바인딩일 뿐 수치의 원본이 아니다.
  • 플레이어·몬스터 공용 — 동일한 GameplayAbilitySO 구조를 플레이어와 몬스터가 함께 쓴다. 몬스터 BT는 AbilitySet의 aiSelectable 공격을 골라 활성화한다.
  • 2단계 Prepare → Commit — 조건 검증(Prepare)과 자원·쿨다운 소비(Commit)를 분리한다. 애니메이션 상태 전환이 실패하면 자원/쿨다운이 소모되지 않는다.
  • 이식 가능한 Core — UPlayGround.Ability.Core는 프로젝트 타입을 참조하지 않는다. Attribute/Effect/Tag/Cooldown/Task 엔진이 독립적으로 존재하고, 모션·전투 데이터는 어댑터로 주입한다.
  • Effect 기반 수치 변경 — 데미지·힐·자원·버프·디버프는 모두 GameplayEffect로 Attribute를 변경한다. 지속/주기/스택/면역/저장을 지원한다.

2. 아키텍처

런타임 코드는 4개 asmdef 계층으로 나뉜다. 화살표는 참조(의존) 방향이다.

[Actor]  UPlayGround.Gameplay.Ability  ── Unity MonoBehaviour 통합
   AbilitySystemComponent   (액터당 1개, 집합 루트 MonoBehaviour)
   ├─ Runtime : AbilitySystemRuntime         ← Core 엔진 인스턴스
   ├─ ProjectAbilities : ActorAbilitySystem   ← Prepare/Commit 실행 관리
   ├─ ProjectEffects : GameplayEffectController
   └─ ProjectTags : GameplayTagContainer
        │ 참조
        ▼
[Adapter] UPlayGround.Ability.UPlayGround  ── 프로젝트 연결 지점
   UPlayGroundMotionAbilityPayloadSO    (MotionSet + AbilityAttackInfo)
   UPlayGroundAbilityPayloadResolver    (WeaponType별 모션 해석)
        │
        ▼
[Data]   UPlayGround.Data.Ability      ── 순수 데이터 SO (수치)
   AbilitySetSO → GameplayAbilitySO → AbilityVariantDefinition → GameplayEffectSO
        │
        ▼
[Core]   UPlayGround.Ability.Core      ── 프로젝트 비의존 엔진
   AbilitySystemRuntime (집합 루트)
   ├─ AttributeSetRuntime      속성 + 클램프/종속자원/트랜잭션
   ├─ GameplayTagAggregator    게임플레이 태그
   ├─ GameplayEventRouter      게임플레이 이벤트
   ├─ AbilityCooldownRuntime   쿨다운 그룹
   ├─ ActiveGameplayEffectContainer  지속/주기/스택/면역 GE
   ├─ AbilityTaskContainer + AbilityTaskGraphSO  다중 프레임 실행
   └─ AbilityDebugRecorder     스냅샷/디버그

핵심 규칙: Core는 PlayerActor·MotionSetAsset 같은 프로젝트 타입을 절대 참조하지 않는다. 프로젝트 종속은 AbilityExecutionPayloadSO(추상 확장점)를 통해서만 주입된다. 덕분에 Core는 다른 프로젝트로 이식 가능하다.

4. 데이터 흐름

공격 하나가 실제 애니메이션과 히트박스로 이어지기까지의 해석 경로다.

CharacterModelData.abilitySet
  → AbilitySetSO                       캐릭터의 전체 공격 세트
      ├─ playerSlots[]     (슬롯 ↔ Ability)
      ├─ combatBindings[]  (약공/강공 콤보 시퀀스)
      ├─ charge            (차지 단계)
      └─ comboRoutes[]     (입력 시퀀스 연계)
  → GameplayAbilitySO                  개별 Ability (조건·비용·쿨다운·동시성)
  → AbilityVariantDefinition           조건별 분기 (지상/공중, 자원량, 태그)
  → executionPayload (UPlayGroundMotionAbilityPayloadSO)
  → attackInfo.baseInfo.motionRef      실행 Motion의 단일 소스
  → MotionReferenceSO.Resolve(WeaponType)
  → MotionSetAsset                     Animancer 타임라인 → 히트박스/VFX/SFX

중복 금지: 실행 Motion의 유일한 소스는 attackInfo.baseInfo.motionRef다. Payload 바깥에 별도 motionRef나 AnimKey 폴백을 다시 두면 안 된다. 제거된 PlayerAttackDataSO, 레거시 Resolver/폴백을 재도입하지 않는다.

6. 실행 생명주기 (Prepare/Commit)

이 시스템에서 가장 중요한 패턴이다. 공격은 항상 Prepare → (상태 전환) → Commit 순서로 실행된다.

1 Evaluate      조건 검사만 (태그/지상/타깃/사거리/자원/쿨다운). 상태 변경 없음
2 TryPrepare    Evaluate 통과 시 AbilityExecution 생성 → handle 반환
                ※ 아직 자원·쿨다운 소비 안 함. 동시성 정책 처리
3 (상태 전환)   PlayerAttackState 등 애니메이션 상태 진입 시도
4a Commit(handle)  상태 전환 성공 → 비용 소비 + 쿨다운 시작 +
                 commit/owner/target Effect 적용 + TaskGraph 시작 + Started 큐
4b Abort(handle)   상태 전환 실패 → 아무것도 소비하지 않고 취소
5 EndActiveAbility(completed)  종료. completed면 endEffects 적용 + Ended 큐

프레임 윈도우 가드: Prepare 후 PreparedFrame + 1 프레임을 넘겨 Commit하면 PreparedExecutionExpired로 자동 Abort된다. Prepare와 Commit은 같은 프레임(또는 바로 다음 프레임)에 이뤄져야 한다.

이 구조 덕분에 "상태 전환은 거부됐는데 궁극기 에너지·쿨다운만 날아가는" 버그가 원천적으로 발생하지 않는다.

7. Attribute & Effect

Attribute (속성)

모든 수치는 AttributeSetRuntime의 Attribute로 관리된다. 각 속성은 Base(기본값)와 Current(Effect 합성 후)를 구분한다.

  • 클램프 정책 — 최소/최대 범위. Health는 0 ~ MaxHealth로 자동 제한.
  • 종속 자원 — MaxHealth 변경 시 Health가 비율 유지(PreserveRatio)로 따라 움직인다.
  • 트랜잭션 — BeginTransaction()으로 여러 Base를 원자적으로 커밋한다.

GameplayEffect (효과)

Attribute를 바꾸는 모든 것은 Effect다. 지속 정책에 따라 세 가지로 나뉜다.

정책설명예시
Instant즉시 Base 변경 후 소멸데미지, 힐, 자원 소비
Duration일정 시간 동안 Current 수정, 만료 시 제거공격력 버프, 슬로우
Infinite수동 제거 전까지 유지장비 보너스, 원소 부여

추가로 주기(Period)(도트 데미지), 스택(Stack)(중첩/갱신/교체), 면역(Immunity), 저장(SaveActiveEffect)을 지원한다. 데미지/힐/강인도는 StandardGameplayExecutions의 실행자와 SetByCaller 값으로 처리된다.

8. 셋업 방법

새 캐릭터(또는 몬스터)에 공격을 붙이는 절차다.

  1. GameplayEffect 에셋 생성 — 필요하면 Create ▸ UPlayGround/Ability/…로 데미지/버프 Effect를 만든다. 단순 확정 데미지는 컴포넌트 내장 API를 써도 된다.
  2. Motion Payload 생성 — UPlayGroundMotionAbilityPayloadSO를 만들고 attackInfo.baseInfo.motionRef에 MotionReferenceSO를 연결한다.
  3. GameplayAbility 생성 — Create ▸ UPlayGround/Ability/Gameplay Ability. abilityId, cost, cooldown, concurrency를 설정하고 variants[0].executionPayload에 2번 Payload를 연결한다. (에디터 창 권장 — 아래 10장)
  4. AbilitySet에 등록 — AbilitySetSO의 playerSlots(슬롯 스킬), combatBindings(약공/강공 콤보), charge, comboRoutes 중 알맞은 곳에 Ability를 넣는다.
  5. 캐릭터에 연결 — CharacterModelData.abilitySet에 이 Set을 지정한다. 액터 생성 시 ActorAbilitySystem.SetAbilitySet으로 로드된다.
  6. 컴포넌트 확인 — AbilitySystemComponent는 GameActor가 초기화 시 자동으로 준비한다(EnsureInitialized). 프리팹에 수동으로 붙일 필요는 없지만, 있어도 무방하다.

플레이어 Ability 에셋은 Assets/10.Datas/Ability/Migrated/에 있다. 기존 에셋을 복제해 시작하면 필드 누락을 피할 수 있다.

9. 사용 예시

플레이어 슬롯 스킬 활성화 (Prepare → Commit)

// PlayerAttackState 내부 — 액터는 actor.Abilities(ActorAbilitySystem)로 접근
bool grounded = controller?.Motor == null
    || controller.Motor.GroundingStatus.IsStableOnGround;

// 1) 준비 — 조건 검증 + 실행 인스턴스 생성
AbilityActivationResult prepare = playerActor.Abilities.TryPreparePlayerSlot(
    PlayerSkillSlot.Skill1,
    grounded,
    target: null,
    out AbilityExecutionHandle handle,
    out AbilityVariantDefinition variant);

if (prepare != AbilityActivationResult.Success)
    return; // 자원 부족/쿨다운/태그 차단 등 — 아무것도 소비되지 않음

// 2) variant의 모션으로 애니메이션 상태 전환 시도 …

// 3) 상태 전환 성공 → Commit (여기서 비용·쿨다운 소비)
AbilityActivationResult commit = playerActor.Abilities.Commit(handle);
if (commit != AbilityActivationResult.Success)
    playerActor.Abilities.Abort(handle); // 실패 시 되돌림

모션에서 공격 정보 해석

if (UPlayGroundAbilityPayloadResolver.TryResolve(
        variant, weaponType,
        out MotionSetAsset motion,
        out AbilityAttackInfo attackInfo))
{
    // motion → Animancer 재생, attackInfo → 히트박스/데미지 계산
}

직접 데미지·힐·버프 적용 (Prepare/Commit 불필요)

// 확정 데미지 (히트 판정 후)
victim.AbilitySystem.ApplyResolvedDamage(
    finalDamage, source: attacker.AbilitySystem, abilityHandle);

// 강인도 데미지
victim.AbilitySystem.ApplyPoiseDamage(poiseDamage, attacker.AbilitySystem);

// 지속 버프 부착 → 핸들 보관 후 나중에 제거
var handle = actor.AbilitySystem.ApplyAttributeEffect(
    "GE_AttackUp",
    new[] { new AttributeModifierValue(
        AttributeIds.Combat.AttackPower,
        AttributeModifierOperation.Multiply, 1.2f) });
// …
actor.AbilitySystem.RemoveEffect(handle);

몬스터 AI에서 Ability 활성화

// EnemyCombat — BT가 고른 aiSelectable Ability를 실행
AbilityActivationResult prepare = _abilitySystem.TryPrepareAbility(
    ability, IsGrounded(), target, out var handle, out _);
if (prepare != AbilityActivationResult.Success) return false;

if (_abilitySystem.Commit(handle) == AbilityActivationResult.Success)
    return true;

_abilitySystem.Abort(handle);
return false;

11. 주의 사항

Commit 없이 Prepare만 하고 방치하지 말 것. Prepare로 만든 AbilityExecutionHandle은 반드시 같은(또는 다음) 프레임에 Commit 또는 Abort로 마무리한다. 방치하면 프레임 가드에 걸려 무효화되고 실행 딕셔너리에 잔여물이 남는다.

  • 수치 원본은 AbilitySet 하나뿐 — PlayerSkillSlot은 입력 바인딩이다. 공격 수치를 슬롯에 두지 않는다.
  • Motion 소스 이중화 금지 — attackInfo.baseInfo.motionRef 외에 별도 motionRef/AnimKey 폴백을 만들지 않는다.
  • WeaponType override — MotionReferenceSO는 무기 타입 없이 임의의 첫 override를 고르지 않는다. 적의 무기 타입 계약이 없으면 기본 Motion을 쓴다.
  • Awake 순서 — 다른 매니저 초기화 전에 GAS에 접근하면 Services.Get<T>() 경고가 날 수 있다. EnsureInitialized()는 안전하지만, 서비스 의존은 지연 조회로 처리한다.
  • 미해결 매핑 — Dryad 공격 3개, Training Dummy 1개는 대응 Motion 근거가 없어 임의 매핑을 금지한 상태다(콘텐츠 확정 후 연결).
  • 완전한 독립 패키지 아님 — Core는 비의존이지만 Effect 정의·수명주기 일부가 Data/Actor에 남아 있어 외부 재사용 패키지로는 아직 미완이다.

12. 확장 포인트

  • 새 실행 Payload 타입 — AbilityExecutionPayloadSO를 상속해 프로젝트 전용 실행 데이터를 추가한다. Core는 구체 타입을 몰라도 된다.
  • 새 Effect 실행자 — IGameplayEffectExecution을 구현하고 GameplayEffectDefinition.executions에 넣어 커스텀 계산(예: 방어 관통, 흡혈)을 추가한다.
  • 새 Attribute — UPlayGroundAttributeDefaults에 기본값을 등록하면 AbilitySystemComponent가 자동으로 표준 등록한다.
  • 다중 프레임 로직 — AbilityTaskGraphSO로 대기/분기/이벤트 대기 등 실행 그래프를 저작한다(WaitMotionSetEndAbilityTask 참고).
  • 연출(VFX/SFX) — MotionSet 타임라인의 MotionEvent(프레임 정확)와 CombatFeedbackDispatcher(피격 반응)로 저작한다. Ability 데이터에는 연출 식별자를 두지 않는다(Cue 계층은 2026-07-26 제거).
  • 저장 연동 — Effect에 SaveActiveEffect를 켜면 세이브/로드와 캐릭터 스왑 시 지속 효과가 보존된다.
