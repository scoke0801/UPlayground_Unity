궁극기 암전 · 별도 스테이지 연출 가이드

스킬 발동 시 화면을 암전하고 배경과 분리된 공간에서 궁극기를 연출하는 방법. 일반적인 Unity 구현 방식과 UPlayground 현재 구조에 맞는 방식을 비교한다.

0. 결론 요약

새 시스템을 만들 필요는 없다

UltimateSequencePlayer를 축으로 하는 궁극기 연출 시스템이 이미 구축되어 있다. 잠금·복구·타임라인 이벤트·에디터 창까지 갖춰져 있으므로, "암전 + 스테이지 격리" 단계 하나를 기존 실행 흐름에 끼워 넣는 문제다.

그리고 진짜 별도 Scene은 권장하지 않는다. Unity의 additive 씬은 런타임에 Active 씬의 라이팅 설정만 적용되는데, 연출 씬을 Active로 만들면 UltimateSequencePlayer가 궁극기를 즉시 중단시킨다. 대신 전용 레이어 + 컬링마스크로 격리한 오프월드 스테이지(A안)를 권장한다. 시각적 결과는 동일하고, 프로젝트에 이미 같은 패턴의 선례가 있다.

2. 일반적인 구현 방식 4종

업계에서 "궁극기 컷신"을 만드는 방식은 크게 네 갈래다. 원신·붕괴 계열의 元素爆発 연출도 이 범주 안에 있다.

방식 1 — 제자리 연출 (In-Place Cinematic)

씬을 그대로 두고 카메라만 클로즈업으로 전환. 배경은 블러·비네팅·조도 저하로 눌러 시선을 캐릭터에 모은다.

  • 장점 — 구현 비용 최소, 전투 상태 완전 보존, 로딩 없음
  • 단점 — 배경이 그대로라 "다른 공간" 느낌이 약함. 지형이 지저분하면 그림이 안 나옴
  • 대표 — 원신 원소폭발 대부분

방식 2 — 오프월드 스테이지 (Off-World Stage)

같은 씬 안의 아주 먼 좌표(예: y = -5000)에 연출 전용 무대를 세워 두고, 캐스터를 순간이동시킨 뒤 전용 레이어/컬링마스크로 원래 월드를 렌더에서 잘라낸다.

  • 장점 — 완전한 배경 격리, 씬 로딩 없음, 매니저/전투 상태 무손상, 복귀가 좌표 되돌리기뿐
  • 단점 — 스테이지 프리팹이 항상 메모리에 상주(또는 사전 Instantiate 필요), 레이어 예산 소모
  • 대표 — 다수의 모바일 액션 RPG 소환/각성 연출

방식 3 — Additive 컷신 씬

연출 전용 Scene을 LoadSceneMode.Additive로 올리고 캐스터를 MoveGameObjectToScene으로 옮긴다.

  • 장점 — 라이팅/볼륨/스카이박스를 통째로 교체 가능, 아티스트가 씬 단위로 저작
  • 단점 — 런타임에는 Active 씬의 라이팅 설정만 적용된다. 연출 씬의 조명을 쓰려면 SetActiveScene이 필수이고, 그러면 게임플레이 씬의 라이트맵/앰비언트가 깨진다. 로딩 히칭도 감수해야 함
  • 제약 — MoveGameObjectToScene은 루트 GameObject만 이동 가능

방식 4 — RenderTexture 합성

격리된 공간을 별도 카메라로 RenderTexture에 그리고 화면에 합성한다.

  • 장점 — 배경과 완전 분리, UI 위에 자유 배치
  • 단점 — 풀스크린 해상도 RT 비용, 포스트프로세싱 이중 적용 문제, HDR/톤매핑 불일치
  • 적합 — 화면 일부에 띄우는 초상화·소환 연출 (이 프로젝트의 UICharacterPreviewRenderer가 이 방식)

3.1 이 프로젝트에서 방식 3(Additive)이 걸리는 지점

치명적 충돌. Unity는 런타임에 additive 씬의 라이팅 설정을 무시하고 Active 씬의 설정만 사용한다. 연출 씬의 조명을 살리려면 SetActiveScene을 호출해야 하는데, UltimateSequencePlayer.cs:459의 HandleActiveSceneChanged가 activeSceneChanged를 받는 즉시 Restore(SceneChanged)를 호출해 궁극기가 시작하자마자 중단된다.

그 외에도:

  • SceneManager.LoadScene/LoadSceneDirect는 모두 단일 씬 교체이고 진입 시 AssetManager.ReleaseSceneAssets()를 호출한다 → 그대로 쓰면 전투 씬이 파괴된다. additive API를 새로 만들어야 한다.
  • MoveGameObjectToScene은 루트 오브젝트만 옮길 수 있다. PlayerActor가 다른 오브젝트의 자식이면 사전 SetParent(null)이 필요하다.
  • KCC Motor는 씬 이동 후 위치/그라운딩 재확립이 필요하다.
다행인 점. GameManager.NotifySceneChanged(GameManager.cs:339)는 Unity의 sceneLoaded가 아니라 SceneManager가 명시적으로 호출한다. 따라서 additive 로드를 하더라도 매니저들의 OnSceneChanged가 잘못 트리거되지는 않는다.

3.2 선정: A안 = 방식 2 (오프월드 스테이지)

"별도 씬"의 실제 목적은 배경 격리이지 Scene 파일 분리 그 자체가 아니다. 컬링마스크로 같은 결과를 얻으면서 로딩·라이팅·중단 문제를 전부 피할 수 있고, 워프 로직은 UltimatePlacementContext가 이미 하고 있다. UICharacterPreviewRenderer가 CharacterPreview 레이어로 같은 격리를 이미 하고 있다는 점도 근거다.

아티스트가 씬 단위 라이팅 저작을 강하게 요구하는 경우에만 방식 3으로 확장하고, 그때는 HandleActiveSceneChanged에 예외 플래그를 반드시 먼저 추가한다.

5.2 UltimateStageContext 골격

namespace UPlayGround.Components
{
    /// <summary>
    /// 궁극기 연출용 격리 스테이지 진입/이탈을 담당한다.
    /// UltimateGameplayLockContext와 같은 원칙: 자신이 바꾼 것만 되돌린다.
    /// Exit은 Restore() 경로에서 동기로 호출되므로 코루틴을 기다리지 않는다.
    /// </summary>
    public sealed class UltimateStageContext
    {
        private readonly Dictionary<GameObject, int> _originalLayers = new();
        private GameObject _stageInstance;
        private GameActor _caster;
        private GameActor _target;
        private Vector3 _casterOriginPosition;
        private Quaternion _casterOriginRotation;
        private int _originalCullingMask;
        private bool _ownsCullingMask;
        private bool _isEntered;

        public IEnumerator Enter(
            UltimateRuntimeContext runtimeContext,
            UltimateStageSettings settings)
        {
            if (_isEntered
                || runtimeContext?.Caster == null
                || settings?.stagePrefab == null)
            {
                yield break;
            }

            yield return FadeRoutine(0f, 1f, settings.fadeOutDuration);

            _isEntered = true;
            _caster = runtimeContext.Caster;
            // ... 백업 → 스테이지 생성 → 워프 → 레이어 전환 → 컬링마스크 교체

            if (settings.fadeHoldDuration > 0f)
                yield return WaitUnscaled(settings.fadeHoldDuration);

            yield return FadeRoutine(1f, 0f, settings.fadeInDuration);
        }

        /// <summary>동기 복구. Restore()가 중단/사망/OnDisable 경로에서도 호출한다.</summary>
        public void Exit()
        {
            if (!_isEntered)
                return;

            // 컬링마스크 → 레이어 → 좌표 → 스테이지 인스턴스 순서로 원복
            _isEntered = false;
        }
    }
}

왜 스테이지가 placement보다 먼저인가. UltimatePlacementContext는 캐스터/타깃의 현재 좌표를 기준으로 상대 배치를 계산한다. 스테이지 워프를 먼저 끝내야 placement가 스테이지 안에서 올바른 상대 배치를 만든다. 순서를 바꾸면 캐스터가 스테이지 밖에 배치된다.

_canvasGroup.alpha = to;

6. 함정 5가지

함정 1 — Restore()는 동기 메서드다. UltimateSequencePlayer.cs:377. OnDisable, 캐스터 사망, 타깃 소실, 실패 경로가 모두 여기로 들어온다. 복귀 페이드를 기다리려고 코루틴을 걸면 중단 시 플레이어가 스테이지에 갇힌다. 상태 복구는 즉시, 페이드인은 UI가 독립적으로 재생하는 구조여야 한다.
함정 2 — 연출 씬을 Active로 만들지 말 것. HandleActiveSceneChanged(:459)가 무조건 Restore(SceneChanged)를 호출한다. 방식 3으로 확장한다면 이 메서드에 "연출 중 예외" 플래그를 먼저 넣어야 한다.
함정 3 — 레이어 원복 누락. 캐스터의 레이어를 자식까지 바꾼 뒤 복구를 놓치면 전투 콜리전과 카메라 컬링이 영구히 망가진다. Dictionary<GameObject, int>로 바꾼 오브젝트만 기록하고, 복구 시 == null 체크 후 되돌린다. (연출 중 파괴된 오브젝트가 있을 수 있다)
함정 4 — 카메라 컬링마스크 소유권. 다른 시스템이 동시에 컬링마스크를 만졌다면 무조건 덮어쓰면 안 된다. UltimateGameplayLockContext의 _ownsCameraInputLock 패턴처럼 "내가 바꿨을 때만 되돌린다" 플래그를 두는 것이 이 프로젝트의 규약이다.
함정 5 — 스테이지 프리팹 상주 비용. 매 발동마다 Instantiate/Destroy하면 히칭이 생긴다. 첫 사용 시 생성 후 SetActive(false)로 캐시하거나 GameObjectManager 풀링에 얹는다. 단, 씬 전환 시 정리 책임을 명확히 할 것.
