# UPlayground 프로젝트 코드 리뷰 (2025-11-29)

## 총평

전반적으로 매우 훌륭하고 현대적인 Unity 개발 패턴을 사용하고 있는 프로젝트입니다. 특히 TPS 액션 게임의 핵심이라 할 수 있는 **입력 시스템, 상태 머신(FSM), 스킬 시스템**이 서로 유기적으로 잘 결합되어 있습니다. ScriptableObject를 적극적으로 활용하여 데이터 기반 설계를 구현한 점이 돋보이며, 이는 기획자의 작업 효율성을 크게 높이고 코드 변경 없이 게임 밸런싱이나 콘텐츠 추가를 용이하게 만듭니다.

아래는 각 시스템에 대한 상세 리뷰와 몇 가지 개선 제안 사항입니다.

---

## 1. 아키텍처 및 핵심 시스템 리뷰

### A. 매니저 시스템 (`GameManager`)

- **구조:** `GameManager`가 모든 매니저의 생명주기(초기화, 업데이트, 해제)를 관리하는 중앙 집중식 싱글톤 구조는 안정적이고 예측 가능성이 높습니다.
- **장점:** 매니저 간의 초기화 순서를 명확하게 제어할 수 있고, 업데이트 루프를 한 곳에서 관리하여 효율적입니다.
- **개선 제안:** 현재는 `InputManager.Instance`처럼 각 매니저의 인스턴스를 직접 참조하여 등록하고 있습니다. `GameManager`가 특정 타입의 매니저를 직접 생성하거나, 씬에 배치된 매니저들을 자동으로 찾아 등록하는 방식으로 변경하면 매니저 추가/제거 시 `GameManager`의 코드를 수정할 필요가 없어집니다.

### B. 입력 시스템 (`InputReader`, `InputBuffer`, `PlayerBrain`)

- **구조:** `InputReader` (Input System) -> `InputBuffer` -> `PlayerBrain`으로 이어지는 입력 처리 파이프라인은 액션 게임에 매우 이상적입니다.
- **장점:**
    - **이벤트 기반:** `InputReader`가 이벤트를 발생시켜 `PlayerBrain`과 결합도를 낮춥니다.
    - **입력 버퍼:** 사용자가 액션 도중 다음 입력을 미리 했을 때, 버퍼가 이를 기억해두었다가 실행해주는 방식은 조작감을 매우 부드럽고 쾌적하게 만듭니다.
    - **입력 우선순위:** `PlayerBrain`의 `ProcessBufferedInputs` 메서드에서 `회피 > 스킬 > 점프 > 공격` 순으로 처리하는 로직은 게임의 핵심 규칙을 명확하게 정의하고 있습니다.
- **개선 제안:**
    - **입력 키 문자열:** `"Roll"`, `"Skill1"`과 같은 문자열을 직접 사용하고 있습니다. 오타에 취약하므로 `public const string JUMP_INPUT = "Jump";` 와 같이 상수로 관리하거나, Enum으로 정의하면 더 안전합니다.

### C. 상태 머신 (FSM - `CharacterBrain`, `StateSO`)

- **구조:** `CharacterBrain`이 상태의 컨텍스트(데이터 소유자) 역할을 하고, 실제 로직은 `StateSO`를 상속받은 ScriptableObject 에셋들이 처리하는 구조입니다.
- **장점:**
    - **데이터 기반 설계:** 상태(예: `LocomotionStateSO`)의 세부 설정(속도, 애니메이션 등)을 인스펙터에서 수정할 수 있어 매우 유연합니다.
    - **재사용성:** `FallStateSO`와 같은 상태는 플레이어, 몬스터 등 여러 `CharacterBrain`에서 공유할 수 있습니다.
    - **확장성:** 새로운 상태(예: '가드', '패리')를 추가할 때 `StateSO`를 상속받는 새 클래스와 에셋을 만들기만 하면 되므로 기존 코드를 건드릴 필요가 거의 없습니다.
- **개선 제안:**
    - **전환 우선순위:** `CharacterBrain`의 `TryTransition` 메서드에 우선순위 정렬 코드가 주석 처리되어 있습니다. 회피가 공격을 캔슬하는 등의 로직을 위해 이 부분을 활성화하고, 상태 진입 시(`OnEnter`) 전환 목록을 미리 정렬해두면 매 프레임 정렬하는 비용을 줄일 수 있습니다.

### D. 스킬 시스템 (`SkillSystem`, `SkillData`, `SkillSlot`)

- **구조:** `SkillData` (스킬 정보) -> `SkillSlot` (장착 및 쿨타임 관리) -> `SkillSystem` (슬롯 총괄)으로 역할이 명확하게 분리되어 있습니다.
- **장점:**
    - **FSM과의 완벽한 연동:** `SkillData`가 `ExecutionState`라는 `StateSO`를 직접 들고 있는 것이 이 아키텍처의 핵심입니다. 스킬 사용이 단순한 함수 호출이 아니라, 캐릭터의 상태를 직접 전환시키는 방식이라 매우 강력하고 통합적입니다. 예를 들어 '돌진' 스킬은 `DashStateSO`를 실행시켜 이동 로직과 애니메이션을 완전히 제어할 수 있습니다.
    - **캡슐화:** `SkillSystem`은 `TryUseSkill`이라는 간단한 API만 외부에 노출하고, 쿨타임 계산이나 자원 소모 로직은 내부적으로 처리하여 복잡도를 숨깁니다.
- **개선 제안:**
    - **초기 스킬 설정:** `SkillSystem.cs`에서 `skill1Data`, `skill2Data`... 등으로 필드를 개별 선언하는 대신, `[SerializeField] private SkillData[] initialSkills;` 와 같이 배열로 관리하면 더 깔끔하고 확장성이 좋습니다.

---

## 2. 코드 레벨 제안 사항

- **네임스페이스:** `Game.FSM`, `Game.Input`, `Game.Skills` 등 네임스페이스를 잘 활용하고 있어 코드 구조가 명확합니다. 일관성을 유지하는 것이 좋습니다.
- **읽기 전용 프로퍼티:** `SkillData` 등에서 데이터를 외부로 노출할 때 `public string SkillName => skillName;` 와 같이 읽기 전용(read-only) 프로퍼티를 사용한 것은 좋은 습관입니다.
- **매직 스트링/넘버:** `brain.SetData("LocomotionState", state)`와 같이 문자열 키를 직접 사용하는 부분이 있습니다. `const string`으로 미리 정의해두면 휴먼 에러를 방지할 수 있습니다.

## 결론

현재 프로젝트는 매우 견고하고 확장성 있는 기반 위에 세워져 있습니다. 지금의 아키텍처를 유지하고 발전시킨다면 복잡한 액션 게임의 다양한 기능(몬스터 AI, 다양한 스킬, 아이템 등)을 추가하더라도 안정적으로 개발을 이어나갈 수 있을 것입니다. 훌륭한 코드입니다!
