# 역할 분담 하네스

리드 한 명이 계획·통합·보고를 맡고, 독립적으로 떼어낼 수 있는 일만 역할 Agent에게 맡기는 운영 규칙이다. [공통 작업 하네스](README.md)의 절차를 대체하지 않고 그 위에서 동작한다. Claude Code(`.claude/agents/`)와 Codex(`.codex/agents/`)의 역할 정의는 모두 이 문서와 `roles/`의 역할 문서를 정본으로 읽는다.

## 왜 이 구조인가

- Anthropic의 다중 Agent 경험상 코딩은 연구보다 진짜 병렬 가능한 일이 적고, 맥락을 공유해야 하거나 서로 의존하는 일은 다중 Agent에 맞지 않는다. 다중 Agent는 일반 대화보다 토큰을 약 15배 쓴다.
- Claude Code 공식 지침도 계획·구현·테스트처럼 맥락을 크게 공유하는 단계는 메인 대화에서, 출력이 길고 자기완결적이며 요약해 돌려받을 수 있는 일은 서브 Agent에서 하라고 권한다.
- 그래서 역할을 수십 개로 쪼개지 않는다. 1인 개발에서 실제로 이득이 나는 지점만 역할로 둔다. 확증 편향 없는 **독립 검증**, 화면 캡처가 많은 **아트 파이프라인**, 구현자와 다른 눈으로 보는 **플레이 경험 검토**, 파일이 겹치지 않는 **병렬 구현**이다.

## 역할

| 역할 | 정의 | 주 산출물 | 맡기지 않는 일 |
|---|---|---|---|
| 리드 (메인 세션) | [lead.md](roles/lead.md) | 계획, 위임 브리프, 통합, 위키·상태 문서, 사용자 보고 | — |
| 서브 프로그래머 | [sub-programmer.md](roles/sub-programmer.md) | 범위가 정해진 코드 단위 구현 | 모듈을 가로지르는 결합 변경, 설계 결정 |
| 디자이너 | [designer.md](roles/designer.md) | 플레이 경험 검토, 설계 문서, 데이터 저작(BT·Ability·퀘스트·대사) | C# 코드 수정 |
| 아티스트 | [artist.md](roles/artist.md) | 구매·MCP 아트 제작·연결, 인수 기록 | C# 코드 수정, 미술 품질 최종 판정 |
| QA 검토자 | [qa-reviewer.md](roles/qa-reviewer.md) | 독립 검증 결과(통과·실패·미수행과 근거) | 파일 수정 |

리드는 별도 Agent가 아니라 사용자와 대화하는 메인 세션이다. 역할 Agent는 다른 Agent를 다시 부르지 않는다.

## 위임 기준

위임은 사용자가 역할을 지정했을 때, 또는 리드가 아래 기준에 맞는다고 판단할 때만 한다. 새 승인 단계는 추가하지 않는다.

**맡긴다**

- 여러 단계·여러 파일에 걸친 변경을 마친 뒤의 독립 검증 → QA 검토자
- Blender·Unity MCP 촬영과 반복 수정이 많은 아트 작업 → 아티스트
- 기능 설계나 밸런스·대사·전투 데이터 변경의 플레이 경험 검토 → 디자이너
- 소유 파일이 서로 겹치지 않고 계약(인터페이스·데이터 형식)이 이미 정해진 구현 단위 → 서브 프로그래머

**맡기지 않는다**

- 바로 끝나는 국소 수정, 사용자와 자주 주고받아야 하는 일
- 계획·구현·검증이 같은 맥락을 크게 공유하는 일, 계약이 아직 정해지지 않은 설계 단계
- 같은 파일·같은 에셋을 두 Agent가 동시에 고쳐야 하는 일

## 공유 자원 규칙

- **Unity Editor는 하나다.** 컴파일을 일으키는 스크립트 저장, Play Mode 진입, MCP를 통한 에셋·씬 쓰기, 테스트 실행은 브리프에서 `Unity 슬롯`을 받은 Agent 하나만 한다. 슬롯이 없는 Agent는 Console·씬 조회 같은 읽기만 하고 필요한 Unity 작업을 보고에 적는다. 두 번째 Editor를 열거나 잠금 파일을 지우지 않는다.
- **Blender 인스턴스도 하나다.** 아트 작업이 둘이면 순차로 진행한다.
- **파일 소유.** 브리프의 `소유 파일` 밖은 수정하지 않는다. 범위 밖 수정이 필요하면 멈추고 보고한다.
- **위키·상태 문서는 리드만 쓴다.** 역할 Agent는 `위키 반영 필요` 항목으로 돌려준다. 같은 문서에 여러 Agent가 동시에 쓰는 충돌을 막기 위해서다.
- 커밋, Player·Addressables 빌드는 어떤 역할도 하지 않는다(사용자 지시가 있을 때 리드가 수행).

## 위임 브리프

역할 Agent는 대화 이력을 물려받지 않는다. 리드는 아래 항목을 채워 넘긴다. 빈 항목은 `없음`으로 쓴다.

```text
목표: 플레이어 경험 관점의 목적 한 줄
완료 조건: 관찰 가능한 조건(무엇이 어떻게 되면 끝인가)
소유 파일: 수정해도 되는 파일·폴더·에셋
읽기 전용 참조: 함께 봐야 할 소비자·연결 에셋
필독 지침: AGENTS.md 작업별 표에서 해당하는 지침 링크
Unity 슬롯: 있음/없음 (있으면 허용 작업: 컴파일·Play Mode·테스트·에셋 쓰기 중)
금지: 이번 작업에서 특히 하지 말 것
알려진 사실: 리드가 이미 확인한 사실과 근거(재조사 방지)
```

## 결과 보고

역할 Agent는 아래 형식으로 끝낸다. 리드는 이 보고를 주장으로 취급하고, 핵심 근거(diff·로그·캡처)를 직접 확인한 뒤 사용자에게 보고한다.

```text
판정: 완료 / 부분 완료 / 차단 / 실패
변경: 파일·에셋 경로와 한 줄 요약 (없으면 없음)
검증: 수행한 검사와 결과·원본 근거 경로 / 미수행 항목과 사유
사용자 확인 필요: 플레이·아트 품질 등 Agent가 판정할 수 없는 항목
위험·발견: 범위 밖에서 발견한 문제(수정하지 않음)
위키 반영 필요: 리드가 갱신할 분야·내용
부산물: 남긴 임시 자료와 이유, 정리한 경로
```
