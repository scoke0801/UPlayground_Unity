# 런타임 성능 오버헤드 조사 (매니저 / 액터 / BT)

> 조사 범위: `Assets/02.Scripts` (ExternalAssets 제외)
> 조사 목적: 매 프레임/틱 단위 핫패스에서 발생하는 CPU·GC 오버헤드 식별 및 개선안 제시
> 핵심 결론: **상태머신의 `new` 할당 + 핫패스 `GetComponent`** 가 가장 큰 GC 원인. 그다음이 BT 틱당 타입체크와 할당형 물리 쿼리.

> **2026-06-04 1차 수정 적용분**
> - `EnemyChaseState`: `EnemyTacticalMemory`를 생성자에서 1회 캐싱(`_memory`), self 콜라이더를 최초 1회만 수집하도록 `CacheContactColliders` 가드 추가. `UpdateState`/`OnMovementHit`의 매-전환 `GetComponent` 제거.
> - `EnemyDetection`: 5개 물리 쿼리(`DetectNewTarget`/`GetAllyCount`/`GetNearbyAllies`/`HasInjuredAllyNearby`/`GetMostInjuredAlly`)를 `Physics.OverlapSphereNonAlloc` + 재사용 버퍼(`_overlapBuffer[64]`)로 전환. 인터페이스 `GetComponent<IDamageable>` → `TryGetComponent`.
> - `BTNode.Tick`: 틱마다 수행하던 `this as BTCompositeNode` / `this is BTConditionNode` 캐스팅을 `Initialize` 시점 1회 캐싱(`_compositeSelf`/`_conditionSelf`)으로 대체.
>
> **상태 객체 풀링(P1)은 보류:** 50여 개 상태 클래스가 진입별 가변 필드(타이머·플래그)를 보유하고 `new` 호출이 170곳에 분산되어 있어, 풀링 전환 시 `OnEnter` 전체 필드 리셋 보장과 생성자 주입 구조 변경이 필요. 게임플레이 전이 의미를 바꾸는 고위험 작업이라 별도 설계 후 단계적으로 진행 권장.

> **2026-06-04 2차 수정 적용분 (P3)**
> - **중앙 틱 통합:** `AgentTickManager`(신규, `Manager/Actor/AgentTickManager.cs`) + `IManagedTick` 인터페이스 추가. `BehaviorTreeRunner` / `EnemyDetection`의 개별 `Update`를 제거하고 `ManagedTick(deltaTime)`로 전환, `OnEnable`에서 매니저에 자가 등록 / `OnDisable`에서 해제. 적 N마리당 발생하던 (BT + Detection) = 2N개의 네이티브 Update 디스패치가 매니저 1개 루프로 통합됨. 각 구성요소가 자체 타이머(`_tickInterval`/`_detectionInterval`)를 유지하므로 동작은 동일.
>   - 등록/해제는 순회 중 안전(null 마킹 후 프레임 말미 일괄 compact), 에디터 모드 매니저 자동 생성 방지를 위해 `Application.isPlaying` 가드.
> - **`GameManager.GetManager<T>`:** 선형 `is` 탐색 → `Dictionary<Type, IManager>` 캐시로 O(1). 인터페이스/베이스 타입 조회는 선형 폴백 유지.
>
> **블랙보드 키 핸들화 보류:** `Blackboard`는 이미 `Dictionary<string, Entry>`로 O(1) 조회를 제공하므로 남은 비용은 문자열 해시뿐. entry 참조를 selector에 캐싱하면 런타임 클론마다 블랙보드 인스턴스가 달라 stale 위험이 커서, 비용 대비 가치가 낮아 보류.

## 🔴 P1 — 상태머신 `new` 할당 (가장 큰 GC 원인)

`GameActor/State` 전반에 **`new XxxState(...)` 호출이 170곳** 존재. 상태 전환마다 힙 객체가 새로 생성된다.

특히 `EnemyChaseState`는 매 프레임 호출되는 `UpdateState`/`UpdateVelocity`/`OnMovementHit`에서 후보 상태를 즉석 생성한다.

```csharp
// EnemyChaseState.cs:71, 181 등 — 프레임마다 평가되는 경로에서 객체 생성
controller.TransitionToState(new EnemyJumpBackState(controller, _context, _detection,
    gameActor.GetComponent<EnemyTacticalMemory>()));   // ← new + GetComponent 동시 발생
```

게다가 `ActorMovementController.cs:148` 의 전이 가드는 **객체를 먼저 생성한 뒤** 전환 가능 여부를 검사한다 — 거부되는 전환조차 garbage를 만든다.

```csharp
public bool TryTransitionToState(GameActorState newState)  // newState는 이미 할당된 상태
{
    if (newState.CanTransitionState(CurrentState.StateName) == false)
        return false;   // 할당된 객체가 그대로 버려짐 → GC
    TransitionToState(newState);
    return true;
}
```

**개선 방향**
- 상태 객체를 액터당 1회 사전 생성해 캐싱(상태 인스턴스 풀).
- 상태들이 생성자에서 `controller / context / detection` 만 받으므로, 액터 초기화 시 `Dictionary<Type, GameActorState>` 또는 enum→인스턴스 배열로 한 번만 만들고 재사용.
- 가드 검사는 캐싱된 인스턴스에 대해 수행하여 "거부 시 할당" 자체를 제거.
- **효과:** 전투 중 GC.Alloc 스파이크 제거 → 프레임 히치 감소 (적이 다수일수록 효과 큼).

## 🔴 P1 — 핫패스 `GetComponent` / 배열 할당

- `EnemyChaseState.UpdateState`/`OnMovementHit`: `gameActor.GetComponent<EnemyTacticalMemory>()` 를 전환 시마다 호출.
  → **`EnemyAIController` 는 이미 `_memory` 를 캐싱**(`EnemyAIController.cs:27, 105`)하고 있으므로 주입받아 재사용하면 된다.
- `EnemyChaseState.CacheContactColliders` (`EnemyChaseState.cs:207`): `GetComponentsInChildren<Collider>()` 로 self+target 배열을 OnEnter·타겟 변경마다 할당. self 콜라이더는 액터 생성 시 1회 캐싱으로 충분.

**개선 방향**
- 모든 컴포넌트 참조는 `Awake/Init` 에서 캐싱.
- `GetComponent<인터페이스>` 는 특히 비싸므로 우선 제거.

## 🟠 P2 — EnemyDetection: 할당형 물리 쿼리

`EnemyDetection.cs` 의 다음 메서드가 모두 할당형 `Physics.OverlapSphere` + 인터페이스 `GetComponent` 를 사용한다.

| 메서드 | 라인 |
|---|---|
| `DetectNewTarget` | 87 |
| `GetAllyCount` | 183 |
| `GetNearbyAllies` | 210 |
| `HasInjuredAllyNearby` | 234 |
| `GetMostInjuredAlly` | 261 |

```csharp
Collider[] colliders = Physics.OverlapSphere(...);     // 매 호출 새 배열 할당
var damageable = collider.GetComponent<IDamageable>(); // 인터페이스 GetComponent (비쌈)
```

`_detectionInterval`(0.2초) gating으로 빈도는 낮지만, 적 수 × 초당 5회 × 결과 콜라이더 수만큼 누적된다.

**개선 방향**
- `Physics.OverlapSphereNonAlloc(... buffer)` 로 재사용 버퍼 사용 (멤버 `Collider[64]` 등).
- `collider.TryGetComponent<IDamageable>(out var d)` 사용 + 콜라이더→IDamageable 결과 캐싱.
- `DistanceToTarget`(`EnemyDetection.cs:32`)은 `Vector3.Distance`(sqrt). BT `IsTargetInRangeNode` 가 매 틱 읽으므로 `sqrMagnitude` 비교로 전환.

## 🟠 P2 — BT 노드 틱당 런타임 타입 체크

`BTNode.Tick()` (`BTNode.cs:83~`) 이 **모든 노드, 모든 틱마다** 런타임 캐스팅을 수행한다.

```csharp
var compositeSelf = this as BTCompositeNode;          // 매 틱
...
if (this is BTConditionNode conditionNode) { ... }    // 매 틱
```

비용 = 트리 노드 수 × 적 수 × (1 / `_tickInterval`). 또한 `_context?.DebugTrace?.Record(...)` 가 디버그 OFF 상태에서도 `DebugTrace` getter(`Runner != null && Runner.DebugMode`)를 매번 평가한다.

**개선 방향**
- 캐스팅 결과를 노드 필드에 1회 캐시(`OnInitialize` 에서 `_compositeSelf`, `_isCondition` 저장), 또는 `virtual bool IsComposite` 플래그.
- 디버그 추적은 `_context.DebugEnabled` bool 한 번으로 분기 후 진입.

## 🟡 P3 — 적 1마리당 MonoBehaviour Update 4개

적마다 다음 4개의 `Update` 가 독립적으로 돈다.

- `BehaviorTreeRunner.Update` (`BehaviorTreeRunner.cs:62`)
- `EnemyDetection.Update` (`EnemyDetection.cs:37`)
- `ActorMovementController.Update` (`ActorMovementController.cs:111`)
- `EnemyAIController.Update` (`EnemyAIController.cs:159`)

Unity의 네이티브↔매니지드 `Update` 호출은 개수 자체가 비용이라, 적이 수십 마리면 누적된다.

**개선 방향**
- 이미 `IManager` + `GameManager` 가 중앙 틱 루프를 보유하므로, BT/Detection을 중앙 매니저(`EnemyAIManager`)에 등록해 한 곳에서 순회 틱.
- MonoBehaviour Update 4개 → 매니저 1개 루프로 통합.
- 단, KCC 콜백과 결합된 `MovementController` 는 분리 검토 필요.

## 🟡 P3 — 블랙보드 문자열 키 & 매니저 미세 항목

- **Blackboard** (`Blackboard.cs`): `Dictionary<string, Entry>` 기반. 서비스/컨디션 노드가 매 틱 다수 `TryGetFloat/SetFloat` 를 문자열 키로 호출 → 할당은 없으나 문자열 해시 비용. `BlackboardKeySelector` 가 entry 참조를 캐싱하거나 int 핸들 인덱싱으로 개선 가능.
- **GameManager.Update/FixedUpdate/LateUpdate** (`GameManager.cs:157~179`): 21개 매니저 전부 `OnUpdate()` 가상 호출(빈 것 포함). "업데이트가 필요한 매니저"만 별도 리스트로 분리하면 불필요한 가상 디스패치 제거.
- **`BaseManager.Instance`** getter(`BaseManager.cs:18`)는 `lock` + 종료 플래그 체크 포함. 핫패스에서 `XxxManager.Instance` 를 반복 호출하는 코드는 로컬 변수로 캐싱 권장.
- `GameManager.GetManager<T>()`(`GameManager.cs:129`)는 선형 탐색 + `is` 캐스팅 — 호출 빈도가 높다면 `Dictionary<Type, IManager>` 로.
