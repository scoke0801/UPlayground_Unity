IMPLEMENTATION SPECIFICATION

목표·전제·종료 범위

1.1 프로젝트 전제

기존 대화의 Unity 6 기반 액션 RPG/TPS 프로젝트를 적용 대상으로 삼는다. Animancer 기반 애니메이션, 이동·전투·카메라 로직과 여러 asmdef가 존재할 가능성이 높지만, 실제 클래스 이름과 현재 패키지 구성을 이 문서가 확인한 것은 아니다. 최근 작업 맥락에는 Unity 6000.3.21f1 / URP 17.3.0이 언급되었고 과거에는 6000.0.60f1을 사용했다. 어느 값도 하드코딩하지 말고 G0에서 저장소와 실행 중 Editor를 대조한다.

1.2 v1의 보장 경계

실제로 확인한 Unity Editor + OS/CPU 조합에서, 허용 목록에 등록하고 사전에 일반 컴파일한 메인 스레드용 비제네릭 클래스 메서드를 지원한다. 첫 플랫폼은 현재 개발 PC를 우선한다. 다른 OS·CPU는 해당 환경의 테스트를 통과하기 전까지 미지원이다. 단일 플레이 세션에서 기존 객체의 필드와 참조를 유지하는 것이 목표이며, 게임 상태의 과거 시점 복원은 목표가 아니다.

필수 완료 범위v1에서 제외할 범위
기존 인스턴스/static 메서드, private/internal/public 접근, 오버로드, 여러 asmdef, partial 파일의 본문 수정필드·타입·시그니처·상속 관계 변경, 새로운 메서드/타입 추가, 생성자·static 초기화 변경
올바른 원본 타입 재연결, 일반 분기·루프·기존 API 호출, 지정된 예외 처리 지원, 코드 롤백async/iterator/람다/로컬 함수 등 컴파일러 생성 코드를 포함한 메서드의 변경
파일 감지, 외부 컴파일러, 검증기, 원자적 적용 시도, 실패 복구, UI, 에이전트 연결, 로그, 테스트Burst/Jobs/Entities 생성 코드, IL2CPP 또는 배포 Player 패치, Native 함수, 임의 Editor 내부 코드 패치
원본 소스 기반 정상 컴파일 및 Player 빌드에서 도구 의존성 제외 확인상용 제품과 100% 기능 동등성, 완전한 디버거 소스 재매핑, 임의 멀티스레드 실행 중 패치
속도를 위해 정확성을 희생하지 않는다
v1은 변경이 포함된 어셈블리 전체를 외부 프로세스에서 컴파일할 수 있다. Unity 전체 스크립트 컴파일/Domain Reload를 피하는 것이 1차 가치이며, 처음부터 “변경 메서드만 수 ms 컴파일”을 약속하지 않는다.

1.3 금지 사항

상용 패키지의 비공개 DLL·서버·라이선스 검증 로직 추출/복제, 인증 우회, 출처 불명 바이너리 사용을 작업에 포함하지 않는다. 기존 사용자 변경을 reset/stash/delete하지 않으며, 엔진 업그레이드·대규모 asmdef 재편·전역 Editor 설정 변경을 조용히 수행하지 않는다. 기본 구현이 불가능한 경우 기능을 몰래 축소하지 말고 재현 사례와 대안을 기록한다.

1.4 최종 판정

VERIFIED_V1은 G0~G12 필수 항목이 모두 PASS일 때만 쓴다. 코드만 준비되면 IMPLEMENTED_UNVERIFIED, 실행했으나 실패하면 FAILED_VALIDATION, G1에서 핵심 패치 경로가 성립하지 않으면 BACKEND_BLOCKED다. “대부분 구현”이나 “컴파일될 것으로 보임”은 완료 판정이 아니다.

IMPLEMENTATION SPECIFICATION

지원 매트릭스와 안전한 거부 정책

아래 “필수”는 구현해야 할 목표이지 이미 검증된 기능이 아니다. 모든 변경은 소스 분석과 출력 IL 검사 두 관문을 통과해야 한다. 검증기가 해석할 수 없는 경우 허용하지 않는다.

변경/상황v1 정책판정 및 테스트
기존 비제네릭 참조 타입 메서드 본문필수메인 스레드 + 사전 NoInlining + allowlist. 인스턴스/static, private/internal/public을 실제 테스트.
int/float/bool/string/참조/Vector3 반환필수원본 시그니처 불변. Vector3 등 값 타입 반환 ABI는 실제 Unity에서 확인.
여러 overload, partial 타입, 다중 asmdef필수완전한 MethodKey로 구분. 현재 .cs 파일만으로 타입을 복제하지 않음.
지역 변수 추가·삭제·형식 변경필수객체 필드 변경과 구별. local signature와 모든 ldloc/stloc/ldloca를 다시 매핑.
기존 private 필드/메서드와 static 상태 접근필수원본 FieldInfo/MethodInfo로 재연결. 생성자/초기화 재실행 금지.
일반 if/switch/loop, 기존 API 호출필수모든 분기 목적지·스택·피연산자 검증. 알 수 없는 opcode는 거부.
기존 닫힌 제네릭 타입/API 호출필수예: List 읽기. 대상 메서드 자체가 제네릭인 것과 구분. 제네릭 인자 재귀 매핑.
기존 API의 out/ref 인자 사용필수예: Raycast의 out 결과. 호출 피연산자와 local address를 보존. 대상 메서드 자체의 ref ABI 지원과 구분.
일반 try/catch/finally, using으로 생성된 finally필수중첩 catch/finally 포함 G4의 EH 테스트를 통과해야 허용. filter/fault는 제외.
기존의 명시적 property/indexer 접근자 본문필수실제 get_/set_ 메서드로 매칭. auto-property의 필드 구조 변경은 제외.
새 local lambda/local function/async/yield 또는 그 내부 수정거부메서드에 이러한 생성 코드를 포함하면 기존 구조가 비슷해도 v1은 보수적으로 FullCompileRequired.
이미 존재하는 코루틴/비동기 메서드를 단순 호출조건부 필수호출자 본문이 지원 범위이고 기존 MethodInfo를 참조하면 허용. 진행 중 상태머신 자체를 갱신하지 않음.
필드 초기값·const·attribute·signature·타입 추가/삭제거부메서드 본문처럼 보여도 메타데이터/초기화 변화로 분류. 현재 세션 유지 + 명시적 정상 컴파일.
새 메서드, 기존 메서드 삭제/rename거부새 코드가 호출 가능한지와 별개로 런타임 표면 변화이므로 v1 전체 배치 거부.
제네릭 메서드/제네릭 선언 타입의 대상 메서드거부runtime specialization과 코드 공유를 v1에서 보장하지 않음. [S17]
struct instance 메서드, ref-return, ref/out/in 대상 인자거부this byref/ABI 등 추가 검증이 필요. 외부 API 호출의 ref/out 피연산자 처리는 별개.

4.1 선택: IL 재연결 + 메서드 본문 전체 교체

외부 Worker는 현재 소스의 컴파일 결과를 실행 대상이 아니라 IL 분석 자료로 사용한다. 컴파일된 게임 어셈블리를 Unity에 Assembly.Load하지 않는다. 변경된 메서드의 IL 피연산자를 원본 런타임 타입과 멤버로 해석한 뒤, Harmony transpiler가 해당 본문을 반환한다. 기존 인스턴스의 this는 그대로 유지된다.

Harmony transpiler는 호출마다 Roslyn을 실행하는 장치가 아니라 패치 코드 생성 시점의 IL 변환이다. Cecil은 실행용 어셈블리 로드 없이 메타데이터와 IL을 읽을 수 있다. 두 기능을 이 설계에 조합하는 것이며, 이 조합의 Unity 호환성은 반드시 G1에서 입증한다. [S15] [S20]

6.2 A0 / Eg / Sr를 분리한다

기호의미갱신 규칙
A0 / RuntimeBaselineUnity가 정상 컴파일하여 현재 로드한 원본 타입·메타데이터·코드실제 정상 컴파일/재로드 후에만 변경. 패치 성공으로 A0를 덮어쓰지 않는다.
Eg / EffectiveGeneration현재 실행 코드. A0 위에 적용된 메서드별 본문 맵패치 또는 코드 롤백의 성공이 확인된 후에만 원자적으로 승격.
Sr / SourceSnapshot현재 디스크 소스의 동결된 revision저장/재스캔 때 생성. 컴파일 실패나 비지원 변경도 Sr에는 존재할 수 있다.
W0 / WorkerBaselineA0와 연결된 소스를 동일 Worker profile로 컴파일한 기준 결과초기 컨텍스트 준비 시 생성. 새로운 Worker 컴파일 결과와 비교하는 기준.

비교는 두 축이다. 구조와 런타임 연결 가능성은 A0에 대해 검증하고, 이번에 바꿔야 하는 실행 본문은 Eg에 대해 계산한다. 소스를 원본으로 되돌린 메서드도 감지해야 하므로 “A0와 다른 메서드만 적용”으로 구현하면 안 된다.

6.3 기준선을 신뢰할 수 있는 조건

세션 시작 전에 마지막 정상 컴파일의 소스 해시와 현재 소스가 대응하는지 확인한다. 추적 기록이 없거나 컴파일 중 파일이 바뀌었다면 Play Mode 안에서 임의의 baseline을 만들지 않는다. 일반 컴파일을 요청하고, 컴파일 시작/종료 동안 입력 해시가 안정적이며 모든 오류가 없고 새 모듈이 로드된 뒤 기준선을 확정한다.

W0와 새 결과는 동일 CompilerProfile로 비교한다. 또한 패치 대상은 W0의 정규화된 본문·시그니처를 실제 A0의 런타임 본문과 비교한다. 디버그 nop 같은 허용된 차이만 정규화하고, 그 외 차이를 “아마 같은 코드”로 넘기지 않는다. IL 후처리나 컴파일 옵션 차이가 남으면 BaselineParityFailed다. Unity와 Worker가 생성하는 바이너리 전체 SHA가 같아야 한다는 요구는 아니며, 패치 대상의 동작에 영향을 주는 IL/메타데이터 대응이 요구된다.

6.4 변경 범위 탐색

메서드 본문 텍스트만 비교하지 않는다. using 별칭 변경으로 같은 텍스트의 호출 대상이 달라질 수 있으므로 영향을 받은 어셈블리의 정규화된 출력과 symbol binding을 비교한다. const, attribute, 초기화, 상속, 인터페이스, 필드 레이아웃, 메서드 추가/삭제, preprocessor 조건의 변화는 별도 구조 변경으로 다룬다. .asmdef/.asmref/.rsp/manifest/참조 DLL 변경은 컨텍스트를 무효화한다.

7.1 실행용 DLL 대신 의미 있는 IL 계획을 전달한다

Worker가 생성하는 NormalizedMethodBody는 기계어도, 기존 모듈에서 그대로 쓸 수 있는 raw metadata token도 아니다. 명령·지역 변수·분기 목적지·예외 영역과 의미 기반 멤버 식별자의 집합이다. Editor는 이를 현재 세션의 원본 런타임 객체로 해석한다.

7.2 반드시 지켜야 하는 재연결 규칙

  1. 자기 타입: 새 PE의 PlayerController TypeDef는 원본의 실제 System.Type으로 매핑한다. 새 타입 객체를 만들지 않는다.
  2. 인스턴스/정적 멤버: ldfld/stfld/ldsfld/stsfld/call/callvirt/newobj/ldtoken 등의 operand를 해당 원본 모듈의 실제 멤버로 변환한다. static 저장소는 A0의 저장소 하나만 사용한다.
  3. 제네릭 피연산자: List<PlayerController>의 PlayerController도 재귀적으로 원본 타입으로 바꾼다. 닫힌 기존 API 호출만 허용한다.
  4. 호출 의미: call과 callvirt를 임의 교환하지 않는다. base 호출을 MethodInfo.Invoke로 흉내 내지 않는다. virtual/interface dispatch, null 검사, boxing/unboxing 의미를 보존한다.
  5. 자기/서로 호출: 재귀와 다른 패치 대상 호출도 원본 MethodInfo를 가리킨다. 이번 배치의 새 PE 메서드를 가리키면 안 된다.
  6. 컴파일러 생성 의존: display class, state machine, 익명 타입, 새 정적 데이터 blob 등 A0에 안전하게 대응되지 않는 참조는 거부한다. 이름이 비슷하다고 토큰 번호를 맞추지 않는다.
  7. 접근 제어: private 접근이 가능한 실행 위치/라이브러리 동작을 G1에서 검증한다. 실패하면 모든 필드를 public으로 바꾸거나 reflection 호출로 몰래 대체하지 않는다.
  8. 외부 참조: 로드된 원본 assembly identity/hash에 정확히 대응해야 한다. 임의 AssemblyResolve 핸들러로 다른 버전의 DLL을 끼워 넣지 않는다.

7.3 Harmony transpiler에서의 변환 순서

G1에서 검증한 Harmony 버전의 CodeInstruction 계약을 사용한다. 분기는 Label, local은 LocalBuilder로 다루며 transpiler 내부에서 임의로 ILGenerator.Emit을 호출해 Harmony의 생성을 우회하지 않는다. [S16]

text
Transpile(original, incomingInstructions, generator):       // 설계 의사코드
  body = registry.GetImmutablePreparedBody(original)
  if body is absent:
      return incomingInstructions

  validate original belongs to current RuntimeBaseline
  allocate fresh Label for each target and end sentinel
  allocate fresh LocalBuilder for each normalized local

  for every normalized instruction:
      resolve opcode and typed operand
      map ldloc/stloc/ldloca variants to the new LocalBuilder
      map branch/switch target IDs to the fresh Labels
      attach labels and exact exception-block boundaries
      append a fresh CodeInstruction

  validate all labels, local uses, EH edges, return paths
  return materializedInstructionList

동일 IR은 재사용할 수 있지만 Label, LocalBuilder, CodeInstruction 인스턴스는 generator별로 다시 생성한다. Harmony가 재적용 중 transpiler를 다시 호출할 수 있으므로 mutable 이전 결과를 캐시하지 않는다. transpiler는 파일 I/O·Worker 호출·소스 분석을 하지 않고 준비된 불변 데이터만 읽는다. [S15]

7.4 예외 처리·검증기의 최소 요건

일반 catch/finally와 중첩 EH를 다루는 전용 변환기를 구현한다. leave, endfinally, try/handler 끝 경계를 단순 분기와 구별하고, 경계에서 필요한 block 종료 순서를 보존한다. using/foreach가 생성한 finally도 동일한 테스트를 통과해야 한다. emit 시 자동으로 생기는 구조와 원본 endfinally를 이중 삽입하지 않도록 실제 라이브러리 코드를 확인한다.

v1 검증기는 허용 opcode 집합에 대해 스택 높이·분기 합류·유효한 return·지역 변수/멤버 타입을 확인해야 한다. 이는 모든 CLI 코드에 대한 완전한 verifier를 만들라는 뜻이 아니다. 지원된 하위 집합만 허용하고, 분석할 수 없는 조합을 차단한다. JIT 성공만으로 전체 게임 코드가 안전하다고 판정하지 않는다.

7.5 기존 호출자의 관찰 가능성

NoInlining이 있는 실제 대상에서 직접 호출, 기존에 캐시한 delegate, Unity Update 콜백, private helper, base/virtual/interface 호출을 fixture로 검사한다. 특정 경로가 갱신되지 않으면 성공으로 표시하지 말고 해당 호출 경로를 지원 경계에서 제외하거나 백엔드를 수정한다. 소스 행 단위 breakpoint가 새 본문으로 이동한다는 보장은 v1에 포함하지 않는다.

9.1 두 단계로 적용한다

Prepare · 게임 코드 실행 금지

전체 타입/멤버 해석, local/EH/스택 검증, owner 충돌 검사, 원본/이전 IR 확보, generation 계획과 journal을 준비한다. 임의의 게임 메서드를 호출하여 “동작 확인”하지 않는다.

컴파일·import·종료 중이 아닌지 확인하고 패치를 적용한다. 전체 성공 후에만 active map과 generation을 갱신한다. 중간 실패는 앞서 적용된 대상까지 역순 복구한다.

보장하는 것은 메인 스레드 전용 대상의 프레임 사이에서 수행하는 응용 수준의 배치 일관성이다. 운영체제 수준의 원자성이나 모든 실행 스레드를 멈추는 전역 safepoint를 구현했다고 주장하지 않는다. 대상 코드가 백그라운드에서도 호출될 수 있다면 v1 대상에서 제외한다. paused Play Mode도 다른 스레드 정지를 보장하지 않는다.

text
Apply(plan):                                           // 설계 의사코드
  RejectIfStaleOrUnsafe(plan)
  oldGeneration = activeGeneration
  prepared = PrepareAll(plan)                          // 원본 상태 유지
  journal.Write("Prepared", plan, oldGeneration)

  try:
      for operation in DeterministicOrder(prepared):
          ApplyOwnTranspilerExactlyOnce(operation)
          verify backend ownership and registration count
      activeGeneration = prepared.DesiredGeneration    // 마지막에 승격
      journal.Write("Committed", activeGeneration)
      return Applied
  catch applyError:
      try:
          RestoreAllTouchedMethodsInReverse(oldGeneration)
          activeGeneration = oldGeneration
          journal.Write("RolledBackAfterFailure", applyError)
          return FailedButRestored
      catch restoreError:
          EnterQuarantinedState(applyError, restoreError)
          return FailedAndQuarantined

9.2 Harmony owner와 재적용

세션별 owner id와 단일 transpiler 메서드를 사용한다. 같은 대상에 같은 hook이 중복 누적되지 않는지 검사한다. 교체 시 기존 자신의 transpiler만 제거·재설치하고, 실패하면 이전의 불변 IR로 다시 설치한다. “모든 패치 제거” API를 전체 프로젝트에 실행하지 않는다. 외부 owner가 같은 대상에 개입한 경우 v1은 합성하지 않고 거부한다. [S18]

9.3 롤백은 코드에만 적용된다

Rollback Last Batch는 직전 Eg의 본문 맵으로 돌아간다. Revert All Overrides는 A0의 본문으로 돌아간다. 두 동작 모두 디스크 소스, HP, 이동 위치, 생성된 오브젝트, 저장 파일, 발생한 이벤트를 되돌리지 않는다. 패치된 게임 코드가 이미 변경한 월드 상태까지 복구한다고 설명하지 않는다.

롤백 후 디스크에는 새 코드가 남을 수 있다. UI는 SourceDiverged를 표시하며 동일 revision의 자동 재적용을 잠근다. 사용자가 새 저장을 하거나 명시적으로 Reapply Current Source를 요청할 때만 다시 적용한다. 게임 코드 예외가 났다는 이유만으로 자동 원복 후 원본 코드를 다시 실행하면 부작용이 두 번 발생할 수 있으므로 금지한다.

9.4 복구 실패

부분 패치의 원상복구를 증명하지 못하면 Quarantined다. 추가 패치를 금지하고 편집기 Play Mode를 가능한 범위에서 일시정지해 위험을 알린다. 진단을 저장하고, 명시적 정상 컴파일 또는 Editor 재시작이 필요하다고 표시한다. 소스 파일은 보존한다. “오류를 무시하고 계속” 버튼은 제공하지 않는다.

9.5 journal의 한계

journal은 진단/복구 계획의 기록이지 JIT 포인터를 복원할 수 있는 영속 상태가 아니다. Editor 재시작 후 이전 네이티브/managed patch handle을 재사용하지 않는다. 새로운 sessionId와 baseline을 만들고 소스로부터 다시 시작한다.

10.1 RefreshLease

소유권을 가진 객체 하나가 DisallowAutoRefresh를 한 번 획득하고, 같은 Editor 세션에서 정확히 한 번 해제한다. API는 on/off 스위치가 아닌 카운터이며 수동 Refresh를 막지 못한다. Unity Preferences의 전역 Auto Refresh 값을 덮어쓰는 방식은 기본 설계에서 사용하지 않는다. [S11] [S12]

text
Acquire():
  assert on Editor main thread
  if this lease is already held: return
  AssetDatabase.DisallowAutoRefresh()
  heldByThisInstance = true

Dispose():
  assert on Editor main thread
  if not heldByThisInstance: return
  heldByThisInstance = false
  AssetDatabase.AllowAutoRefresh()

복구 버튼에서 AllowAutoRefresh를 반복 호출해 카운터를 0으로 “맞추지” 않는다. 다른 도구의 lease를 침범할 수 있다. 프로세스가 바뀐 뒤 남은 journal만 보고 이전 lease가 아직 살아 있다고 추측하지 않는다. domain reload를 가로지르는 카운터 동작은 실제 버전에서 시험하고, 소유권을 추적할 수 없는 경우 blind decrement 대신 안전 중지와 Editor 재시작 안내를 사용한다.

10.3 Domain Reload 비활성화도 시험한다

Enter Play Mode 설정으로 static 상태·이벤트 구독이 유지될 수 있다. Bootstrap을 여러 번 실행해도 update/compilation/playMode 이벤트에 중복 등록하지 않아야 한다. 일반 게임플레이 static 상태를 도구가 임의로 초기화하지 않는다. 도구 자신의 session registry·watcher·bridge만 명시적으로 수명 관리한다. [S14]

10.4 “Refresh 잠금”의 사용자 경험

감시 중에는 텍스처·프리팹·shader 등 다른 에셋의 import도 지연될 수 있다. 상단에 Auto Refresh held by this session 배지를 상시 표시한다. v1은 “C#만 막고 다른 자산은 항상 자동 import”를 보장하지 않는다. 수동 Ctrl/Cmd+R 또는 타 도구의 명시적 Refresh를 감지하면 세션을 안전하게 무효화한다. 파일 감시에는 Unity의 자동 import가 완료되어야만 호출되는 콜백을 유일한 수단으로 쓰지 않는다.

11.1 Watcher의 책임

파일 이벤트는 “변경했을 수 있음”의 신호다. FileSystemWatcher는 중복 이벤트나 오류를 낼 수 있으므로 실제 content hash로 중복을 제거하고, 오류·버퍼 overflow 시 해당 root를 다시 스캔한다. [S22]

항목설계 기본값 / 처리
감시 대상프로젝트 소유 .cs와 컴파일 컨텍스트 파일. Library/Temp/obj/bin/.git/PackageCache/도구 자체 산출물은 제외. 경로 규칙은 G0에서 실제 프로젝트 기준 확정.
Debounce기본 300ms. 연속 저장은 하나의 revision으로 합침. 임계값은 설정 가능하며 정확성은 해시 검증이 담당.
완전한 파일 쓰기연속 두 번의 읽기에서 해시가 안정적인지 확인하고 짧은 공유 위반 재시도. 단순 시간 지연만으로 완성 저장을 확정하지 않음.
폴링OS watcher 불가 시 폴링으로 전환. idle 프레임마다 전 파일 해시를 계산하지 않음. 기본 주기 1초, 주기적 전체 정합성 점검은 별도.
경로 정규화절대 경로 정규화 후 프로젝트 허용 root 안인지 검사. OS별 대소문자 규칙 적용. symlink/reparse point 우회에 대한 정책을 명시.
rename/delete/create안정된 스냅샷에서 최종 상태를 판정. 영구 파일 추가/삭제는 v1 컨텍스트 변경으로 정상 컴파일 요구.
한글/공백 경로UTF-8 프로토콜과 ProcessStartInfo 인자 배열을 사용. shell 문자열 결합 및 따옴표 추정 금지.
동시 변경Worker는 1개, 최신 revision 우선. 동시에 여러 patch commit 금지. 취소와 늦은 결과 폐기를 모두 구현.

11.2 에이전트가 여러 파일을 수정할 때의 배치 장벽

Debounce는 논리적 트랜잭션이 아니다. Claude/Codex가 A를 수정한 뒤 몇 초 후 B를 저장하면 A만 먼저 적용될 수 있다. 에이전트 작업은 begin_edit_batch → 파일 수정 → end_edit_batch → dry-run/apply를 사용한다. 장벽 안에서는 변화만 수집하고 자동 적용하지 않는다. 에이전트가 중단되면 timeout을 이유로 미완성 배치를 적용하지 말고 Paused로 남겨 명시적 종료/취소를 받는다.

11.3 Worker 실행 계약

Editor가 UseShellExecute=false로 로컬 Worker를 시작한다. stdin/stdout은 길이 프레임 또는 명확한 NDJSON 프로토콜 중 하나로 고정하고, 로그는 stderr로 분리한다. protocolVersion/프로세스 세션 token/컴파일 context hash를 handshake한다. 프로토콜에 임의 shell command 또는 C# eval을 넣지 않는다.

Worker는 소스 읽기·Roslyn·Cecil·계획 생성만 수행한다. 게임 어셈블리의 user code·static constructor를 실행하지 않는다. source generator/analyzer를 임의 실행하는 것도 코드 실행이므로, v1 기본값은 신뢰·재현성이 확인되지 않은 generator를 거부하는 것이다. Worker 프로세스 분리는 의존성/장애 격리이지 악성 소스에 대한 완전한 보안 sandbox가 아니다.

11.4 중단·재시작

취소는 요청별 token으로 전달한다. timeout이면 해당 request를 폐기하고 필요 시 자신이 시작한 Worker만 종료한다. 전체 dotnet/Unity 프로세스를 kill하지 않는다. 재시작 후 context를 다시 전송하고 세션·revision 일치를 확인한다. 이전 Worker 응답은 새 세션에서 적용하지 않는다. 디스크 snapshot은 atomic rename으로 확정한다.

[작업 목표]

[먼저 읽을 것]

2. 전달한 Unity_HotReload_Design_and_Agent_Handoff.html 또는 DESIGN_SPEC.md 전체.
3. 이미 존재하면 Docs/HotReload/progress.json, Inventory.md, adr/, evidence/.

[실행 방식]
