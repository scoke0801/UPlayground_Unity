# 지형·물 아트 작업 교훈 (RiverBasinWorld B1 R3)

RiverBasinWorld B1 구간 비주얼 개선(R3, 2026-11-09)에서 사용자 지적으로 다시 고친 항목을 정리한다. 같은 실수를 반복하지 않도록 **증상 → 원인 → 올바른 방법 → 검수 방법** 순으로 적는다.
상위 지침은 `OPENWORLD_MAP_AUTHORING_GUIDE.md`이고, 이 문서는 그 지침의 실무 함정을 다룬다. 작업 스크립트는 `Tools/RiverBasinWorld/VisualR3/`, 백업과 캡처는 `output/RiverBasinWorld/VisualR3/`에 있다.

---

## 0. 공통 원칙 (모든 항목에 적용)

1. **"사람이 만든 티"의 대부분은 경계에서 난다.** 원형·직선·일정 폭·일정 간격·격자는 거의 항상 지적된다. 마스크·배치·형상을 만들 때 경계가 **자연물의 원인**(물길, 수관, 경사, 마모)을 따르는지 먼저 묻는다.
2. **고정 카메라 원경 캡처만으로 "완료"라고 하지 않는다.** 이번 지적의 대부분은 **위에서 내려다본 시점, 근접 시점, Scene 뷰 자유 시점**에서 나왔다. 검수 구도에 반드시 넣을 것: 위에서 내려다보기(45~90°), 대상 1~3m 근접, 사용자가 실제로 가는 위치.
3. **원인을 모르는 상태에서 덮지 않는다.** 거품 띠, 페이드, 노이즈로 경계를 가리는 방식은 이번에 네 번 실패했다. 먼저 **왜 선이 생기는지**(셰이더·메시·데이터)를 확정한다.
4. **같은 문제를 세 번째 고치게 되면 접근을 바꾼다.** 수치 조정을 반복하지 말고 구조(셰이더 통합, 메시 재설계)를 바꾸거나 사용자에게 방향을 묻는다.
5. **파괴적 편집 전 백업, 실행 취소는 믿지 않는다.** `Undo.RegisterCompleteObjectUndo`가 같은 그룹으로 묶여 의도와 다른 단계가 되돌려진 적이 있다. 지형·메시는 단계마다 파일 백업(`backup-r3b/pre-*.asset`)을 남기고, 되돌릴 때는 백업에서 복원한다.

## A. 자연스러운 지면·지형·꾸밈요소 일반 규칙

아래 규칙은 새 구간을 만들 때 먼저 적용한다. 수치는 B1 구간(TPS 카메라, 피치 14°/FOV 55°, 보행 기준)에서 쓴 **출발값**이다. 다른 구간에서는 같은 구도의 캡처로 다시 조정한다. 1~4장의 사례는 이 규칙을 어겼을 때 실제로 생긴 실패다.

### A.0 인위적으로 보이는 패턴 (금지 목록)

| 패턴 | 어디서 생기나 | 대신 |
|---|---|---|
| 완전한 원·타원 경계 | 공터·패드 마스크 | 저주파 노이즈로 일그러진 넓은 전이 (1.1) |
| 직선 경계, 일정 폭 띠 | 길 가장자리, 강, 수면 끝 | 사행·폭 노이즈·비대칭 (3.3) |
| 등간격·격자 배치 | 풀, 바위, 나무 | 셀별 해시 확률 + 군락 노이즈 (2.3) |
| 같은 크기·같은 회전 반복 | 소품 산포 | 크기 위계 + 회전·축별 스케일 편차 (A.4) |
| 칼같이 끊기는 전이 | 텍스처 레이어 경계, 셰이더 경계 | 전이 폭 확보, 셰이더 통일 (A.1, 4.1) |
| 계단·평탄면 + 수직벽 | 수면, 깎은 길 | 연속 프로필, 필렛 (3.1, 1.2) |
| 매끈한 계산 곡면 | 파낸 지형 | 2단 요철(큰 형태 + 잔 요철) (1.3) |
| 공중에 뜬 물체, 덜 묻힌 밑면 | 바위·통나무·풀 | 지형 높이 기준으로 묻기 (A.4) |
| 이유 없는 색 튐 | 원본 패키지 색(연두 풀, 원색 시안 물) | 장면 팔레트에 맞춘 전용 복사본 (2.3, 4.2) |
| 근경 단일 텍스처 대면적 | 흙·초원 넓은 면 | 2~3 레이어 + 저주파 변주 (A.1) |

**판정 질문:** 이 경계나 배치에 **자연적인 원인**(물, 경사, 그늘, 마모, 바람)이 있는가? 대답이 "계산식이라서"라면 고친다.

### A.1 지면 텍스처 규칙

- **레이어는 원인으로 결정한다.** 경사 → 바위, 물가(수면 위 0~1.2m) → 젖은 자갈, 수면 아래 → 하상 자갈, 나무 아래(수관 4~12m) → 낙엽토, 볕 드는 평지 → 초원, 길 중심 → 다져진 흙. 노이즈만으로 레이어를 정하지 않는다.
- **전이 폭은 최소 셀 4개다.** 지형 텍스처 셀이 2m면 8m 이상이다. 그보다 좁으면 계단이 보인다.
- **경계 왜곡 노이즈의 파장은 셀 크기의 8배 이상이다.** 2m 셀이면 15~40m. 고주파 "패치 분해"는 얼룩이 된다(1.1).
- **타일 반복 감추기:** 근경 단일 레이어 면적이 화면 하단의 30%를 넘으면, 같은 계열 레이어 2개를 저주파 노이즈(파장 30~100m)로 섞거나 오버레이 셰이더에서 두 스케일로 샘플한다.
- **명도 대역:** 캐릭터·적이 서는 전투 면은 중간 명도로 둔다. 순백 흙이나 과노출 오버레이(틴트가 1을 넘는 값)는 금지한다.
- **길:** 중심은 Footpath, 가장자리 1~2m는 풀·낙엽이 섞인 전이로 둔다. 길 마스크는 경로 데이터(`production-plan.json`)를 단일 소스로 쓴다.

### A.2 지형(높이) 규칙

- **두 단계 형태:** 큰 형태(파장 20m 이상, 진폭 수 m)와 잔 요철(파장 2~6m, 진폭 0.3~1m)을 함께 둔다. 계산으로 만든 곡면은 반드시 잔 요철을 덧입힌다.
- **깎은 면에는 필렛:** 길이나 공터를 평탄화할 때 회랑 밖 4~7m를 완만하게 이어 붙인다. 1m 격자 2차 차분 0.35m를 넘는 꺾임은 남기지 않는다(1.2).
- **사면 경사:** 걸어 다니는 사면은 30° 이하로 둔다. 30~45°는 바위 레이어나 암반 소품으로 "못 오르는 곳"임을 보여 준다. 45°를 넘는 곳은 암반 메시로 덮는다.
- **물가:** 강둑은 수면 위 0.3m부터 시작해 경사 0.4~0.7 사이로 올린다. 수면 아래는 가장자리에서 중앙으로 깊어지는 단면(지수 0.8 근처)으로 판다.
- **보호 구역:** 경로, 다리 지지면, 전투 공터, 충돌체 주변은 높이 편집 마스크에서 제외하고 페이드로 경계를 잇는다.
- **편집 후 필수:** 위에 놓인 오브젝트 재안착, NavMesh 재생성, 경로 구간 검사(5장 체크리스트).

### A.3 잔디·초화 규칙

- **수단:** 수백 개를 넘으면 Terrain 디테일(인스턴싱, `InstanceCountMode`)을 쓴다. 개별 GameObject는 상징적인 덤불이나 꽃 군락에만 쓴다.
- **배치 단위:** 0.5m 셀에 칸당 0~1포기를 확률로 둔다. 칸당 고정 개수는 줄무늬를 만든다.
- **군락:** 저주파 노이즈(파장 10~15m)로 빽빽한 곳과 빈터를 만든다. 밀도 하한은 최대치의 45% 정도로 두어 초원이 듬성해 보이지 않게 한다.
- **경계:** 초원 텍스처 경계를 그대로 쓰지 않는다. 노이즈 디더(±0.2)로 흩뜨리고 가장자리에서 서서히 성기게 한다.
- **종 혼합:** 낮은 풀(주력, 약 60%), 중간 풀(군락 안 일부, 약 35%), 큰 포기(약 3~5%)를 섞는다.
- **색:** 장면 계절 팔레트에 맞춘다. 가을이면 마른 황록과 올리브로 두고, 싱싱한/마른 색 편차(healthy/dry)를 쓴다.
- **비우는 곳:** 길 중심, 공터 중앙, 물속, 물가 0.4~0.5m, 바위 텍스처 위, 큰 바위 밑.
- **거리와 성능:** 표시 거리 출발값은 90m다. 바꾼 뒤에는 프레임 비용을 측정해 기록한다.

### A.4 꾸밈요소(바위·나무·소품) 규칙

- **군락으로 둔다:** 하나씩 흩뿌리지 않는다. 중심 하나와 주변 위성으로 묶고, 군락 사이에는 비어 있는 공간을 남긴다.
- **크기 위계:** 군락마다 큰 것 1, 중간 것 2~3, 작은 것 여럿. 같은 크기만 반복하지 않는다.
- **편차:** 회전은 Y축 0~360°, 기울기 ±8~12°. 스케일은 축별로 0.85~1.3 편차를 준다(납작하고 긴 바위가 자연스럽다).
- **묻기:** 바위는 높이의 25~50%, 소품은 밑면 0.1~0.2m를 지형 높이 기준으로 묻는다. 경사면에서는 낮은 쪽 밑면이 뜨지 않는지 확인한다.
- **지형 논리를 따른다:**
  - 강가 바위·자갈은 물길 방향으로 길게 놓고, 물이 부딪히는 쪽에 모은다.
  - 쓰러진 나무와 낙엽 퇴적은 경사 아래쪽과 물가에 모은다.
  - 폭포·낙구 양 끝은 큰 바위로 덮어 물의 사각 윤곽을 지운다.
- **일렬·등간격 금지:** 길을 따라 등간격으로 서는 나무나 바위는 정원처럼 보인다. 길에서의 거리를 섞고 군락으로 끊는다.
- **동선 보호:** 길 중심, 전투 공터, 카메라가 지나가는 면은 비운다. 비워 둔 공간에 소품을 채우지 않는다.
- **원본 보호:** 색이나 크기를 바꾸려면 전용 복사본을 쓴다. 원본 패키지 프리팹과 재질은 수정하지 않는다.

### A.5 검수 구도 (모든 항목 공통)

1. 플레이어 높이의 진행 방향과 역방향.
2. 위에서 내려다보기(45~90°): 원·직선·격자·계단이 가장 잘 보이는 시점이다.
3. 대상 1~3m 근접: 묻힘, 이음새, 셰이더 경계를 확인한다.
4. 원경(50m 이상): 타일 반복과 명도 대비를 확인한다.
5. 야간이나 역광 1장.

## 1. 지면 (사례)

### 1.1 원형 공터 / 흙 원판

- **증상:** 전투 공터가 노란 원판·선명한 원으로 보였다. 노이즈를 넣은 뒤에는 "얼룩덜룩하게 끊긴" 다각형 얼룩이 됐다.
- **원인:**
  - 계획 데이터의 공터가 **타원 마스크**였고, 흙 텍스처와 흙 오버레이 메시가 반지름 12~18m 사이 약 6m 안에서 함께 사라졌다.
  - 이후 넣은 노이즈 패치는 지형 텍스처 해상도(2m)와 오버레이 메시 정점 간격(1m)에서 계단식 얼룩이 됐다.
- **올바른 방법:**
  - 전이 폭은 반지름의 **25~110%**처럼 넓게 잡고, 경계 왜곡은 **저주파 노이즈(파장 15~40m)**만 쓴다. 고주파 "패치 분해"는 해상도가 낮은 지형 텍스처에서 쓰지 않는다.
  - 오버레이 메시가 경계를 만들면 오버레이를 끄고 지형 텍스처만으로 해결한다.
  - 길 회랑(중심 3~6m)은 마스크에서 보호한다.
- **검수:** 위에서 내려다보는 구도에서 원·다각형·계단이 보이지 않는가.

### 1.2 날카로운 언덕 경계

- **증상:** 길 옆 언덕 경계가 칼로 자른 듯했다.
- **원인:** 길을 평평하게 깎으면서 사면 곡률이 급하게 바뀌었다.
- **올바른 방법:**
  - 1m 월드 격자에서 높이 2차 차분이 0.35m를 넘는 곳만 찾아, 그 주변 4m에 확산 완화를 건다.
  - 길·강·다리·공터는 보호한다.
  - 지형 조각이 여러 장이면 **월드 좌표 격자**로 계산해야 이음새가 같은 값을 받는다.
  - 높이를 바꾼 뒤에는 그 위의 나무·바위·풀을 새 높이로 옮긴다.
- **검수:** 길 옆 사면을 낮은 시점에서 본다. 경로가 끊기지 않는지 NavMesh도 확인한다.

### 1.3 강가 지형이 매끈함

- **증상:** 파낸 강둑이 계산식 그대로의 매끈한 곡면이었고, 바위 텍스처 한 가지가 고르게 덮었다.
- **올바른 방법:**
  - 물 위로 드러난 강둑에만 높이 요철(능선형 노이즈 + 큰 덩어리, 0.5~1m)을 넣는다.
  - 텍스처는 수면선의 젖은 자갈 띠, 그리고 바위·흙·낙엽이 섞인 얼룩으로 칠한다.
  - 작은 바위를 흩는다. 바위는 반드시 **지형 높이 기준으로 묻어서** 놓는다(공중에 뜬 선반 금지).

## 2. 풀·잔디

### 2.1 듬성듬성함

- **원인:** 다른 문제를 고치면서 개별 오브젝트 풀을 일괄로 꺼서 초원까지 성겨졌다.
- **올바른 방법:** 대량의 풀은 **Terrain 디테일(GPU 인스턴싱)**로 깐다. 개별 GameObject 수천 개는 쓰지 않는다.

### 2.2 디테일이 거의 안 보임

- **원인:** Terrain 디테일 기본값은 **CoverageMode**라 레이어 값을 0~255 비율로 해석한다. 셀당 개수(1~4)를 넣으면 거의 그려지지 않는다.
- **올바른 방법:** 셀당 개수를 쓸 때는 `SetDetailScatterMode(DetailScatterMode.InstanceCountMode)`를 먼저 호출한다.

### 2.3 인위적 배치 (줄무늬·칼 경계·단색)

- **원인:** 1m 격자에 칸당 3포기, 한 종류, 한 색, 초원 텍스처 경계를 그대로 따랐다.
- **올바른 방법:**
  - 0.5m 셀에 칸당 0~1포기를 셀별 해시 확률로 둔다(격자 줄무늬 제거).
  - 노이즈 두 겹으로 군락과 빈터를 만든다. 경계는 노이즈로 흩뜨려 서서히 성기게 끝낸다.
  - 풀 2~3종을 섞는다. 낮은 풀 위주에 가끔 큰 포기를 둔다.
  - **색은 장면 계절에 맞춘다.** 원본 연두색은 가을 단풍 장면에서 따로 논다. 원본 프리팹·재질은 건드리지 않고 전용 복사본(`03.Prefabs/.../VisualR3/PF_B1_*`)을 만든다.
  - 물속·물가 0.4~0.5m 띠는 비운다.

## 3. 강·수면

### 3.1 계단식 수면

- **증상:** 폭포가 층층이 계단처럼 보였다.
- **원인:** 강바닥은 일정 경사인데, 수면만 24m마다 평탄한 판과 수직 벽으로 깔았다.
- **올바른 방법:** 수면 프로필(급류 → 낙차 → 소)을 먼저 설계하고, 강바닥을 그 프로필 **아래로만** 판다. 수면 메시는 실제 강둑과 만나는 지점까지 단면마다 폭을 계산한다.

### 3.2 강이 끊김 (내 버그)

- **원인:** "강둑 아래 묻힌 삼각형" 기준으로 수면 삼각형을 지웠다. 그런데 이 메시는 한 줄에 정점이 양쪽 강둑 끝에만 있어서, **강폭 전체의 띠가 통째로 삭제**됐다.
- **교훈:** 메시를 꼭짓점 조건으로 자르기 전에 메시 구조(한 줄에 정점이 몇 개인지)를 먼저 확인한다. 자르기는 좌표 범위처럼 명확한 기준만 쓴다. 자른 뒤에는 위에서 내려다보는 캡처로 확인한다.

### 3.3 강폭·깊이가 일정함

- **올바른 방법:**
  - 중심선은 사행시키고(진폭 4~5m), 좌우 폭에 비대칭 노이즈를 준다.
  - **소(넓고 깊음, 4m 이상)와 여울(좁고 얕음, 1.5~2m)**을 번갈아 둔다.
  - 다리 교각 바닥처럼 고정 제약이 있는 곳은 얕은 여울로 남긴다.

### 3.4 수영이 안 됨

- **원인:** 맵에 수영 판정용 수면(`FootstepWaterSurface`)이 하나도 등록돼 있지 않았다. 수영 진입 판정은 등록된 수면의 높이만 본다.
- **올바른 방법:**
  - 새 물 메시에는 반드시 `FootstepWaterSurface`를 붙인다(`profile`은 Surface_ShallowWater).
  - 수영 진입 기준은 수심 1.2m(`SwimEnterDepth`)다. 수영시킬 구간은 1.8m 이상으로 판다.
  - 메시를 바꾸면 `RefreshMesh()`를 호출한다.

## 4. 폭포 (가장 많이 다시 고친 항목)

### 4.1 셰이더가 다르면 경계가 생긴다

- **증상:** 낙구에 선명한 선, 밝은 띠, 색 차이가 반복해서 지적됐다.
- **원인:** 강 수면(`LakeWater`)은 물 밑 지형까지의 **깊이로 색을 정하고 뒤 장면을 굴절해 합성**한다. Polyart 폭포 셰이더는 깊이 개념 없이 자기 색과 투명도로 덧칠한다. 서로 다른 셰이더가 만나는 곳은 색을 맞춰도 시점에 따라 다르게 보인다. 강 수면의 굴절 합성은 반투명한 폭포 윗부분을 지우기도 했다.
- **효과 없던 방법 (반복 금지):**
  - 낙구 거품 띠로 덮기
  - 강 수면 끝을 투명하게 하기(`_ShoreFade` UV)
  - 낙구 바닥을 바위 턱으로 올리기 → 얕은 물이 녹색 띠로 비침
  - 낙구 앞을 깊게 파기 → 투명한 수면 아래로 구덩이가 보임
  - 강 수면 셰이더를 폭포면에도 쓰기 → 뒤 풍경이 비침
- **올바른 방법 (후속 개선 반영):** 낙구 앞 수면부터 낙하면까지 전용 `VisualR3/RiverFall.shader`로 이어 그린다. 상류 연결부에서는 강 수면의 **굴절·반사·투명도를 포함한 최종 합성 결과**를 재현하고, 낙구 전에는 같은 음영의 불투명한 물로 서서히 전환한다. 곡면을 넘으며 기존 낙수 음영으로 이어지게 한다. 재질 색만 보간하거나 셰이더 이름을 같게 만드는 것으로는 충분하지 않다.
- **적용 범위:** 기존 강 수면과 폭포는 별도 메시로 유지했다. 폭포 메시가 상류 수면을 따라 겹쳐 시작하고 같은 합성 결과로 연결되므로, 반드시 강 전체를 한 메시로 합칠 필요는 없다. 공용 `LakeWater.shader`는 수정하지 않았다.
- **검수 결과:** 두 폭포의 고정 구도 5개에서 낙구 경계선과 물밑 턱이 드러나던 띠가 개선됐다. 실제 Play Mode 이동·수영·시간대 변화는 미검증이다. 구체적인 절차와 근거는 4.6을 따른다.

### 4.2 폭포 색이 강과 다름

- **원인:** 강 수면은 하늘 반사 때문에 짙은 청회색으로 보이는데, 폭포 재질은 원색 청록이었다. 물보라 입자도 원색 시안이었다.
- **올바른 방법:** 폭포·물보라 색은 **렌더된 강 수면의 실제 색**(캡처에서 확인)에 맞춘다. 재질의 설정값끼리 맞추는 것으로는 부족하다. 외부 패키지 재질은 전용 복사본을 만들어 수정한다.

### 4.3 메시 법선과 양면

- **함정 1:** 같은 정점에 앞면·뒷면 삼각형을 두고 `RecalculateNormals`를 부르면 법선이 상쇄되어 조명이 얼룩진다. **앞면만으로 법선을 계산한 뒤** 뒷면 삼각형을 추가한다.
- **함정 2:** 수평 앞치마(낙구 위 구간)는 하늘을 거울처럼 반사해 크롬 얼룩이 생겼다. 셰이더에서 낙구 구간의 법선을 위쪽(0,1,0)에서 낙하면 법선으로 천천히 넘어가게 한다.
- **함정 3:** 재질 값이 같아도 메시의 **삼각형 감김 방향과 앞뒷면 분기**가 다르면 색이 달라진다. 이번 강 메시의 법선은 아래를 향해 위에서 보아도 `LakeWater`의 뒷면 색·투명도를 사용하고 있었다. 연결부에서 윗면 표현만 재현하자 새로운 녹색 경계가 생겼다. 원본 메시의 방향까지 읽어 같은 표현으로 시작하도록 동기화했다. 강 전체의 방향 수정은 상류 색과 수중 시야까지 바뀌므로 별도 작업으로 남겼다.

### 4.4 Polyart 폭포 셰이더 규약

- u의 양 끝을 투명 처리하므로 **u는 반드시 0~1**이어야 한다. 반복 UV를 쓰면 이음새가 생긴다.
- v=0이 낙구, v=1이 바닥이다. 시작 부분이 투명하게 시작한다(`_InitialOpacityGradience`).
- 이 값을 크게 올리면 줄무늬가 크롬처럼 깨진다.

### 4.5 거품

- **증상:** 거품이 빗살처럼 규칙적이고, 바닥에 하얀 테가 생겼다.
- **올바른 방법:**
  - 단단한 문턱(smoothstep 폭 0.18) 대신 넓은 폭(0.35 이상)으로 번지게 한다.
  - 큰 덩어리 노이즈로 군데군데 끊고, 아래로 갈수록 거듭제곱으로 늘린다.
  - 바닥은 투명도를 흐려 물보라 입자 속으로 녹아들게 한다.
  - u 방향 노이즈 타일링은 3 전후로 둔다. 7 이상이면 빗살이 된다.

### 4.6 낙구 연결 개선의 재현 절차와 검증 범위

- **추가로 확인한 원인:** 폭포 시작부는 일정 높이였지만, 그 아래 강 수면은 경사져 있었다. 같은 평면처럼 보이는 부분에도 높이 차이가 있었으므로 셰이더 수정만으로 해결하면 안 됐다.
- **적용 절차:**
  1. 강 메시의 실제 정점에서 단면별 높이·폭·낙구 굴곡을 읽어 폭포의 상류 연결부를 만든다. 이번에는 낙구 앞 약 **5.5m**부터 연결했고, 겹침부를 수면보다 **8mm** 높였다. 이 값은 해당 메시의 적용값이며 다른 맵의 고정 규격이 아니다.
  2. 연결 시작점에서는 강 수면의 최종 합성 결과를 재현한다. 정점 색 R을 전환 마스크로 사용해 낙구 **3.5m 전까지** 물밑이 보이지 않는 수면으로 바꾼다. 이때 불투명 수면의 음영·반사도 강과 맞춰야 새 색 띠가 생기지 않는다.
  3. 곡면에서 수면 파동 법선과 낙수 법선을 서서히 섞고, 재질의 `_FallBlendRange`로 낙수 음영 전환 범위를 조정한다. 기존 하부 메시·거품 UV·물보라는 보존한다.
  4. 수영 판정용 `FootstepWaterSurface`의 메시와 지형·충돌체는 유지한다. 시각 연결을 고치기 위해 물 밑을 다시 파거나 수영 판정을 낙수면으로 바꾸지 않는다.
- **재질 동기화:** 전용 재질의 `River` 계열 값은 현재 강 재질에서 복사한다. 강 재질을 바꾼 뒤에는 `Tools/RiverBasinWorld/VisualR3/connect-waterfall-lip.csx`를 다시 실행해 동기화한다. 스크립트는 기존 하부를 UV로 찾아 보존한다.
- **수행한 검사:** Unity 6000.3.21f1 Editor에서 셰이더 import·카메라 렌더, ShaderUtil 진단 0·콘솔 오류 0을 확인했다. 폭포별 925정점·1,728삼각형의 채널 길이, 인덱스, 전환 마스크 끝점, 중복 삼각형 검사를 통과했다. 위·낙구 근접·정면·측면·두 번째 폭포의 고정 캡처 5개를 AI가 확인했다.
- **남은 검사:** 실제 Editor Play Mode의 카메라 이동·수영 진입/이탈, 낮·밤·날씨·수중 시점, GPU 성능은 사용자 테스트 대기다. 고정 캡처에서 경계가 개선된 것을 전체 플레이 품질 검증 완료로 기록하지 않는다.
- **근거와 복구:** [전후 캡처·검사 결과·사용자 테스트 명세](../../../output/RiverBasinWorld/VisualR3/lip-continuity/RESULT.html), 촬영 스크립트 `Tools/RiverBasinWorld/VisualR3/capture-lip-continuity.csx`, 작업 전 사본 `output/RiverBasinWorld/VisualR3/lip-continuity/backup/`. 해당 환경 에셋은 기존 git ignore 대상이므로 저장소 diff만으로 변경·복구 가능 여부를 판단하지 않는다.

### 4.7 헤엄쳐 닿으면 막히는 낙구

- **증상:** 수면 위에서는 폭포가 이어져 보이지만 헤엄쳐 접근하면 수중의 높은 강바닥 턱에 몸이 막혔다. 수영에는 낙구를 넘을 때 부력을 해제하는 처리도 없었다.
- **올바른 방법:** 시각 수면, 물리 통과 공간, 수영 상태 전환을 따로 확인한다. 이번에는 두 낙구 앞 강바닥의 중앙 통로를 낮추고 작은 배치물 6개를 재안착했으며, 통로를 막던 큰 바위 1개는 강둑으로 옮겼다. 이는 **플레이어의 통과 공간 확보**이며, 색 경계를 가리려고 지형을 파는 4.1의 실패 사례와 목적이 다르다.
- **물살과 낙하:** `WaterfallCurrent`의 로컬 +Z를 하류로 배치한다. 접근 구간에서는 수영 속도에 물살을 더하고, 낙구 경계를 넘으면 `Swim → Airborne`으로 바꿔 기존 낙하 모션과 중력을 사용한다. 낙하 영역 안에서는 상류 수면의 수영 재진입을 막고, 하류 입수 높이에서는 이 제한을 해제한다. 영역·속도·경계·해제 높이는 인스턴스에서 조정한다.
- **검수:** 수면 위 캡처만 보지 말고 수중에서 낙구를 바라본다. 접근→낙하→하류 재입수까지 캐릭터 몸통의 통과 공간을 검사한다. 이번 보조 검사에서는 수영·물살 EditMode 테스트 68개와 두 폭포의 중앙·좌우 캡슐 경로 6개가 통과했고, 기존 경로의 NavMesh 연결 실패는 0이었다. 캡슐 경로 검사는 실제 KCC·입력·애니메이션의 Play Mode 검증을 대신하지 않는다.
- **근거:** [구현 결과와 사용자 테스트 명세](../../../output/RiverBasinWorld/WaterfallTraversal/RESULT.html). 실제 키보드·게임패드 조작의 낙하 감각과 하류 수영 복귀는 사용자 테스트 대기다.

### 4.8 수중 통로를 사각형 도랑으로 만들지 않는다

- **증상:** 통과 공간만 확보한 뒤 수중에서 보니 일정 폭의 절삭 경계와 평평한 바닥이 인공 수로처럼 보였다.
- **올바른 방법:** 물길의 실제 단면을 읽고, 비대칭으로 굽는 중심선·폭포 아래 깊은 소·완만한 자갈 사면을 함께 조형한다. 수면의 계단식 낙차를 바닥에 그대로 복제하지 않고 넓은 침식 경사로 연결한다. 저주파의 큰 굴곡 위에 작은 요철을 더하고, 볼록한 절삭 모서리만 완화한다. 기존 암반과 강바닥 자갈 레이어를 경사·퇴적 위치에 따라 섞는다.
- **이번 적용:** 두 폭포 구간의 수중 높이 표본 1,787개를 낮췄다. 소 중앙 수심 표본은 약 5.7~7.2m이며 육상 높이 변경은 0이다. 지형을 내릴 때 배치물도 재안착하고, 물살·낙하 통과와 NavMesh를 다시 검사했다. 재시도는 작업 시작 높이 백업에서 계산해 굴착이 누적되지 않게 했다.
- **검수:** 물속에서 강둑 옆면과 바닥 가까이를 직접 본다. 수면 위에서 자연스럽게 보이는 것만으로 통과시키지 않는다. [수중 지형 전후 비교와 검증 범위](../../../output/RiverBasinWorld/RiverbedSculpt/RESULT.html)를 참고한다. 실제 Play Mode의 수영 감각은 사용자 테스트 대기다.
