# 투사체 패리 — 구현 요청 프롬프트

기준: [Astra 확정 설계](../design/combat/PROJECTILE_PARRY_SYSTEM_DESIGN.md). [현재 상태](../../../docs/work-status/projectile-parry.md) · [전투 위키](../../../docs/wiki/combat.md).

이 문서는 복사해서 요청할 작업문이며 현재 구현 실행 지시가 아니다. 전체 구현은 아래 ‘전체 구현 요청’을 사용한다. 세션을 나눌 때는 P0~P4 프롬프트를 순서대로 사용한다. 각 프롬프트는 이 파일의 공통 규칙을 읽도록 되어 있다. 같은 작업 폴더와 Unity Editor에 여러 구현 세션을 동시에 실행하지 않는다.

## 공통 규칙

- 루트: `C:/UsingProject/UnityProject/UPlayground`. AGENTS.md, 전투 위키, 설계 전체, 최신 상태를 먼저 읽고 실제 코드·에셋과 대조한다. 설계 속 제안 필드명을 이미 존재하는 API로 가정하지 않는다.
- 필독: `Tools/Harness/README.md`, `Assets/docs/guide/CODE_AUTHORING_GUIDE.md`, `.claude/rules/architecture.md`, `.claude/rules/code-conventions.md`, `Assets/docs/guide/COMBAT_SYSTEM_AUTHORING_GUIDE.md`, `.claude/rules/gameplay-ability.md`, `Assets/docs/guide/TEST_VALIDATION_GUIDE.md`. C# 수정·컴파일에는 Hot Reload 운영 지침과 MCP 연동·복구 설계도 읽는다.
- 계획만 반환하지 말고 요청한 단계의 실제 작업·관련 검사·인계까지 수행한다. 전체 요청은 P0~P4를 연속 수행하되, 사용자 플레이 판정은 직접 테스트 명세로 남긴다. 단계별 요청은 지정 단계까지만 수행한다. 선행 구현이 없으면 존재하는 것으로 가정하지 않고 필요한 선행 단계와 근거를 보고한다.
- 시작 시 관련 미커밋·미추적 변경을 기록하고 보존한다. 궁수 발사 이벤트·모션·Staff·BT·기존 투사체 테스트의 다른 작업 변경을 되돌리지 않는다. GUID·meta·구매 원본 보존. 요청 없는 커밋·스테이징·Player/Addressables 빌드 금지.
- 열린 Unity Editor 하나를 MCP/Test Runner로 사용한다. 지원 변경은 Hot Reload 우선, 미지원 변경은 정상 컴파일. 차단 원인을 분류하고 도구 결함이면 수정·동일 작업 재검증한다. 두 번째 Editor·잠금/Library/Temp 삭제·기본 해법으로 재시작은 금지한다.
- 기존 ProjectileRuntime·전투 파이프라인·방어 컨트롤러·피드백 핸들러를 확장한다. 별도 패리 매니저/투사체 계층/테스트 프레임워크를 만들지 않는다. Data의 Actor/Manager 의존, 하위 모듈의 신규 매니저 싱글톤 참조, 액터/스테이지 이름 분기를 추가하지 않는다.
- GAS/AbilitySet이 공격 원본, MotionKey가 실행 모션 원본이다. 수치는 해당 SO, 운동은 ProjectileDefinition, 타이밍/표현은 MotionSet, 판단은 BT가 소유한다. 실제 데이터 저작 시 설치된 `uplayground-gas-data`, `uplayground-motion-skill`, BT 변경 시 `uplayground-bt-data` 중 해당 스킬을 읽고 적용한다.
- 핫패스의 GetComponent·Find·LINQ·매 틱 할당을 피한다. 검증은 관련 기존 테스트 확장과 실제 동작 경계를 중심으로 한다. 테스트 전용 가짜 구현을 제품에 넣지 않는다.
- 설계 구조를 조용히 바꾸지 않는다. 실제 구조와 충돌하면 근거·영향·최소 대안을 기록한다. 설계 변경 필요와 초깃값 튜닝을 구분한다. 범위 밖의 근접 가드 내구도·BT 밸런스 문제는 보고하고 별도로 남긴다.

### 빠뜨리면 안 되는 확정 계약

1. 기존 Guard 입력의 투사체 전용 창 0.18초, 재개방 0.35초, 몸 정면 140도. 근접 PerfectGuard 창은 별도 유지한다. 유지·조기 재입력·스왑으로 창을 연장/초기화하지 않는다. 일반 가드 진입·회피 반응성은 유지한다.
2. 초기 대상은 명시적으로 opt-in한 Parryable 직선 화살/단일 직선 마법탄이다. 지원 motion·behavior의 정확한 조건은 설계 §4를 따른다. 비지원 조합·GuardableOnly·Unblockable은 디버그/정책으로도 반사하지 않는다.
3. Guard의 같은 창에 들어온 적격 탄은 모두 반사, 성공 보상은 행동당 1회. 공격/assist는 첫 성공 후 기존 공격 종료/assist 폴백 취소를 유지하고 창을 새로 만들지 않는다. 한계 직전 내구도라도 적격 패리는 소모 0이며, 이미 가드 불능이면 구제하지 않는다.
4. 판정 준비 → 반사 준비 → 탄 상태 확정 → 방어/보상 적용. ReceiveHit 부작용 뒤 반사를 시도하는 순서로 완료 처리하지 않는다. 중복 접촉·풀 세대 검증과 단일 확정이 필요하다. 승인 후 반사 공간/마스크가 없으면 Absorbed로 안전 소멸하고 피해·폭발·분열을 발생시키지 않는다.
5. 반환은 접촉 순간 탄 중심에서 시작한다. 기본 역방향, 원 발사자에 한해 30도/35m·사선 조건의 1회 조준 보정. 속도 ×1.25와 maxSpeed 상한, 반환 수명 2초, 생애 반사 1회. 벽 관통·다른 타깃 자동 선택·잔여 원방향 sweep 처리를 금지한다.
6. 공격 수치는 최초 발사 스냅샷, 킬/기여도는 반사자 귀속. 명중 대상의 현재 방어·면역 정책을 통과한다. 반사자의 무기 공격력/속성·새 치명 재계산·원 공격 재발동을 하지 않는다.
7. 반사 순간 원 발사자 OnParried·freeze·전체 적 슬로우·근접 카운터 창을 만들지 않는다. 실제 반환탄 명중으로만 적 피해/경직이 발생한다. 일반 NotifyAttackHit를 통한 공격 proc/게이지/추가타 재귀를 억제한다. 직접 추가 VitalOrb 0회, 기존 방어성공 구독자의 보상도 행동당 1회다.
8. Guard 투사체 창/재개방과 지원 탄 비행/수명은 전역 게임 시간·일시정지를 따르고 Actor 로컬 정지와 분리한다. 공격/assist의 기존 판정 창은 유지한다. 저프레임 sweep 접촉과 입력 창을 같은 시간 기준으로 비교해 늦은 입력을 소급 인정하지 않는다.
9. NonAlloc 결과 정렬만으로 버퍼 포화를 해결했다고 보고하지 않는다. 설계의 재조회/상한 안전 소멸·초기 겹침·동률 장애물 우선·풀 초기화를 구현하고 검증한다.
10. 숫자는 플레이 검증 전 초깃값이다. 런타임 하드코딩만으로 두지 않고 해당 SO로 연결한다. 반사 가능 탄은 색에만 의존하지 않는 형태·소리로 구분한다.

### 단계 종료와 보고

- 단일 상태 정본 `docs/work-status/projectile-parry.md`에 현재 단계, 변경 파일·에셋/GUID, 검사 결과와 원본 근거, 알려진 실패·미수행, 다음 행동을 갱신한다. 긴 근거가 필요하면 `docs/work-status/projectile-parry/`에 보관하고 상태에서 연결한다.
- 각 단계마다 전투 위키의 해당 항목과 요청서 연결을 갱신하고 로컬 링크를 검사한다. 설계 정본에는 계약만 유지하며 검증 로그를 누적하지 않는다. 이번 작업에서 만든 불필요 임시 자료만 정리한다.
- 코드 변경은 Unity 컴파일과 관련 EditMode, 실행 경계는 관련 Editor PlayMode, 데이터 변경은 조합/참조 검사를 수행한다. 실행할 수 없으면 원인과 실제 남은 범위를 기록한다. 과거 통과·보조 컴파일·코드 열람을 현재 Unity 통과로 승계하지 않는다.
- 최종 보고는 변경/왜 필요한지, 수행·실패·미수행 검사와 근거, 사용자 테스트 대기, 범위 밖 발견, 다음 단계, 갱신한 위키/상태 링크를 포함한다. 사용자 입력·손맛·미술·청감은 자동 검사로 합격 처리하지 않는다.

## P0 — 연결 조사와 구현 범위 확정

```text
작업 루트 C:/UsingProject/UnityProject/UPlayground.
Assets/docs/requests/PROJECTILE_PARRY_IMPLEMENTATION_PROMPTS.md의 공통 규칙을 읽고 설계 P0만 수행해줘.

1. 최신 코드·에셋을 대조해 실제 적 화살 1종과 적 단일 직선 마법탄 1종의 AbilitySet → Ability/Variant/Payload → HitPhase → MotionKey/MotionSet → SpawnProjectile → Definition/호환 셸 → 실제 프리팹·액터를 추적해줘. 경로·GUID·현재 미커밋 변경·공용 참조 범위를 표로 남겨줘. Griffin WindBolt나 플레이어 StaffBolt를 실제 적 화살/마법탄 연결의 증거 없이 대신 등록하지 마.

3. 지원 탄의 현재 속도·곡선·Behavior·시간축·벽 충돌 레이어·표시/음향 리소스를 확인하고 opt-in 대상과 제외 대상을 확정해줘. 공용 Definition을 바꾸면 비대상까지 영향받는지 확인하고 필요한 경우 기존 GUID를 보존한 별도 Definition 연결안을 정해줘.
4. 기존 테스트·저작 검증기·MCP/Hot Reload 사용 가능 상태를 읽기 위주로 확인하고 P1~P4의 수정 범위·의존성과 검증 준비표를 만들어줘. 아직 런타임·SO·프리팹을 변경하지 마.

완료 조건: 두 실제 발사 연결과 소비자/부작용 목록, 초기 대상·제외 대상, 후속 구현 범위가 근거와 함께 식별되어 있다. 근거 없는 대상 선정은 미확정으로 남긴다. 상태와 전투 위키를 갱신하고 P1 인계를 제공해줘.
```

## P1 — 판정과 단일 확정 계약

```text
작업 루트 C:/UsingProject/UnityProject/UPlayground.
Assets/docs/requests/PROJECTILE_PARRY_IMPLEMENTATION_PROMPTS.md의 공통 규칙과 완료된 P0 기록을 읽고 설계 P1을 구현해줘.

1. 순수 방어 후보 입력, Guard/Attack/Assist 출처, 방어 행동 토큰, 탄 발사/접촉 ID와 풀 세대, None/Reflected/Absorbed 응답을 기존 파이프라인에 필요한 최소 구조로 연결해줘. DefenseOutcome만으로 반사를 추측하지 않게 해줘.
2. 투사체 전용 Guard 창·재개방·정면 판정과 실제 새 입력 조건을 구현해줘. 근접 가드 판정과 공격/assist 창의 기존 시간 계약을 보존하고 투사체 Guard 시간축은 설계대로 분리해줘. FaceIncomingAttack 이전 방향을 사용해줘.
3. 적격 패리는 가드 소모 전 확정하고, 비적격 투사체 가드는 Block/GuardBreak로 처리해줘. 같은 Guard 창의 다중탄은 모두 처리하되 보상은 1회, 공격/assist는 첫 성공 후 기존 행동 종료/폴백 취소를 유지해줘.
4. 준비 단계는 무부작용, commit 뒤에만 방어·피드백·보상 적용이 가능하도록 연결해줘. 중복/stale 접촉 취소와 승인 후 실패의 Absorbed를 구현해줘. 반사 런타임 연결에 필요한 최소 P2 접점도 제품 경로에서 일관되게 처리하고 성공만 반환하는 임시 스텁을 남기지 마.
5. 창·각도·재개방 경계, 내구도 한계, 비지원/Unblockable, 세 경로 배타성, 다중탄 보상, 중복 접촉/풀 세대, 실패 소멸 회귀를 추가해줘. 기존 근접 가드·회피·패리 회귀도 확인해줘.

완료 조건: 컴파일 가능한 판정·단일 확정 경로와 관련 테스트 결과가 있다. 새 탄 콘텐츠는 아직 활성화하지 않는다. P2가 남은 동작을 구현 완료로 보고하지 않고 상태·위키에 정확히 기록해줘.
```

## P2 — 반사 운동·피해 출처·수명

