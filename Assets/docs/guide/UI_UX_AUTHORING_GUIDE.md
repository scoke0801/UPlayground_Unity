# UI/UX 제작 지침

> 대상: 이 프로젝트의 화면(HUD·Scene·Popup·WorldSpace)을 새로 만들거나 고치는 모든 작성자(사람과 AI)<br>
> 파일 생성 절차: [`/add-ui`](../../../.claude/commands/add-ui.md) — 이 지침은 그 명령이 만든 뼈대를 **무엇으로 채울지**를 정한다.

---

## 1. 역할과 목표

이 문서를 들고 작업하는 사람은 **게임 UI/UX 전문 디자이너**다. 요청받은 화면을 띄우는 것이 아니라, **플레이어가 헤매지 않고 쓸 수 있는 화면**을 만드는 것이 목표다.

세 가지를 동시에 만족해야 한다.

1. **쉽다.** 설명 없이 조작 방법을 안다. 원하는 동작에 도달하는 경로가 짧다.
2. **이해된다.** 화면에 뜬 숫자와 아이콘이 무엇을 뜻하는지, 지금 무엇을 결정해야 하는지 안다.
3. **통일되어 있다.** 다른 화면에서 익힌 규칙이 이 화면에서도 그대로 통한다.

그리고 **게임의 UI는 문서 뷰어가 아니다.** 단순한 값 변경이나 열고 닫기라도 트윈을 넣어 살아 있게 만드는 것을 항상 먼저 검토한다.

---

## 2. 작업 시작 전 필수 절차

새 화면을 그리기 전에 반드시 이 순서를 밟는다. 건너뛰면 통일성이 깨진다.

1. **비슷한 기존 화면을 찾는다.** `Assets/02.Scripts/UI/` 아래에서 같은 성격의 화면을 연다. 인벤토리형인지, 목록+상세형인지, 확인 팝업형인지.
2. **재사용할 수 있는지 판단한다.** 기존 화면·컴포넌트를 확장하면 되는 일을 새 화면으로 만들지 않는다.
3. **공용 컴포넌트를 확인한다.** `Assets/02.Scripts/UI/Common/`에 이미 있는 것을 다시 만들지 않는다.
4. **리소스를 먼저 찾는다.** 6절의 폴더에서 실제 사용할 스프라이트를 정한 뒤 레이아웃을 잡는다. 리소스 없이 잡은 레이아웃은 대부분 다시 그려야 한다.

## 3. 통일성 — 최우선 규칙

플레이어는 화면마다 새로 배우고 싶어 하지 않는다. **개별 화면의 완성도보다 화면 사이의 일관성이 먼저다.**

### 3.1 구조 통일 — 베이스 클래스와 레이어

| 화면 성격 | 상속 | `CanvasLayer` | 특징 |
|---|---|---|---|
| 전투 중 상시 노출 정보 | `UI_Base` | `HUD` (0) | 입력 차단 없음, 커서 없음 |
| 전체 화면 메뉴 (인벤토리·퀘스트·설정 등) | `UI_SceneBase` | `Scene` (1000) | 페이드+슬라이드 인/아웃 내장 |
| 확인·경고·모달 대화 | `UI_PopupBase` | `Popup` (2000) | Dim 페이드 + 패널 스케일 팝인 내장 |
| 시스템 알림·로딩 | `UI_Base` | `System` (3000) | |
| 월드 공간 표시 (체력바·마커) | `UI_Base` | `WorldSpace` (10000) | 커서·입력 레이어 대상 아님 |

- **레이어를 임의로 바꾸지 않는다.** 커서 표시(`RequiresCursorVisible`)와 입력 차단(`BlocksLowerInput`) 판정이 레이어에 묶여 있다.
- 입력을 독점해야 하는 모달은 `BlocksLowerInput`을 `true`로 오버라이드한다. 월드 상호작용 프롬프트처럼 게임플레이 입력을 막으면 안 되는 화면은 기본값을 유지한다.
- 팝업/씬 화면을 만들면서 **자체 열기·닫기 연출을 새로 짜지 않는다.** 베이스가 이미 제공한다. `OnShow`에서 `base.OnShow()`를 호출하는 것으로 끝난다.

### 3.2 공용 컴포넌트 재사용

`Assets/02.Scripts/UI/Common/` 에 있는 것을 우선 사용한다.

| 컴포넌트 | 용도 |
|---|---|
| `UICommonButton` | 표준 버튼 |
| `UICommonSlider` | 값 조절 슬라이더 |
| `UICommonDropdown` | 선택 목록 |
| `UISwitchButton` | 켜기/끄기 토글 |
| `UITabGroup` / `UITabButton` | 탭 전환 (메인/서브 탭 단축키는 `UI_Base`가 처리) |
| `UIScrollRectForwarder` | 중첩 스크롤 전달 |
| `UISelectOnPointerEnter` | 마우스 호버 시 선택 동기화 |
| `UGuiFactory` | **데이터 개수에 따라 구조가 변하는 화면**을 코드로 조립할 때 |

**프리팹 고정 저작이 원칙**이고, 키 설정 목록처럼 항목 수가 데이터에 따라 달라지는 화면만 `UGuiFactory`로 코드 조립한다. 반대로 고정 레이아웃을 코드로 짜지 않는다.

### 3.3 네이밍

- `UI_Base` 계열을 상속하는 화면 클래스만 `UI_` 접두사를 쓰고, **화면이 속한 `CanvasLayer`를 접두사에 명시한다.**
  - `CanvasLayer.HUD` → `UI_HUD_{이름}` (`UI_HUD_PlayerInfo`, `UI_HUD_QuickSlot`)
  - `CanvasLayer.Scene` → `UI_Scene_{이름}` (`UI_Scene_Inventory`, `UI_Scene_PauseMenu`)
  - `CanvasLayer.Popup` → `UI_Popup_{이름}` (`UI_Popup_Item`, `UI_Popup_Respawn`)
  - `CanvasLayer.System` → `UI_System_{이름}` (`UI_System_LoadingScreen`)
  - 이름 본문에 레이어를 뜻하는 단어를 중복해 넣지 않는다. (`UI_HUD_HudSkill` ✕ → `UI_HUD_Skill` ○)
  - 공통 베이스(`UI_Base`, `UI_SceneBase`, `UI_PopupBase`)는 화면이 아니므로 접두사를 붙이지 않는다.
- 그 외 UI 보조 클래스는 언더스코어 없이 `UIXxx`. (`UICommonButton`, `UITabGroup`, `UIActorHpBar`)
- **프리팹 이름은 컴포넌트 클래스 이름과 같게 맞춘다.** (`UI_Scene_Inventory.cs` ↔ `UI_Scene_Inventory.prefab`)
- 스크립트 위치는 `Assets/02.Scripts/UI/<Category>/`, 카테고리는 `HUD` / `Scene` / `Dialogue` / `Interaction` / `WorldSpace` / `Common` / `InputPrompt`.

### 3.4 비주얼 통일

- **한 화면에 서로 다른 리소스 팩을 섞지 않는다.** 프레임은 A팩, 버튼은 B팩인 화면은 즉시 이질감을 만든다.
- 같은 의미에는 항상 같은 색을 쓴다. 체력·기력·경험치·위험·비활성의 색은 화면마다 달라지면 안 된다.
- 여백·모서리 반경·아이콘 크기는 기존 화면에서 측정해 그대로 따른다. 새 값을 도입하려면 기존 화면도 같이 바꿔야 하므로, 그럴 만한 이유가 있을 때만 제안한다.
- 폰트는 TextMeshPro를 쓰고 기존 화면에서 쓰는 크기 단계를 재사용한다. 임의 크기를 새로 만들지 않는다.

### 3.5 상호작용 통일

- **닫기 규칙:** ESC로 닫히는지 여부는 `_canCloseWithEsc`로 통일한다. 화면마다 다른 닫기 키를 만들지 않는다.
- **버튼 사운드:** `UI_Base`가 하위 `Button`에 기본 클릭 사운드를 자동 바인딩한다. 개별 화면에서 중복으로 붙이지 않는다. 예외가 필요하면 `_playDefaultButtonSound`를 끈다.
- **초기 포커스:** 모달과 전체 화면은 `SetDefaultFocus`로 의미에 맞는 첫 항목을 지정한다. 게임패드로 열었을 때 아무것도 선택돼 있지 않으면 조작이 막힌다.
- **키 안내:** 조작 키 표시는 `Assets/02.Scripts/UI/InputPrompt/`의 입력 프롬프트 시스템을 사용한다. 키 이름을 텍스트로 하드코딩하지 않는다. 장치가 바뀌면 글리프도 바뀌어야 한다.

## 4. 트윈 연출 — 단순한 처리에도 연출을 넣는다

### 4.1 원칙

**즉시 나타나고 즉시 사라지는 UI는 싸구려로 보인다.** 값이 바뀌고, 열리고, 선택이 옮겨가는 모든 순간에 트윈을 검토한다.

트윈은 장식이 아니라 **정보 전달 수단**이다.

- 어디서 어디로 갔는지 보여준다 (획득 아이템이 슬롯으로 날아감)
- 무엇이 바뀌었는지 알려준다 (체력바가 깎이는 과정)
- 무엇을 봐야 하는지 가리킨다 (새 항목의 짧은 강조)
- 조작이 먹혔음을 확인시킨다 (버튼 눌림 반응)

### 4.2 프로젝트 제약 — 반드시 지킬 것

이 프로젝트는 DOTween을 쓰지만 **UI 어셈블리에는 두 가지 제약**이 있다.

1. **모든 UI 트윈에 `SetUpdate(true)`를 붙인다.** 히트스톱과 일시정지(`timeScale = 0`) 중에도 UI는 움직여야 한다. 빠뜨리면 정지 중 UI가 얼어붙는다.
2. **`CanvasGroup.DOFade` / `RectTransform.DOAnchorPos`를 쓸 수 없다.** UI asmdef는 프리컴파일된 `DOTween.dll`만 참조하므로 `DOTweenModuleUI` 확장이 없다. 기존 코드처럼 `DOTween.To`로 직접 트윈한다.

```csharp
// 알파
DOTween.To(() => _canvasGroup.alpha, v => _canvasGroup.alpha = v, 1f, duration).SetUpdate(true);

// 위치
DOTween.To(() => _rect.anchoredPosition, v => _rect.anchoredPosition = v, end, duration)
       .SetEase(Ease.OutCubic)
       .SetUpdate(true);
```

3. **트윈은 반드시 정리한다.** `OnHide` / `OnDestroy` / `OnDispose`에서 `Kill()`한다. 파괴된 오브젝트를 향해 살아 있는 트윈은 예외를 던진다. 시퀀스를 새로 만들기 전에도 기존 것을 먼저 죽인다.

### 4.3 표준 타이밍

기존 베이스 클래스의 값이 이 프로젝트의 기준이다. 새 화면은 여기서 벗어나지 않는다.

| 구분 | 열기 | 닫기 | Ease (열기/닫기) |
|---|---|---|---|
| 팝업 (`UI_PopupBase`) | 0.22초 | 0.14초 | `OutBack` / `InCubic` |
| 전체 화면 (`UI_SceneBase`) | 0.25초 | 0.18초 | `OutCubic` / `InCubic` |
| 소형 피드백 (버튼·선택·강조) | 0.08~0.15초 | — | `OutQuad` / `OutBack` |
| 값 변화 (체력·게이지·수치) | 0.2~0.4초 | — | `OutCubic` |

**닫기는 항상 열기보다 빠르다.** 사용자는 이미 결정을 내렸으므로 기다리게 하면 안 된다.

### 4.4 과잉 연출 금지

트윈이 조작을 방해하면 연출이 아니라 결함이다.

- **입력을 막지 않는다.** 연출 중에도 다음 조작을 받고, 필요하면 진행 중인 트윈을 즉시 완료시킨다.
- **자주 여는 화면일수록 짧게.** 하루에 백 번 여는 인벤토리에 0.5초 연출을 넣으면 그 게임은 느린 게임이 된다.
- **반복 노출되는 연출은 스킵 가능해야 한다.**
- **동시에 움직이는 요소는 적게.** 화면 전체가 흔들리면 무엇이 중요한지 알 수 없다.
- **0.5초를 넘는 UI 트윈은 근거가 필요하다.** 연출 목적(획득 연출, 레벨업 등)이 아니면 넘기지 않는다.

## 5. 이해되는 화면 만들기

- **한 화면에 목적은 하나.** 지금 플레이어가 내려야 할 결정이 무엇인지 한 문장으로 말할 수 없으면 화면을 쪼갠다.
- **위계를 만든다.** 가장 중요한 정보 → 보조 정보 → 부가 정보 순으로 크기·명도·위치가 명확히 차이 나야 한다. 전부 같은 크기면 아무것도 안 보인다.
- **숫자에는 의미를 붙인다.** `+12`가 좋은 것인지 나쁜 것인지 색이나 기호로 보여준다. 원시 수치만 던지지 않는다.
- **빈 상태를 설계한다.** 목록이 비었을 때 빈 칸이 아니라 "왜 비었고 무엇을 하면 채워지는가"를 보여준다.
- **되돌릴 수 없는 조작에는 확인을 둔다.** 반대로 되돌릴 수 있는 조작에는 확인을 넣지 않는다. 확인 팝업이 흔해지면 아무도 읽지 않는다.
- **용어는 게임 세계의 말로 쓴다.** 개발·시스템 용어를 화면에 노출하지 않는다. 자세한 기준은 [STORY_PLOT_AUTHORING_GUIDE.md](STORY_PLOT_AUTHORING_GUIDE.md) 3절을 따른다.

### 6.3 규칙

1. **먼저 찾고, 없으면 보고한다.** 임의로 색만 칠한 사각형으로 대체하고 넘어가지 않는다. 무엇이 없어서 무엇으로 임시 대체했는지 명확히 보고한다.
2. **한 화면 안에서는 한 팩으로 통일한다.** (3.4 참조)
3. **입력 글리프는 반드시 `InputIcon`을 쓴다.** 키 이름 텍스트로 대체하지 않는다.
4. **9-슬라이스를 활용한다.** 크기가 변하는 프레임·버튼 배경은 스프라이트를 늘리지 말고 border를 설정한다.
5. **외부 팩의 원본 파일을 수정하지 않는다.** 색·크기 변경은 `Image`의 color/material 또는 프로젝트 쪽 사본으로 처리한다. 원본을 고치면 팩 갱신 시 전부 날아간다.

## 7. 게임패드 조작 규칙

**이 게임은 패드로 하는 액션 게임이다. 게임패드가 1급 입력이고 마우스가 보조다.** 마우스로만 누를 수 있는 버튼은 기능이 아니라 결함이다.

아래 규칙은 콘솔 UI의 업계 표준(Xbox 접근성 가이드라인 XAG 112, 상용 콘솔 타이틀 관례)을 이 프로젝트 구조에 맞춰 정리한 것이다.

### 7.1 포커스 기반 조작 — 가장 중요한 원칙

콘솔 UI는 **포인터가 아니라 포커스로 움직인다.** 패드로 조작하는 동안 마우스 커서를 띄우지 않는다.

- **항상 정확히 하나가 선택되어 있다.** 선택이 없는 순간이 생기면 그 화면은 패드로 조작 불능이다.
- **화면을 열면 즉시 포커스를 준다.** `UI_Base.SetDefaultFocus(selectable)`로 화면 의미에 맞는 첫 항목을 지정한다. 지정하지 않으면 첫 번째 유효 `Selectable`이 자동 선택되는데, 그것이 의미상 맞는 항목인 경우는 드물다.
- **닫고 돌아오면 있던 자리로 복원한다.** `UIFocusScope`가 선택을 스택으로 보존·복원한다. 화면마다 따로 구현하지 않는다.
- **선택 상태는 한눈에 보여야 한다.** 은은한 하이라이트로는 부족하다. 테두리·확대·배경 대비 중 **둘 이상**을 겹쳐 쓴다. 색만으로 구분하지 않는다.
- **비활성 항목은 포커스를 받지 않고 건너뛴다.** 다만 왜 비활성인지는 보여준다.
- 선택 이동에 짧은 트윈(0.08~0.15초)을 붙여 **어디서 어디로 갔는지** 보이게 한다. 순간이동하면 위치를 잃는다.

### 7.2 버튼 규약 — 화면마다 달라지면 안 된다

프로젝트의 `UIAction` 상수를 그대로 쓴다. 화면별로 새 버튼 의미를 만들지 않는다.

| 역할 | 액션 | 규칙 |
|---|---|---|
| 확인·실행 | `Submit` | 남쪽 버튼(A / ✕). 항상 "진행" |
| 취소·뒤로 | `Cancel` | 동쪽 버튼(B / ○). 항상 "한 단계 뒤로". **어느 화면에서든 반드시 동작해야 한다** |
| 이동 | `Navigate` | D-Pad와 왼쪽 스틱 **양쪽** 지원 |
| 메인 메뉴 전환 | `MainTabPrevious` / `MainTabNext` | 숄더(LB/RB). 대분류 페이지 이동 |
| 서브 탭 전환 | `SubTabPrevious` / `SubTabNext` | 트리거(LT/RT). 페이지 내 탭 이동 |
| 공간 지시 | `VirtualCursorMove` | 오른쪽 스틱. 지도처럼 좌표를 직접 가리켜야 할 때만 |

- **`Cancel`로 빠져나갈 수 없는 화면을 만들지 않는다.** 이것이 패드 UI에서 가장 흔하고 치명적인 결함이다.
- 탭 전환을 `Navigate`(방향키)로 처리하지 않는다. 목록 이동과 탭 이동이 같은 입력을 쓰면 반드시 충돌한다.
- 파괴적 조작을 `Submit`에 바로 걸지 않는다. 확인 팝업을 거친다.

### 7.3 포커스 이동 규칙

- **방향은 시각적 배치와 일치한다.** 왼쪽을 누르면 화면상 바로 왼쪽 항목으로 간다. `Selectable`의 Navigation 연결이 실제 레이아웃과 어긋나지 않는지 확인한다.
- **1차원 목록은 순환(loop)한다.** 위/아래만 또는 좌/우만 움직이는 목록은 끝에서 처음으로 감긴다.
- **2차원 격자는 순환하지 않는다.** 상하좌우로 자유롭게 움직이는 배치에서 끝에서 감기면 플레이어가 위치를 잃는다.
- **화면 간에 배치 순서를 일관되게 유지한다.** 여러 화면에 반복 등장하는 요소(제목, 확인/취소 프롬프트)는 항상 같은 자리, 같은 순서에 둔다.
- **스크롤 목록은 선택을 따라 자동으로 스크롤한다.** `UIFocusScope`가 선택을 감싸는 `ScrollRect`를 추적한다. 선택 항목이 화면 밖에 있으면 안 된다.
- 항목이 아주 많은 목록(도감·인벤토리)에는 **탐색 수단을 하나 더 준다.** 탭 필터, 정렬, 점프 등. 스틱으로만 훑게 하지 않는다.

### 7.4 입력 응답성

- **스틱 한 번 기울임 = 한 칸 이동.** 임계값(0.5 내외) 이상에서 1회만 발화하고, 스틱이 중립으로 돌아오기 전까지 재발화하지 않는다. 이것을 처리하지 않으면 한 번 밀 때 두세 칸씩 튄다.
- **길게 누르면 자동 반복.** 첫 반복까지 약 0.4초 지연, 이후 약 0.1초 간격. 지연이 없으면 미끄러지고, 반복이 없으면 긴 목록을 훑을 수 없다.
- D-Pad는 디지털이므로 임계값 처리가 필요 없다. 다만 **자동 반복은 동일하게 적용**한다.
- 홀드가 필요한 조작(길게 눌러 삭제 등)은 **진행 게이지를 보여준다.** 얼마나 더 눌러야 하는지 모르면 홀드는 스트레스다.

### 7.5 화면 안내 (Input Prompt)

- **지금 쓸 수 있는 버튼을 화면에 표시한다.** 최소한 `Submit`과 `Cancel`은 항상 보인다.
- 프롬프트 바는 **화면마다 같은 위치**에 둔다. 항목 수가 달라져도 위치와 상대 순서는 유지한다.
- 표시에는 `Assets/02.Scripts/UI/InputPrompt/`의 글리프 시스템을 쓴다. **키 이름을 텍스트로 하드코딩하지 않는다.** 장치가 Xbox·PlayStation·키보드로 바뀌면 글리프도 자동으로 바뀌어야 한다.
- 컨텍스트 전용 조작(LT/RT 등)이 있으면 그 화면에서 반드시 라벨과 함께 노출한다.

### 7.6 가상 커서는 예외다

지도처럼 **좌표를 직접 가리켜야 하는 화면에서만** `UIVirtualCursorController`를 켠다.

- 오른쪽 스틱이 처음 움직일 때 포인터 모드로 전환하고, 왼쪽 스틱/D-Pad `Navigate`가 들어오면 즉시 포커스 모드로 복귀한다.
- **일반 메뉴에 가상 커서를 도입하지 않는다.** 포커스 이동으로 가능한 일을 커서로 처리하면 조작이 느려지고 콘솔 관례에서 벗어난다.

### 7.7 그 외 접근성

- 색만으로 상태를 구분하지 않는다. 아이콘·형태·텍스트를 함께 쓴다.
- 최소 클릭·선택 대상 크기를 지키고, 해상도 변화에 대비해 앵커를 올바르게 설정한다. 고정 좌표로 배치하지 않는다.
- 텍스트 크기가 커져도 **두 방향으로 스크롤해야 내용이 보이는 상태**가 되지 않게 한다.
- 하위 화면 어디에서든 상위 화면으로 돌아가는 경로가 항상 열려 있어야 한다.

### 7.8 게임패드 검증 절차

**마우스를 뽑고 패드만으로 다음을 전부 수행한다.** 하나라도 막히면 미완성이다.

1. 화면을 연다 → 의미에 맞는 항목에 포커스가 있는가
2. 모든 조작 가능 요소에 도달할 수 있는가
3. 방향 입력이 시각적 배치와 일치하는가
4. 스틱을 한 번 밀었을 때 한 칸만 움직이는가
5. 길게 눌렀을 때 적절한 속도로 반복되는가
6. 선택이 스크롤 뷰 밖으로 나가지 않는가
7. `Cancel`로 빠져나올 수 있는가
8. 다시 들어왔을 때 이전 선택이 복원되는가
9. 화면에 표시된 버튼 안내가 실제 동작과 일치하는가
10. 장치를 키보드/Xbox/PlayStation으로 바꿨을 때 글리프가 따라 바뀌는가

## 8. 최종 체크리스트

**통일성**
- [ ] 비슷한 기존 화면을 확인했고, 구조·여백·색·폰트 단계를 따랐다.
- [ ] 올바른 베이스 클래스와 `CanvasLayer`를 사용했다.
- [ ] 공용 컴포넌트를 재사용했고, 있는 것을 다시 만들지 않았다.
- [ ] 한 화면 안에서 리소스 팩을 섞지 않았다.
- [ ] 네이밍 규약(`UI_{레이어}_{이름}` vs `UIXxx`)을 지켰고, 접두사가 실제 `_layer` 값과 일치한다.
- [ ] 프리팹 이름을 컴포넌트 클래스 이름과 동일하게 맞췄다.

**연출**
- [ ] 열기·닫기 연출이 있다 (베이스 제공분 포함).
- [ ] 값 변화·선택 이동·피드백에 트윈을 검토했다.
- [ ] 모든 트윈에 `SetUpdate(true)`가 있다.
- [ ] `CanvasGroup.DOFade` / `DOAnchorPos` 대신 `DOTween.To`를 썼다.
- [ ] `OnHide` / `OnDestroy` / `OnDispose`에서 트윈을 `Kill`한다.
- [ ] 닫기가 열기보다 빠르고, 연출이 입력을 막지 않는다.

**사용성**
- [ ] 이 화면에서 플레이어가 내릴 결정을 한 문장으로 말할 수 있다.
- [ ] 정보 위계가 크기·명도·위치로 구분된다.
- [ ] 빈 상태와 오류 상태가 설계되어 있다.
- [ ] 화면에 개발·시스템 용어가 노출되지 않는다.

**게임패드** (7.8의 10단계를 마우스 없이 실제로 수행했는가)
- [ ] 열자마자 의미에 맞는 항목에 포커스가 있고, 선택이 항상 하나 존재한다.
- [ ] 모든 조작 요소에 도달 가능하고, 방향 입력이 시각적 배치와 일치한다.
- [ ] 1차원 목록은 순환하고 2차원 격자는 순환하지 않는다.
- [ ] 스틱 한 번에 한 칸 이동하고, 홀드 시 자동 반복이 동작한다.
- [ ] 선택이 스크롤 뷰 밖으로 나가지 않는다.
- [ ] 어느 지점에서든 `Cancel`로 빠져나올 수 있다.
- [ ] 탭 전환을 방향키가 아닌 숄더/트리거에 배치했다.
- [ ] `Submit`/`Cancel`을 포함한 입력 프롬프트가 표시되고, 글리프가 장치에 따라 바뀐다.
- [ ] 가상 커서를 일반 메뉴에 쓰지 않았다.

**리소스**
- [ ] `Assets/04.Images/` 또는 `Assets/ExternalAssets/UI/`에서 실제 리소스를 찾아 썼다.
- [ ] 찾지 못한 리소스는 임시 대체 사실을 보고했다.
- [ ] 외부 팩 원본 파일을 수정하지 않았다.
