# explain-diagram — SVG 도식 + 구조 설명 HTML

산출물은 **HTML 단일 파일**(SVG는 인라인)이다. 기본 모양은 `Assets/docs/design/dev-tools/BT Editor Design Guide.html`과 같은 **어두운 에디토리얼 스타일**(히어로·번호 섹션·카드·칩·전후 비교·로드맵)이다. `theme="light"` 또는 `"auto"`로 바꿀 수 있다. 글꼴(IBM Plex)은 웹 글꼴이며 오프라인이면 시스템 글꼴로 대체된다.

## 저장 위치 (역할 분리 — CLAUDE.md 문서 분리 규칙)
문서는 **역할이 같은 것끼리 한 폴더**에 둔다. 기준 폴더는 모두 `Assets/docs/` 아래다.

| 문서 종류 | 위치 |
|---|---|
| 설계·구조 설명 | `Assets/docs/design/<분야>/<시스템>/<UPPER_SNAKE>_DESIGN.html` (분야: `combat`·`content`·`npc`·`ui-player`·`world-art`·`dev-tools`) |
| **저작·사용 지침(가이드)** | **`Assets/docs/guide/<UPPER_SNAKE>_GUIDE.html`** (하위 폴더 없이 이 폴더에 둔다. `design/` 밑에 `guide` 폴더를 만들지 않는다) |
| 작업 요청서·프롬프트 | `Assets/docs/requests/` |
| 조사·근거 | `Assets/docs/research/` |
| 시안·참조 이미지 | `Assets/docs/reference/` |
| 구현 진행·검증 상태 | `docs/work-status/<작업명>/` (설명 문서에 섞지 않는다) |

- 새 시스템 폴더는 그 분야에 같은 시스템 문서가 둘 이상일 때 만든다. 새 폴더를 만들면 `.meta`도 함께 만들거나 Unity에서 열어 생성한다.
- 문서를 추가하면 **그 폴더의 `README.md`**(한국어 문서 목록)에 한 줄을 추가한다.
- 분야 위키(`docs/wiki/`)에는 요약과 링크만 남긴다.
- 임시 산출물·PNG 캡처는 scratchpad에 둔다. 문서 폴더에 PNG를 남기지 않는다.

## 절차
1. **조사:** `docs/wiki/README.md`와 대상 코드·에셋을 먼저 읽어 사실을 확인한다. 추측으로 박스를 그리지 않는다. 확인 못 한 부분은 도식에 `kind="warn"`으로 표시하고 본문에 "미확인"이라 쓴다.
2. **독자·질문 정하기:** 독자가 이 문서를 읽고 답할 수 있어야 할 질문 1~3개를 정한다(예: "공격 한 번이 어떤 순서로 처리되나?"). 질문에 답하지 않는 도식은 넣지 않는다.
3. **도식 선택:** 아래 표에서 질문에 맞는 유형을 고른다. 한 도식은 한 가지만 보여 준다(노드 12개 이하 권장, 넘으면 쪼갠다).
4. **스크립트 작성:** `scripts/example_rich.py`(전체 컴포넌트 템플릿, 권장)나 `scripts/example_layers.py`(도식 중심 최소형)를 scratchpad로 복사해 수정한다. 좌표는 격자(20px 단위)에 맞추고 노드 간격은 라벨이 들어갈 만큼 100px 이상 둔다.
5. **실행·검사:** `python -I <script> <out.html>` 실행 시 `WARN:`이 나오면 간격·라벨을 고친다. 이어서 `python -I scripts/render_check.py <out.html> <png>`로 캡처한 뒤 PNG를 Read로 직접 보고 겹침·잘림·글자 넘침이 없는지 확인한다. 보지 않고 완료라 하지 않는다.
6. **배치:** 확정 HTML을 위 저장 위치에 둔다. 위키 연결은 문서 종류로 정한다.
   - `design/`·`requests/`·`research/` 문서: 해당 분야 위키에 요약과 링크를 추가하고 work-status와 양방향으로 연결한다.
   - `guide/` 문서: **위키 추가 대상이 아니다.** 위키·work-status에 링크를 넣지 않는다(저작 규칙은 CLAUDE.md 진입 안내가 따로 맡는다).
   - 문서 안에서 다른 문서의 상태를 바꾸지 않는다. 다른 작업(예: 마이그레이션 계획 정정)은 발견만 보고하고 별도 작업으로 넘긴다.

## 도식 유형
| 질문 | 유형 | 구성 |
|---|---|---|
| 무엇이 무엇을 포함·의존하나 | 계층도 | `group`을 세로로 쌓고 안에 `node`, 층 간 `edge` |
| 어떤 순서로 일어나나 | 흐름도 | 가로 `node` 열 + `badge="1"` 번호 + `edge` |
| 누가 누구를 호출하나 | 모듈 관계도 | 격자 `node` + 방향 `edge`, 약한 참조는 `dashed=True` |
| 상태가 어떻게 바뀌나 | 상태도 | `node` 격자 + 라벨 있는 `edge`, 양방향은 `both=True` |
| 데이터가 어디서 오나 | 데이터 흐름도 | `kind="data"` 노드, 외부 의존은 `kind="external"` |

색 의미는 문서 안에서 고정한다: primary=핵심 주체, data=데이터·에셋, external=외부·참조, warn=위험·미확인, muted=보조. 범례가 필요하면 `d.text`로 한 줄 적는다.

## 그림 설명 (필수)
모든 도식에는 바로 아래 **그림 설명**을 단다. `sections`의 4번째 항목이며 없으면 실행 시 `WARN`이 나온다.
- 무엇을 보여 주는가 1문장 + **어떻게 읽는가**(시작점, 화살표 방향, 실선·점선·번호의 뜻) 1~2문장.
- 도식에서 가장 중요한 한 곳을 짚는다("핵심은 …").
- 색 범례는 사용된 노드 종류에 맞춰 자동으로 붙는다. 이 문서에서 색 의미가 기본과 다르면 `html_page(..., legend={"primary": "..."})`로 바꾼다.
- 그림 번호("그림 N.")는 자동이다. 본문에서 "그림 2"처럼 참조할 수 있다.

## 시각 구성 (읽기 쉽고 예쁘게)
문서를 글 덩어리로 두지 말고 아래 컴포넌트로 나눠 담는다. 모두 `scripts/dockit.py`에 있고 HTML 문자열을 돌려주므로 `Section.body`에 이어 붙인다.

| 말하려는 것 | 컴포넌트 |
|---|---|
| 결론·핵심 수치 | `callout("ok", 제목, 본문)`, `stats([(값, 라벨), ...])` |
| 항목 3~4개 병렬 소개 | `grid(3, card(제목, 본문, label="STAGE 1", kind="accent"), ...)` |
| 문제 → 개선 | `compare("현재", ... , "개선", ...)` + `chips([...], "bad"/"ok")` |
| 순서·로드맵 | `steps([(제목, 설명, "P0"), ...])` |
| 구조·흐름 | `Section(..., diagram=Diagram, caption=...)` |
| 표·색 샘플·코드 | `table(헤더, 행)`, `swatches([(색, 이름, 용도)])`, `code(텍스트)` |
| 경고·미확인 | `callout("warn", ...)`, `chip("미확인", "warn")` |

- 문서 맨 위에는 `tag`(DESIGN·GUIDE 등)와 `meta`(작성일·검증 범위 칩)를 단다. 검증 범위("코드 대조 완료", "게임 실행 없음")를 칩으로 먼저 보여 준다.
- 섹션마다 `sub`(부제 한 줄)를 달면 목차 칩과 번호 헤더가 읽기 안내 역할을 한다.
- 한 섹션에는 컴포넌트를 2~3종류까지만 섞는다. 카드·칩을 남발하면 오히려 읽기 어렵다.
- 색 의미는 의미 있는 곳에만 쓴다: accent=핵심, ok=개선·확인됨, warn=주의·미확인, bad=문제.

## 문서 구성 (`html_page`의 sections)
1. **한 줄 요약**(`lead`) — 결론부터. 전문용어 없이 한 문장.
2. **전체 그림** — 가장 큰 도식 1개와 "읽는 법" 2~3문장.
3. **부분별 설명** — 도식마다 바로 위 문단에 "무엇을 보여 주는가", 아래에 "핵심은 ○○"를 쓴다.
4. **용어 표** — 처음 나오는 용어·약어를 표로 정리한다.
5. **한계·미확인** — 확인하지 못한 것, 현재 구현과 다른 점.

## 글쓰기 규칙
- 본문은 한국어 구어체에 가까운 평서문. 한 문단 3문장 이하. 도식에 이미 보이는 내용을 문장으로 반복하지 않고 **왜 그렇게 나뉘었는지**를 쓴다.
- 도식 라벨은 짧게(노드 라벨 12자 이내, 보조 설명 20자 이내). 클래스명은 영어 그대로, 설명은 한국어.
- 코드에서 확인한 사실에는 `파일경로:줄`을 `<code>`로 달아 근거를 남긴다.
- 설계 예시나 계획을 구현 완료처럼 쓰지 않는다. "현재 구현"과 "계획"을 도식에서 색으로 구분한다(계획=`external`).

## svgkit API 요약 (`scripts/svgkit.py`)
- `Diagram(w, h, title)` → `.group(label,x,y,w,h,kind="a|b|c|d")`, `.node(id,x,y,w,h,label,sub,kind,badge)`, `.edge(a,b,label,dashed,both,a_side,b_side,via)`, `.note(x,y,text)`, `.text(x,y,s)`, `.check()`, `.save_svg(path)`
- `html_page(title, lead, [Section(...), ...], out, legend=None, theme="dark", tag="", meta=None, toc=True)` (`dockit.py`, `svgkit`에서도 import 가능) — 히어로·목차 칩·번호 섹션·그림 번호·그림 설명·색 범례 포함. 예전 튜플 `(제목, 본문, Diagram, 설명)`도 받는다.
- `Section(title, body="", diagram=None, caption="", sub="")` — 도식이 있으면 `caption` 필수(없으면 `WARN`).
- `Diagram.to_svg(theme=None|"light"|"dark", transparent=False)` — 단독 SVG 파일은 시스템 테마를 따르고, HTML 안에서는 페이지 테마와 투명 배경으로 들어간다.
- 엣지는 상대 위치로 변을 고르는 직교선이다. 모양이 어색하면 `a_side`/`b_side`(`l r t b`)로 변을 지정한다. 세로 선의 라벨은 선 오른쪽에 붙는다.
- 한글 폭은 추정치이므로 노드 폭은 라벨 글자 수 × 14px + 20px 이상으로 잡는다.

## 흔한 실패
- 한 도식에 모든 것을 넣어 화살표가 교차한다 → 도식을 나눈다.
- 라벨이 짧은 엣지 위에서 노드를 덮는다 → 노드 간격을 넓힌다(`check()` 경고).
- 클래스 이름만 나열한 박스 그림 → 각 노드에 "무슨 책임인지" `sub`를 단다.
- 그림만 있고 설명이 없다 → 4번째 항목(그림 설명)을 쓴다.
- 카드·칩·콜아웃을 한 섹션에 모두 쓴다 → 섹션당 2~3종류만 쓴다.
- 렌더 확인 없이 완료 보고 → 반드시 PNG를 보고 확인한다. 다크·라이트를 둘 다 쓰는 문서는 두 테마를 각각 캡처한다.
