# RiverBasin4km 지면 식생 — 레퍼런스 격차 해소 설계

상태: **Opus 검증 반영본 (조건부 타당 → 수정 반영, 사용자 확인 대기)**. 구현 전. 2026-11-22.
범위: RiverBasin4km 서부 가을 숲(X 440~1450 / Z 1600~2900). 다른 지역에 확장하기 전에 한 구간에서만 검증한다.

## 1. 목적

레퍼런스(Ghost of Tsushima 풍 초원·숲: 지면 전체를 덮는 긴 풀, 바람에 한 방향으로 쓸리는 결, 청록 그림자, 성근 줄기 사이의 열린 풀밭)와 현재 숲 화면이 크게 다르다. 원인 5가지를 정리하고, **성능 예산을 늘리지 않는 순서**로 격차를 줄인다.

완료 기준은 "풀 개수가 늘었다"가 아니라 **같은 구도 비교 캡처에서 풀 사이 바닥이 비어 보이지 않고, 바람 결이 읽히며, 숲의 풀밭 구간이 시선을 끈다**는 것이다. 미술 판정은 사용자 확인이다.

## 2. 원인 진단 (근거 구분)

| # | 원인 | 근거 수준 |
|---|---|---|
| C1 | 밝은 단색 지표 위에 풀 포기가 점점이 놓여 포기 사이 바닥이 드러난다 | 위키 기록 + 저장 캡처(`Tools/RiverBasinWorld/Rebuild/GrassCompare/`). 실제 지표 TerrainLayer 속성은 Phase 0에서 측정 |
| C2 | 풀 바람이 결을 만들지 못한다. 현재 풀 셰이더(`Environment/Vegetation/4fb6b416…shader`)는 `_LW_Wind`를 읽지 않고, 노이즈 텍스처 RGB를 오브젝트 공간 오프셋으로 더하며 스크롤 방향이 UV(0,0.2) 고정이라 방향성이 없다. 재질의 `_Wind_Large/Small_*`는 셰이더에 없는 잔존 속성이고 실제 값은 `_WindNoise01/02Multiplier` 0.2, Size 12다. (풀 종류는 이미 11종이며 키 큰 풀·억새 포함이라 "짧은 3종"은 낡은 서술) | 셰이더·재질 확인(Opus 검증 + `_LW_Wind` 미참조 직접 확인). 시각 영향은 추정 |
| C1b | 풀 셰이더가 지형 알베도를 샘플하지 않는다. 밑동 색은 `_ColorBottom`과 오브젝트 높이로만 정해져 지표와 이어지지 않는다. 디더링(`_DitherBottomLevel`, `_DitherFade`)이 밑동을 깎아 바닥 노출을 키울 가능성 | 셰이더 확인(샘플 없음). 디더 영향은 추정 |
| C3 | 수관 피복 55%의 꽉 찬 숲이라 풀이 주인공이 될 공간이 없다. 풀은 수관 아래에서 의도적으로 성기게 배치됨 | 위키 기록(배치 규칙) |
| C4 | 색·그림자 톤: 균일한 황록색, 얕은 그림자. 툰 안개의 식생 연동은 검증 미완 | 캡처 + 위키 상태. 식생 연동 효과는 추정 |
| C5 | 성능 예산: 식생을 모두 꺼도 CPU가 16.7ms 근처, 풀 90m/밀도 100%가 기준값 | 위키 계측(Editor, 신뢰도 낮음) |

C1·C2·C4의 시각 기여도는 실측으로 분리한 적이 없다. Phase 0에서 한 요인씩 바꿔 기여도를 확인한 뒤 우선순위를 확정한다.

## 3. 원칙

- 구매 원본 재질·TerrainLayer를 수정하지 않는다. 프로젝트 소유 복제본에만 적용한다 (WorldToon 통합 계약 §1·§6, AGENTS 규칙 5).
- 새 바람 입력을 만들지 않는다. WorldToon 계약상 바람은 `EnvironmentShaderState`의 `_LW_Wind/_LW_PreviousWind`만 읽는다. **현재 풀 셰이더는 이 값을 읽지 않으므로** 바람결을 만들려면 셰이더 수정이 필요하며(Phase 2), 수정은 원본 `Foliage/UPG_Grass.shader`에서 하고 반응형 파생 셰이더는 `VegetationReactionShaderAuthoring.Generate`로 재생성한다. 파생 파일은 직접 고치지 않는다. 접촉 변위(`UPG_FoliageInteraction.hlsl`)·`VegetationReaction.hlsl` 계약은 유지한다.
- 지형 TerrainData·WorldBuilder 타일(`Production/Layers/*.terrainlayer` 포함)은 읽기 전용이다. 레이어 배열 교체는 TerrainData 수정이므로 **검증 씬 복제 지형에서만** 하고, 제작 반영은 사용자 승인 후에 한다.
- 수치(풀 높이·밀도·색)는 SO·재질 데이터로 둔다. 구역 이름으로 분기하지 않는다.
- 성능 예산을 늘리지 않는다. 밀도를 올리는 구간은 다른 곳에서 같은 양을 회수한다.
- Player·Addressables 빌드는 별도 지시 전 `사용자 지시 대기`.

## 4. 작업 단계

각 단계는 같은 위치·같은 카메라(자세·화각 고정)의 전/후 캡처와 Console 오류 0건을 근거로 남기고, 위키·work-status를 갱신한 뒤 다음으로 간다.

### Phase 0 — 기준선과 기여도 측정 (코드 변경 없음)
- 비교 구도 3곳(숲 안, 능선, 공터)의 카메라 자세를 저장한다. 레퍼런스와 같은 구도(낮은 시점, 열린 풀밭 + 멀리 성근 나무)를 공터에 1곳 추가한다.
- 숲 지표 TerrainLayer의 알베도·평균색·smoothness·타일링과 지표/풀 밑동 색 차이를 읽는다.
- 기록할 조건: 기존 캡처가 Scene 뷰인지 Game 뷰인지, 노출·후처리 동일 여부. 이후 캡처는 Game 뷰 기준으로 통일한다.
- 이미 알려진 사실: `Forest.terrainlayer`/`Meadow.terrainlayer`의 DiffuseRemapMax는 (0.3,0.43,0.66)/(0.34,0.56,0.8)로 레이어 쪽에서 이미 어둡게 보정돼 있다. 그런데도 화면이 밝으므로 **알베도 원본 텍스처, 숲 구간 스플랫 지배 레이어, 라이팅·후처리 중 어디가 원인인지**를 먼저 분리한다. 숲 타일별 실제 레이어 수와 지형 재질이 URP TerrainLit인지도 측정한다.
- 요인 분리 캡처(한 번에 한 요인): ① 지표 알베도/지배 레이어 ② 풀 디더링 끄기 ③ 풀 표시 거리(위키 90m, 검증 씬 일부 타일 80m) ④ 후처리 끄기 ⑤ 노이즈 바람 배수 상향. 어느 요인이 레퍼런스에 가까워지는지 사용자에게 보여 우선순위를 확정한다.
- 비용 기준선: 현재 풀 인스턴스·draw call·CPU/GPU 프레임 (Editor 계측은 참고값. 판정은 Player 계측 대기).

### Phase 1 — 지표 재질 보정 (C1)
- 숲 지표용 TerrainLayer 복제본을 만든다. 풀 사이 바닥에 보이는 색은 풀 밑동보다 어둡고 채도가 낮은 흙·이끼·낙엽 톤으로 하고, 저주파 변화를 준다.
- **결정 항목:** 풀 셰이더는 지형 알베도를 샘플하지 않는다(확인됨). ① 지표와 `_ColorBottom`을 수동으로 맞춘다(기본안, 구역별 재질 복제본) ② 셰이더에 지형 알베도 샘플 기능을 추가한다(Phase 0 결과에서 ①로 부족할 때만, 원본 `UPG_Grass` 수정 + 반응형 파생 재생성).
- 기존 가을 풀의 밑동 밝히기 보정(어두운 포기가 구멍처럼 보였던 이력)과 충돌하지 않게 밑동 밝기를 지표와 함께 재조정한다.
- 레이어 교체는 **검증 씬의 복제 지형에서 기존 URP TerrainLit 레이어로만** 시험한다. 제작 지형 반영은 사용자 승인 후. "4레이어 이하" 같은 수치는 타일별 실측 후에만 문서에 쓴다.

### Phase 2 — 풀 메시·바람 결 (C2)
- 새 에셋을 찾기 전에 기존 `FW_MI_Grass_Tall_Autumn`·억새의 스케일·비율·밑동 그라데이션 조정부터 시험한다. 부족할 때만 카탈로그(`plant.html`)에서 길고 가는 블레이드 클러스터를 고른다. 높이 0.5~0.9m 범위.
- 바람: 현재 셰이더의 방향 없는 노이즈 오프셋을 `_LW_Wind` 기반의 방향성 휨(바람 방향으로 기울고 끝이 더 흔들림)으로 바꾼다. 셰이더 수정이며 §3의 재생성 절차를 따른다. 접촉 변위와 합산되어 이중 움직임이 되지 않는지 확인한다.
- 키 큰 풀은 인스턴스가 늘기 쉬우므로 지형 셀당 상한을 두고 수관 아래에서는 제한한다.
- 접촉 변위·반응형 불·물 계약을 회귀 확인한다(밟기·불 반응 동작).

### Phase 3 — 열린 풀밭 구간 (C3)
- 서부 숲 안에서 **한 곳**만 후보로 골라 수관 피복을 약 20~30%로 낮추는 열린 풀밭 구간을 만든다. 풀은 이미 별도 스크립트(`forest-west-grass.cs.txt`)로 분리돼 있고 나무 배치 스크립트의 옛 풀 코드는 실행되지 않는다. 더 큰 위험은 **나무 재배치로 TreeInstance 인덱스가 바뀌어 벌목·밑동 반응 원장이 어긋나는 것**이다. 나무를 재배치하지 말고 해당 구간의 나무만 비활성·제거하는 최소 변경을 먼저 검토하며, 기존 원장 ID 보존 방식(같은 위치·수종 ID 승계, `RiverBasinTerrainTreeAuthoring.Apply()`)을 따른다.
- 그 구간에서만 풀 밀도·높이를 올린다. 올린 만큼 인접 숲 구간의 풀 표시 거리·밀도를 줄여 총량을 유지한다.
- 레퍼런스처럼 성근 줄기 사이의 시야가 열리는지, 길 가독성·퀘스트 동선이 유지되는지 확인한다. 이 구간이 플레이 경험에서 휴식·전망 역할을 하는지는 디자이너 판단으로 별도 확인한다.

### Phase 4 — 색·그림자 톤 (C4)
- 툰 안개·후처리 프리셋에서 식생에 영향을 주는 값(그림자 색 틴트, 거리 팔레트)만 비교한다. 식생 셰이더 자체의 조명은 건드리지 않는다.
- 연동 검증이 미완이므로, 이 단계는 Phase 1~3 결과를 본 뒤 필요할 때만 진행한다.

## 5. 성능 계획 (C5)

| 항목 | 방침 |
|---|---|
| 총량 | 기준선 대비 풀 **인스턴스 수** 증가 0을 목표로 하고 증가분은 다른 구간에서 회수한다. draw call은 프로토타입이 3→11종으로 이미 늘었을 수 있어 Phase 0 실측값을 기준선으로 별도 상한을 정한다. InstanceCountMode의 셀당 상한과 레퍼런스급 밀도 달성 가능성은 미측정 |
| 병목 | 식생을 모두 꺼도 CPU가 높은 원인(나무 4,400여 그루 외)은 이 작업의 범위가 아니다. 분리해 보고만 한다 |
| 계측 | Editor 값은 참고용. 목표 판정은 Player 계측이며 `사용자 지시 대기` |

## 6. 위험과 완화

| 위험 | 완화 |
|---|---|
| 지표를 어둡게 하면 숲 전체가 칙칙해짐 | Phase 0 요인 분리 캡처로 정도를 정하고 구역(숲/공터) 구분은 데이터 마스크로 |
| 긴 풀이 근접 카메라·캐릭터를 가림 | 높이 상한과 플레이어 주변 감쇠를 확인하고 TPS 구도 캡처 |
| 바람 진폭 상향 시 반응형 변위와 이중 움직임 | 바람은 `_LW_Wind` 단일 입력만 사용 |
| 열린 풀밭이 길 가독성·동선을 해침 | 길 중심 비움 규칙 유지, 순환로·사당길 4m 침범 0 재검사 |
| 나무 재배치로 TreeInstance 인덱스가 바뀌어 벌목·반응 원장이 어긋남, 파일럿 경계 훼손 | 복제 씬에서 먼저 실행, 원본 보존, 기존 ID 승계 도구 사용, 파일럿 경계 규칙 유지 |
| 셰이더 원본 수정 후 반응형 파생이 어긋남 | 원본만 수정, 파생은 `VegetationReactionShaderAuthoring.Generate`로 재생성, 반응형 환경 테스트 회귀 |

## 7. 검증

- 자동: Console 오류 0, 누락 프리팹·재질 참조 0, 길·수면·부지 침범 0, 반응형 식생 환경 테스트 회귀(해당 EditMode 슈트).
- 시각: 같은 구도 전/후 캡처 세트(숲 안·능선·공터·레퍼런스형 구도). 자동 캡처까지만 확인하고 미술 품질은 `사용자 테스트 대기`.
- 성능: Editor 계측은 참고, Player 계측은 `사용자 지시 대기`.

## 8. 비범위

- 나무 모델·수관 질감 교체, 지형 조형, 다른 지역 확장
- Terrain4·WorldToon 도입 결정(별도 보류 상태 유지)
- 풀 렌더링 방식 교체(GPU 인스턴싱 풀 시스템 신규 도입). 필요성은 Phase 2 결과를 본 뒤 별도 설계

## 9. 검증 이력

- 2026-11-22 Opus 검토: **조건부 타당.** 진단 방향(지표·풀·수관·톤)은 맞고, 두 기술 전제가 실제 코드와 달라 수정했다. ① 풀 셰이더는 `_LW_Wind`를 읽지 않음(직접 재확인) → 바람결은 셰이더 수정 작업으로 재정의 ② 풀 셰이더는 지형 알베도를 샘플하지 않음 → 결정 항목화. 추가 반영: 레이어가 이미 어둡게 보정돼 있어 원인 위치 분리를 Phase 0으로, 읽기 전용 규칙과 레이어 교체 범위 명시, 나무 재배치 원장 위험, draw call 별도 상한, 캡처 뷰 통일. 규칙 위반은 없음.
- 직접 확인하지 못한 항목: 지형 재질의 TerrainLit 여부, 타일별 레이어 수·스플랫 지배 레이어, 지표 알베도 실제 밝기, 기존 캡처의 뷰 종류, 디더링의 시각 영향, InstanceCountMode 한계. 모두 Phase 0 측정 대상.
