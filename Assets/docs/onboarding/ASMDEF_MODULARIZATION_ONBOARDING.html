10분 빠른 시작

처음 참여했다면 아래 다섯 가지만 먼저 기억하면 대부분의 경계 오류를 피할 수 있습니다.

1

데이터는 아래로만

UPlayGround.Data는 SO, DTO, enum 같은 순수 데이터입니다. 런타임 매니저·Actor·UI 타입을 참조하지 않습니다.

2

구체 매니저 대신 계약

UI와 하위 모듈에서는 SomeManager.Instance를 새로 만들지 않습니다. Svc.Xxx 또는 UISvc.Xxx를 사용합니다.

3

Editor는 별도 asmdef

UnityEditor, 커스텀 인스펙터, 프리팹 빌더는 반드시 Editor 전용 폴더와 asmdef 아래에 둡니다.

4

Awake 접근을 경계

Services.Get은 자동 생성하지 않습니다. GameManager 등록 전에 호출하면 null이며 최초 1회 경고가 출력됩니다.

5

SerializeReference는 이동 금지 수준으로 조심

MotionEvent·Ultimate 이벤트 타입 이동 시 MovedFrom 없이 저장하면 이벤트와 VFX 연결이 유실될 수 있습니다.

✓

끝은 Player Build

Editor 컴파일 성공만으로 끝내지 않습니다. Missing Script, managed reference, VFX 참조와 Player Build를 함께 확인합니다.

BOUNDARY POLICY

의존성 규칙

해야 하는 것

  • 공유 계약은 Contracts에 둔다.
  • 한 소비자만 필요한 계약은 소비자 모듈이 소유한다.
  • UI는 Svc와 UISvc로 기능을 요청한다.
  • 기능 전용 UI는 기능 폴더가 소유하고 UI 기반 타입만 참조한다.
  • asmdef references는 실제 using/type 사용을 근거로 추가한다.

하지 말아야 하는 것

  • 컴파일 오류를 없애기 위해 무작정 Assembly-CSharp 타입을 옮긴다.
  • UI에서 PartyManager.Instance 같은 직접 접근을 추가한다.
  • Data에 MonoBehaviour 런타임 구현을 넣는다.
  • 서비스가 null일 때 FindFirstObjectByType로 우회한다.
  • Editor 폴더 없이 UnityEditor using을 추가한다.
기존 코드와 신규 정책을 구분하세요. Actor 모듈에는 Camera 모듈 타입을 직접 사용하는 기존 코드가 있습니다. asmdef가 허용하는 모듈 간 직접 참조 자체는 유효하지만, 새로운 상위 Manager 의존을 추가하는 근거로 사용하면 안 됩니다.
RUNTIME SERVICES

서비스 레지스트리 동작

Services는 구체 매니저를 하위 모듈에 노출하지 않기 위한 런타임 레지스트리입니다. GameManager가 매니저를 등록할 때 구현된 모든 IGameService 인터페이스가 자동 바인딩됩니다.

Svc / UISvc 조회

Svc

여러 런타임 모듈이 공유하는 공용 계약입니다.

Svc.Input, Svc.Asset, Svc.GameTime, Svc.Camera, Svc.Events, Svc.Sound 등.

UISvc

UI가 실제로 소비하는 표면만 노출하는 UI 소유 계약입니다.

UISvc.Party, UISvc.Inventory, UISvc.Quest, UISvc.Scene, UISvc.UI 등.

조회 예시

// 공용 런타임 서비스
var input = Svc.Input;
input?.ShowCursor(true);

// UI 소비자 전용 서비스
var inventory = UISvc.Inventory;
if (inventory != null && inventory.HasItem(itemId))
{
    inventory.TryUseItem(itemId);
}
초기화 타이밍: Services.Get<T>()은 BaseManager.Instance처럼 객체를 자동 생성하지 않습니다. GameManager 등록 전 필드 초기화나 이른 Awake에서 접근하면 null이며 [Services] 등록되지 않은 서비스 계약 요청 경고가 최초 1회 발생합니다.
HOW TO EXTEND

새 서비스 추가 방법

구현을 옮기기 전에 소비자가 정말 필요한 최소 API부터 계약으로 정의합니다.

1

계약 위치 결정

Camera·Actor·UI 등 여러 모듈이 쓰면 Contracts. UI만 쓰면 UI/Contracts처럼 소비자 모듈에 둡니다.

2

최소 표면 선언

구체 Manager 전체 API를 복사하지 말고 현재 소비 코드가 요구하는 이벤트·프로퍼티·메서드만 선언합니다.

3

Manager가 구현

Assembly-CSharp에 남은 Manager가 인터페이스를 구현합니다. GameManager 등록 코드는 추가할 필요가 없습니다.

4

접근점과 검증

Svc 또는 UISvc getter를 추가하고 직접 싱글톤 호출을 치환한 뒤 Play Mode 경고를 확인합니다.

// 1) 소비자 또는 Contracts 모듈
public interface IExampleService : IGameService
{
    bool IsReady { get; }
    void Execute(string key);
}

// 2) Assembly-CSharp의 구체 매니저
public sealed class ExampleManager :
    BaseManager<ExampleManager>, IManager, IExampleService
{
    public bool IsReady => _isReady;
    public void Execute(string key) { /* 구현 */ }
}

// 3) 단축 접근점
public static IExampleService Example =>
    Services.Get<IExampleService>();
자동 등록 조건: Manager 인스턴스가 IGameService를 상속한 인터페이스를 구현하고 기존 GameManager.RegisterManager 경로로 등록되면 해당 계약은 자동으로 레지스트리에 들어갑니다.

DATA SAFETY

SerializeReference와 에셋 안전

MotionSet과 Ultimate 이벤트는 구체 타입 정보를 어셈블리 이름까지 포함해 저장합니다. 클래스 이름과 네임스페이스가 같아도 어셈블리가 바뀌면 Unity 입장에서는 다른 타입입니다.

실제 장애 사례: MotionEvent 타입이 Assembly-CSharp에서 UPlayGround.Actor로 이동한 뒤 매핑이 없으면 이벤트가 Unknown/null이 되고, 그 안의 Particle/VFX 오브젝트 참조도 사라진 것처럼 보일 수 있습니다.

필수 매핑

using System;
using UnityEngine.Scripting.APIUpdating;

[Serializable]
[MovedFrom(true, sourceAssembly: "Assembly-CSharp")]
public sealed class SlashVFXEvent : MotionEvent
{
    // 기존 직렬화 필드 이름과 타입도 유지
}

이동 전

  • [SerializeReference] 하위 타입 목록 수집
  • 원래 assembly / namespace / class 기록
  • MotionSet·Ultimate 대표 에셋 백업
  • 에셋 diff가 깨끗한지 확인

이동 후

  • 모든 구체 타입에 MovedFrom 적용
  • managed reference null/Unknown 0건 확인
  • particlePrefab, vfxPrefab null 0건 확인
  • 검증 중 자동 재직렬화된 에셋 diff 확인
금지: 타입 오류가 있는 상태에서 MotionSet/Ultimate 에셋을 열고 저장하거나, 전체 에셋을 일괄 재직렬화하지 마세요. 먼저 컴파일과 타입 매핑을 복구해야 합니다.
DECISION TREE

새 파일은 어디에 둘까?

  1. SO, DTO, enum, 순수 계산인가? → Data
  2. 여러 모듈이 구현과 분리해 써야 하는 계약인가? → Contracts
  3. 카메라 모드·효과·락온 구현인가? → Camera
  4. GameActor, 전투, 상태, AI, MotionEvent인가? → GameActor
  5. 일반 UI 런타임인가? → UI
  6. 사이클 등 특정 기능 구현에 결합된 UI인가? → 해당 기능의 UI 하위 폴더
  7. UnityEditor API를 사용하는가? → 참조 대상에 따라 모듈 Editor 또는 전역 02.Scripts/Editor
폴더를 정한 다음 “그 폴더의 asmdef references만으로 컴파일 가능한가?”를 확인하세요. 불가능하다면 references를 늘리기 전에 파일 소유권이나 서비스 계약이 잘못된 것은 아닌지 먼저 검토합니다.
TROUBLESHOOTING

자주 만나는 오류 진단

CS0246 — 타입 또는 네임스페이스를 찾을 수 없음
먼저 타입 정의가 어느 asmdef에 포함되는지 확인합니다. 소비 모듈의 asmdef reference가 정당한지, 타입이 잘못된 모듈에 놓였는지, Editor 타입이 런타임에 섞였는지 순서대로 봅니다. 단순히 using만 추가해서 해결되지 않는 경우가 대부분입니다.
CS0535 / CS0738 — 서비스 인터페이스 구현 불일치
계약의 반환 타입, 이벤트 제네릭 타입, nullable/오버로드가 구체 Manager의 public API와 정확히 같은지 확인합니다. 필요하면 명시적 인터페이스 구현으로 구체 API 노출을 제한합니다.
[Services] 등록되지 않은 서비스 계약 요청
Manager가 해당 IGameService 인터페이스를 구현하는지, GameManager에 등록되는 타입인지, 조회 시점이 등록 이전인지 확인합니다. Awake 필드 캐시보다 OnShow/Init 이후 지연 조회를 우선합니다.
Missing Prefab / Missing Script
이동한 파일의 .meta가 함께 이동했는지 확인합니다. 프리팹에 기록된 GUID를 프로젝트의 meta에서 찾고, GUID를 새로 만들거나 프리팹 YAML을 임의 삭제하지 않습니다.
MotionEvent는 보이지만 VFX가 null
디스크 YAML의 GUID 존재 여부와 Unity 메모리 역직렬화 결과를 구분해 확인합니다. MovedFrom 적용 후 에셋을 unload/reimport하고 object reference null 수를 검증합니다.
Burst의 Failed to resolve assembly
대개 선행 C# 컴파일 실패 때문에 대상 DLL이 생성되지 않은 2차 오류입니다. Burst 스택보다 먼저 출력된 첫 번째 CS 오류를 해결합니다.
