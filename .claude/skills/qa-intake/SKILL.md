# QA Intake (버그 제보·플레이 소감 접수)

사용자가 직접 플레이하고 보낸 결과를 수정 작업 전에 구조화한다. 규칙 원문은 [테스트 작업 지침 「명세 밖 결과 접수」](../../../Assets/docs/guide/TEST_VALIDATION_GUIDE.md)에 있고, 이 스킬은 실행 순서만 담는다.

## 절차

1. **원문 보존:** 사용자 문장을 요약하기 전에 그대로 인용해 둔다. 추정을 사실처럼 바꿔 쓰지 않는다.
2. **항목 분리:** 결함과 체감 의견을 나누고 항목마다 ID를 붙인다(예: 기능 상태 문서의 기존 ID 규칙을 따르고, 없으면 `BUG-<작업명>-01`·`FEEL-<작업명>-01`).
3. **결함 정리:** 지침의 기록 항목(재현 절차, 빈도, 회귀 여부, 캐릭터·무기·씬·저장 슬롯·입력 장치, 기대/실제)과 S1~S4 심각도를 채운다. 빠진 정보는 원인 조사에 꼭 필요한 것만 한 번에 묶어 되묻는다.
4. **위치 찾기:** [작업 위키](../../../docs/wiki/README.md)에서 해당 분야와 상태 문서를 찾고 실제 코드·데이터와 대조한다. 로그가 필요하면 열린 Editor의 Console을 Unity MCP `read_console`로 읽는다(두 번째 Editor 금지, Play Mode·테스트 실행은 Unity 슬롯이 있을 때만).
5. **체감 의견 분류:** SO 수치 조정 후보 / 설계 검토(디자이너 역할) / 연출·UI 다듬기로 나눈다. 액터·스테이지 이름 분기를 해법으로 제시하지 않는다. 설계 의도와 충돌하면 근거를 붙여 되묻는다.
6. **기록:** 관련 `docs/work-status/` 상태 문서에 항목·심각도·현재 상태(`실패`·`사용자 테스트 대기` 등)를 남기고 분야 위키 요약을 갱신한다. 새 버그 폴더를 만들지 않는다.
7. **수정 후:** 원래 재현 절차를 재검증 명세로 돌려준다. 사용자 결과 전에는 `사용자 테스트 대기`이며, 코드 수정·자동 검사 통과만으로 해결 보고하지 않는다.

## 사용자에게 돌려줄 정리 형식

```text
[결함] ID / S1~S4 / 증상 한 줄 / 재현: 빈도·회귀 / 확인 필요 정보 / 다음 행동
[체감] ID / 의견 요약 / 분류(SO 수치·설계·연출) / 근거 데이터·문서 / 다음 행동
```

출처: 결함·체감 분리와 수정 후 재현 확인 관점은 Donchitos/Claude-Code-Game-Studios(MIT)의 bug-report·playtest-report 스킬을 참고해 이 프로젝트 규칙에 맞게 새로 썼다.
