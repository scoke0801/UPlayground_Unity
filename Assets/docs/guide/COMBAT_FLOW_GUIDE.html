전투 런타임 플로우 가이드

버튼을 누른 순간부터 데미지 숫자가 뜨고 카메라가 흔들릴 때까지, 코드가 실제로 지나가는 경로를 순서대로 기술한다.

0. 이 문서의 범위

전투 시스템 작업 지침이 무엇을 어디에 저작하는가(BT·GAS·MotionSet의 3계층 경계)를 정한다면, 이 문서는 그 데이터가 런타임에 어떤 순서로 실행되는가를 정리한다. 새 공격을 붙이다 막혔을 때 "지금 어느 단계에서 끊겼는지" 찾는 용도로 쓴다.

읽는 순서 1장의 흐름도에서 문제 구간을 특정하고 → 해당 장으로 내려가 그 구간의 진입점 함수와 소유 파일을 확인한다. 각 장 끝의 보라색 경로가 그 구간을 소유한 파일이다.

1. 전체 흐름 한 장

플레이어와 몬스터는 행동을 고르는 방식만 다르고(2~3장), 판정·피해·리액션·피드백(4~7장)은 같은 코드를 지난다. 아래에서 파란색은 공격자측, 붉은색은 피격자측 소유 구간이다.

1

입력 / 판단 공통

플레이어는 InputBuffer의 선입력을, 몬스터는 BT가 고른 EnemyActionRequest를 상태 전환 요청으로 만든다.

↓
2

행동 확정 플레이어=GAS몬스터=BT

플레이어는 TryPrepare… → Commit 2단계로 Ability를 확정하고, 몬스터는 EnemyActionResolver.TryTransition이 쿨다운·상태 락을 검사한 뒤 전환한다. 결과물은 양쪽 모두 AttackData 하나다.

↓
3

모션 재생 · 판정 개폐 MotionSet

MotionSetAsset 타임라인이 흐르면서 BeginCollisionEvent가 CombatActionRunner에 판정 시작/종료를 알린다. 언제 때리는가는 전부 여기가 소유한다.

↓
4

히트 검출 공격자

PerformHitDetection()이 활성 히트박스 그룹 또는 명시적 판정 형상으로 대상을 모은다. 프레임당 1회, 대상당 1회로 제한된다.

↓
5

피격 해석 피격자

IDamageable.ReceiveHit() → CombatResolutionPipeline.Execute(). 방어 → 피해 → 리액션 순으로 계산해 CombatResult 하나로 봉한다. 모든 피해의 단일 진입점이다.

↓
6

피드백 소유권 분리

데미지 숫자·히트 FX는 공격자가, 충돌음·햅틱·컬러 플래시는 피격자가 낸다. 히트스톱·카메라는 공격 1회당 1번만 실행된다.

↓
7

자원 갱신 · 기록 공통

Poise/Break 게이지, 스킬 게이지, VitalOrb 드롭, 페이즈 전환이 갱신되고 CombatLogRecorder가 결과를 기록한다.

2. 입력과 상태 진입

2.1 선입력과 캔슬

입력은 즉시 상태를 바꾸지 않는다. Svc.Input.InputBuffer에 쌓인 뒤, 현재 상태가 그 입력을 받아줄 수 있을 때 소비된다. 받아줄 수 있는지를 정하는 것이 PlayerInterruptAction 마스크다.

  • 공격 중 캔슬 — AttackData.interruptActions에 허용된 액션만 현재 공격을 끊는다.
  • 차지 중 캔슬 — PlayerCombat.GetChargeInterruptActions()가 홀드 중 탈출 가능한 액션을 돌려준다.
  • 콤보 윈도우 — OpenComboWindow()/CloseComboWindow()가 다음 타로 이어질 수 있는 구간을 연다. 윈도우 밖 입력은 캔슬 경로로 처리된다.
공격 상태는 전역 버퍼를 오래 붙들지 않는다 PlayerAttackState.CapturePendingAttackIntent()가 약/강 입력을 전역 버퍼에서 즉시 회수해 자기 소유의 단일 "다음 공격" 슬롯에 보관한다. 콤보 윈도우를 기다리며 전역 버퍼 만료를 멈추면 회피·가드 같은 다른 액션의 수명까지 함께 늘어나기 때문이다.

2.2 진입 시 결정되는 것

PlayerAttackState.OnEnter는 이 시점에 다음을 확정한다.

  • GameplayTags.State_Combat_Attack 부착
  • 강제 공격(_forcedAttackAction) 여부 — 직전 공격이 완료 경계에서 인계한 값. 버퍼 재해석으로 뒤집지 않는다(강공격이 약공격으로 변질됨)
  • 입장 공격(ConsumeEntryAttackPending), 카운터 공격, 콤보 리셋 여부

소유: GameActor/State/Player/PlayerAttackState.cs, GameActor/State/Player/PlayerInterruptResolver.cs, GameActor/Component/Player/PlayerCombat.Combo.cs

3. 행동 결정 — 플레이어(GAS)와 몬스터(BT)

3.1 플레이어 — Prepare / Commit 2단계

스킬은 곧바로 실행되지 않는다. 준비 → 검증 → 확정 순서를 거치며, 중간에 실패하면 Abort로 되돌린다. 비용·쿨다운을 먼저 깎고 나중에 모션이 없어 실패하는 사태를 막기 위한 구조다. 

AbilityActivationResult prepare = playerActor.Abilities.TryPrepareAbility(ability, grounded, …, out handle);
if (prepare != Success)            → 후보 탈락, 다음 우선순위로
if (모션 해석 실패)                 → Abilities.Abort(handle)
AbilityActivationResult commit = playerActor.Abilities.Commit(handle);
if (commit != Success)             → Abilities.Abort(handle)

공격 후보의 우선순위는 PlayerAttackState가 아래 순서로 평가한다.

  1. 강제 공격(forcedAttackAction) — 이전 상태가 확정해 넘긴 값
  2. 숫자 키 스킬 슬롯(PlayerSkillSlot) — GAS Prepare/Commit 경유
  3. 기본 약/강 콤보 — PlayerCombat.ExecuteAttack() / ExecuteHeavyAttack()

약·강 이중 콤보 체인

약 체인과 강 체인은 인덱스를 각각 보존한다(_normalComboIndex, _heavyComboIndex). 전환 시 ResetCombo()를 부르면 반대편 체인이 날아가므로, 대신 _comboController.CloseWindow()로 stale 윈도우만 닫고 인덱스를 복원한다. 태그도 Combo_Light/Combo_Heavy가 상호 배타적으로 직접 교체된다.

차지 공격

ExecuteChargeAttack(stageIndex, chargeRatio). 단계별 임계값은 chargeStageThresholds가 있으면 그 값을, 없으면 단계 수로 균등 분할한 값을 쓴다. 최종 피해는 단계 데이터에 Lerp(1.0, 1.5, chargeRatio)를 곱한다. 차지 릴리즈는 별도 상태이므로 연계 라우트용 ComboInputToken.Charge를 여기서 직접 push한다.

3.2 몬스터 — BT가 고르고 Resolver가 검증한다

BT의 RequestEnemyActionNode가 EnemyActionRequest(Intent · Style · CooldownId)를 만들고, EnemyActionResolver.TryTransition()이 아래를 순서대로 검사한 뒤에야 상태를 바꾼다.

검사실패 시
ActorMovementController 존재"ActorMovementController가 없습니다."
IsCooldownReady(cooldownId)쿨다운 미준비 — 해당 Intent 탈락
CreateState() 해석Intent·Style을 상태로 옮길 수 없음
IsTransitionBlockedByActionLock()현재 상태가 액션 락 중
controller.TryTransitionToState()상태 자신의 전환 조건 불통과
BT가 골랐다고 실행된 것이 아니다 위 5단계 중 하나만 막혀도 조용히 실패한다. "BT는 공격을 고르는데 몬스터가 안 움직인다"의 원인은 대부분 cooldownId 불일치 또는 상태측 CanTransitionState 거부다. failureReason 문자열을 먼저 확인한다.

소유: GameActor/Gameplay/Ability/ActorAbilitySystem.cs, GameActor/AI/BehaviorTree/Runtime/EnemyActionResolver.cs, …/RequestEnemyActionNode.cs

4. 모션 재생과 판정 개폐

공격이 확정되면 AttackData.motionAsset의 타임라인이 재생되고, 그 위에 얹힌 MotionEvent가 판정을 켠다. 이 구간에는 수치가 없다. 모션은 "언제"만 소유한다.

4.1 판정 소스는 두 종류다 — 그리고 배타적이다

CollisionSourceType의미용도
AttachedHitboxGroup무기·신체에 부착된 CombatHitbox를 groupId로 켠다일반 근접 타격(기본값)
ExplicitShape이벤트가 직접 소유한 판정 형상을 그 자리에서 만든다폭발·충격파·광역 지면 타격
명시적 세션이 열려 있으면 부착형 그룹은 질의하지 않는다 PerformHitDetection()은 _collisionSession.ShouldDetect()가 참이면 부착형 히트박스를 아예 보지 않는다. 두 소스를 섞어 쓰면 같은 타격이 두 번 커밋된다.

4.2 평가 방식

  • Window — 판정 구간 동안 매 프레임 검출(스윕). 종료 이벤트까지 유지된다.
  • OnceOnBegin — 시작 시점 1회로 끝. MarkConsumed() 후 다시 질의하지 않는다. 이 경우 RequiresPostEvaluation이 켜져 그 프레임의 최종 본 포즈로 형상을 샘플링한다.

4.3 HitPhase 인덱스 동기화

멀티 히트 공격은 구간마다 다른 수치를 쓴다. BeginCollisionEvent.hitPhaseIndex가 CombatActionRunner.CurrentPhaseIndex를 갱신하고, 검출 직전에 _currentAttackData.hitPhaseIndex가 여기에 맞춰 SetHitPhaseIndex()로 재동기화된다.

소유: GameActor/Animation/MotionEvents/MotionEvent_Collision.cs, GameActor/Combat/Action/CombatActionRunner.cs, GameActor/Combat/Detection/CombatCollisionSession.cs, …/CombatHitboxSet.cs

5. 히트 검출

PlayerCombat.PerformHitDetection()이 공격자측 마지막 단계다. 두 겹의 중복 방지가 걸려 있다.

가드막는 것이유
_lastHitDetectionFrame == Time.frameCount 같은 프레임 2회 검출 LateUpdate 폴링과 애니메이션 이벤트가 같은 프레임에 겹치면 스윕 기준 형상이 이중 커밋되어 스윕 구간을 잃는다
_hitTargets 집합 한 공격에서 같은 대상 재타격 판정 구간이 길어도 대상당 1회. 다음 공격 시작 시 ClearHitTargets()로 비운다

검출된 CombatHit마다 다음이 일어난다.

foreach (CombatHit hit in _detectedHits)
{
    _currentAttackData.hitTarget / hitPoint / attackDirection = 퍼-타겟 값 기록
    CombatResult result = hit.Damageable.ReceiveHit(HitRequest.FromAttackData(_currentAttackData));
    ShowAttackHitFeedback(result);   // 대상마다 — 데미지 숫자 + 히트 FX
    OnAttackHit?.Invoke(_currentAttackData);
}
if (hitOccurred) ApplyHitFeedback();  // 공격당 1회 — 히트스톱 / 카메라 / 킬캠
대상마다 vs 공격마다 데미지 숫자와 히트 FX는 맞은 수만큼, 히트스톱·카메라·바이탈오브는 첫 히트 기준 1회만. 광역기가 5마리를 맞혔다고 히트스톱을 5번 걸면 프레임이 멈춘다. 투사체·AOE도 ShowExternalHitFeedback()(대상마다) / ApplyExternalAttackImpact()(1회)로 같은 정책을 재사용한다.

소유: GameActor/Component/Player/PlayerCombat.HitDetection.cs, GameActor/Combat/Detection/CombatHitDetector.cs

6. 피격 해석 파이프라인

여기부터는 피격자 소유다. 근접·투사체·잔류 판정·환경 피해가 전부 이 한 지점으로 모인다. 

CombatResolutionPipeline.Execute(victim, request)
  ├─ victim이 ICombatResolvable인가            → 아니면 에러 로그 후 default
  ├─ resolvable.CanResolveHit(request)         → 무적·가드 블록·사망이면 여기서 종료
  ├─ CombatResult resolved = ResolveHit(...)      // 계산만 — 방어 → 피해
  ├─ CombatResult result  = ApplyResolvedHit(...) // 적용 — HP, 리액션, 자원, 피드백
  └─ RecordIfObservable(result)                   // CombatLogRecorder 기록
계산과 적용이 분리되어 있다 ResolveHit는 부수효과가 없다(밸런스 툴이 같은 함수를 그대로 호출한다). HP 차감·상태 전환·연출은 전부 ApplyResolvedHit에서만 일어난다. 이 경계를 넘기면 시뮬레이션 도구가 실제 액터를 건드리게 된다.

6.0 CanResolveHit — 시작도 못 하는 경우

  • 플레이어: 항상 true. 방어 처리는 뒤의 DefenseResolver가 전담한다.
  • 몬스터: 특수 브레이크는 BreakGauge.IsExposed일 때만 통과. 가드 중이면 EnemyGuardState.OnAttackBlocked()를 호출하고 false. CanTakeDamage()가 거짓이면(사망·무적·상태 무적) 스로틀 로그 후 false.

6-1. 방어 판정 (플레이어 전용)

DefenseResolver.ResolvePlayerDefense()는 아래 순서로 먼저 성립하는 것을 채택한다.

#결과성립 조건피해
1Guarded가드 중 + 가드 상태 + 정책이 해당 AttackDefenseType 가드 허용없음
2Parried아래 패리 조건 참조없음
3PerfectDodged피해 불가 상태 + 퍼펙트 회피 상태·윈도우 + 정책 허용없음
4Invincible피해 불가지만 위 조건에 해당 없음없음
5UnblockableHitAttackDefenseType.Unblockable적용
6None그 외 전부적용

패리가 성립하는 세 경로

  1. 디버그 — AlwaysParry
  2. 어시스트 스왑 패리 — IsAssistParryWindow. 단 Unblockable은 명시적으로 제외해 빨강 Danger Ring은 회피만 통한다(정책 미설정 환경 포함)
  3. 공격 패리 — 공격 상태 + 판정 활성 + 해당 공격이 parryCapable + 정책 허용
투사체는 패리 대상이 아니다 isProjectile && !isReflectableProjectile이면 디버그 AlwaysParry보다 먼저 차단된다. 전달 방식 자체가 패리·카운터의 대상이 아니라는 규칙이라, 디버그 플래그로도 뚫리지 않는다.

6-2. 피해 계산

플레이어·몬스터 모두 최종적으로 DamageExecution.Calculate() 하나를 지난다.

finalDamage = base
            × max(0, attackPower)
            × (1 - clamp01(defenseRate))
            × max(0, damageTakenMultiplier)
            × max(0, elementMultiplier)
            × max(1, criticalMultiplier)

return base > 0 ? max(1, finalDamage) : 0;   // 피해가 있었다면 최소 1은 보장
항출처비고
baseHitPhaseData.damage일반 공격은 ±20% 난수(ApplyRandomValue), 차지는 Lerp(1.0,1.5,ratio)
attackPower공격자 Attributes.Combat.AttackPower없으면 1
defenseRate피격자 Attributes.Combat.Defenseclamp01 — 비율 감쇠
damageTakenMultiplier취약 배율 통합 채널아래 참조
elementMultiplierCombatElementRules속성 상성 + ElementalAdvantageMultiplier
criticalMultiplierHitContext.CriticalMultiplier1 초과일 때만 크리티컬로 표기
취약 배율은 max-wins 단일 채널이다 리액션 상태 취약(Stun/Knockdown/Airborne/Grabbed)과 Break 노출 취약이 동시에 성립해도 CombatPolicyResolver.GetVulnerabilityMultiplier()가 더 큰 하나만 적용한다. 곱해 쌓으면 스턴 중 브레이크에서 피해가 폭주한다.

여기에 몬스터 도감 보정이 별도로 곱해진다 — 플레이어가 받는 피해는 GetDamageTakenMultiplier(공격 몬스터), 몬스터가 받는 피해는 GetDamageDealtMultiplier(피격 몬스터).

특수 브레이크 피해는 이 식을 타지 않는다. max(최대HP, 최소기준HP) × 비율 + 고정값으로 방어·크리티컬 없이 계산되며, 최대 HP가 낮은 대상에서도 비율 피해의 하한이 보장된다.

6-3. 리액션 결정

ReactionResolver가 넉백을 줄지, 상태를 바꿀지, 카메라를 흔들지를 각각 따로 결정한다.

플레이어

  • IgnoreHitReaction(슈퍼아머·상태 자체 억제) → 아무것도 안 함
  • 경직 내성(Stagger Protection) — 리액션 회복 직후 창 동안 약한 리액션(None/Light/Hit)은 상태 전환과 카메라만 억제한다. 피해는 그대로 들어간다. 강한 리액션(Heavy/넉백/에어본/다운/스턴/잡기)은 통과시켜 한 방은 여전히 흔들리게 한다.
  • ReactionType.None은 상태로 보내지 않는다 — 대응 트리거 태그가 없어 "전환하기로 했는데 아무도 수행하지 않는" 상태가 되기 때문

몬스터

상황목표 상태정책 우회
Poise 브레이크 발생Knockdown 가능하면 Knockdown, 아니면 Stun등급 정책은 적용
GuaranteedReaction리액션 보장등급 정책·Poise 요구 모두 우회(상태 기반 제외는 유지)
ForceReaction정책이 등급별로 허용할 때만없음
특수 브레이크 생존Knockdown 모션 있으면 Knockdown, 없으면 Stun—
ForceReaction과 GuaranteedReaction은 다른 것이다 ForceReaction은 등급 정책의 허가를 구한다(보스는 여전히 안 흔들릴 수 있다). GuaranteedReaction은 정책을 넘어선다(보스도 흔들린다). 보스가 안 흔들린다고 ForceReaction만 켜면 아무것도 달라지지 않는다.

소유: GameActor/Combat/Resolution/ — CombatResolutionPipeline.cs, DefenseResolver.cs, DamageResolver.cs, ReactionResolver.cs, CombatPolicyResolver.cs, Ability/Core/StandardGameplayExecutions.cs

7. 피드백과 소유권

같은 타격의 연출이 공격자와 피격자로 나뉜다. 어느 쪽이 부르는지가 규칙으로 고정되어 있고, 어기면 이중 재생이 된다.

7.1 히트스톱 — 비대칭 프리즈

플레이어 공격이 적중하면 피격자는 완전 정지(VictimFreezeScale = 0f), 공격자는 약한 스케일로만 느려진다. 사람 눈은 0%와 10%의 차이를 잘 못 느끼지만, 공격자 쪽 루트모션과 카메라가 미세하게 진행되면 조작감이 끊기지 않는다.

다인 전투 누수 차단

플레이어가 이미 피격 히트스톱 중이면(IsActorHitStopping(victim)) 피해자 freeze를 재시작하지 않는다. 매 히트마다 재시작하면 다수의 적에게 둘러싸였을 때 플레이어가 영구히 멈춘다. 단 공격자 히트스톱과 global pulse는 타격 피드백이므로 그대로 유지한다.

경직 내성과의 연동

경직 내성 창에서 흡수된 약한 피격은 히트스톱도 함께 생략한다 (PlayerActor.OnDamaged가 ReactionResolver.IsMinorPlayerReaction()을 직접 참조). 컬러 플래시와 히트 FX는 유지해 "맞았다"는 사실은 여전히 보인다.

패리 윈도우 보호

ApplyImpact(attackData, protectParryWindow: true)일 때, 카운터 공격이나 useCounterHitFeedback이 아닌 일반 타격의 임팩트 연출은 생략한다. 패리 가능 구간에서 자기 히트스톱에 갇혀 패리 입력을 놓치는 것을 막는다.

소유: GameActor/Combat/Feedback/CombatFeedbackDispatcher.cs, GameActor/Component/Player/PlayerCombatPresenter.cs, Manager/Handler/Combat/GameHitStopHandler.cs, …/DefenseSuccessFeedbackHandler.cs

8.1 태그 트리거 — 리액션 상태 전환의 실제 수행자

ReactionDecision은 결정만 한다. 실제 상태 전환은 Abilities.IssueTriggerEvent(triggerTag, …)가 발급한 GameplayEvent를 받아 태그 트리거 Ability가 수행한다.

순간 GameplayEvent는 현재 상태와 무관하게 매 피격마다 발급한다 Hit 상태 중이라고 발급을 막으면 같은 프레임의 두 번째 피격 사건 자체가 유실된다. 중복 리액션 차단은 발급측이 아니라 Ability의 blockAny가 해야 한다. 단 외부 리액션 억제 스코프(_externalHitReactionSuppressionCount)는 기존 계약대로 발급도 억제한다.

8.2 기록

RecordIfObservable()은 피해가 들어갔거나(FinalDamage > 0) 방어 결과가 있었으면(DefenseOutcome != None) CombatLogRecorder에 남긴다. 가드·패리·회피도 관측 대상이라 밸런스 툴이 "얼마나 맞았나"뿐 아니라 "얼마나 막았나"까지 볼 수 있다.

9. 자주 틀리는 지점

  1. 모션이 안 나온다 → motionKey가 해당 액터의 ActorAnimationMotionSet.abilityMotions에서 해석되는지 확인. 플레이어는 현재 WeaponType 세트 → NoWeapon 순으로 폴백한다.
  2. 피해가 0이다 → HitPhaseData는 있는데 BeginCollisionEvent.hitPhaseIndex가 어긋났을 가능성이 가장 높다.
  3. 같은 타격이 두 번 들어간다 → 부착형 그룹과 ExplicitShape를 같은 이벤트에서 섞었거나, 애니메이션 이벤트와 폴링이 겹쳤는데 프레임 가드가 우회됐다.
  4. 보스가 안 흔들린다 → ForceReaction이 아니라 GuaranteedReaction이 필요하다(6-3장).
  5. 광역기에서 프레임이 멈춘다 → 히트스톱을 대상마다 걸고 있다. ApplyImpact는 공격당 1회다.
  6. 충돌음이 두 번 난다 → 공격자측에서 PlayDamageImpact를 부르고 있다. 소유는 피격자다.
  7. 몬스터가 BT 대로 안 움직인다 → EnemyActionResolver의 failureReason을 본다. 대부분 cooldownId 아니면 상태 락이다.
  8. 강공격이 약공격으로 바뀐다 → forcedAttackAction을 받은 뒤 입력 버퍼를 재해석했다. 인계값은 뒤집지 않는다.
  9. 회피가 씹힌다 → 공격 상태가 전역 InputBuffer를 붙들고 있어 다른 액션의 수명이 늘어났을 수 있다(2.1).
  10. 다수전에서 플레이어가 영구히 멈춘다 → 피격 히트스톱을 매 히트마다 재시작하고 있다(7.1).
