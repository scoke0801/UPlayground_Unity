# 테스트 작업 지침

## 목적과 기본 원칙

변경으로 깨질 수 있는 동작을 가장 작은 유효한 검증으로 확인한다. AI가 테스트 작업 명세를 작성하고, 사용자가 직접 실행·판단한 결과를 전달하는 방식을 기본으로 한다. 오래 걸리거나 자동화하기 어려운 플레이 검증을 AI가 끝까지 자동화하려고 하지 않는다. 일반 작업마다 Windows 실행 파일을 만드는 것을 기본 절차로 삼지 않는다. 자동화 테스트와 Player 빌드는 별도 단계이며, Play Mode 테스트는 Editor 안에서 실행하는 것을 기본으로 한다.

- 먼저 변경 파일, 호출자, 소비 모듈, 연결 에셋을 확인하고 필요한 검증과 선택 이유를 정한다.
- 기존 테스트·검증 도구·수직 슬라이스를 우선 사용한다. 테스트를 빠르게 하려는 목적으로 새 프레임워크나 대규모 구조 변경을 도입하지 않는다.
- 관련 검증이 통과하면 종료한다. 새 변경·실패·해결되지 않은 위험이 없는 상태에서 전체 테스트나 빌드를 반복하지 않는다.
- 요구된 검증을 수행할 수 없으면 원인과 남은 항목을 보고한다. 보조 검사 통과를 Unity·Play Mode·Player 검증 통과로 바꾸어 표현하지 않는다.

## 사용자 직접 테스트 운영

- **검증용 빌드 금지:** 사용자의 최신 지시에 따라 전투를 포함한 검증은 Unity 컴파일·EditMode·Editor Play Mode에서 진행한다. 검증을 목적으로 Player 또는 Addressables 콘텐츠 빌드를 실행하지 않는다. 아래 Player 검증 기준에 해당하더라도 별도 빌드 지시가 없으면 미수행으로 기록한다. 시각적 품질은 수치 검사 통과와 구분한다.

- AI는 변경 영향과 미검증 항목을 조사하고, 사용자가 바로 실행할 수 있는 테스트 작업 명세를 작성한다. 사용자는 명세에 따라 테스트하고 결과를 전달한다. AI는 전달받은 결과를 정리하고 실패 원인을 조사·수정한 뒤 영향 범위의 재검증 명세를 작성한다.
- 긴 플레이 경로, 실제 화면·입력, 전투 감각, 카메라·연출·UI 품질처럼 사람의 판단이 필요한 검증은 사용자 직접 테스트로 진행한다. 이를 대신하려고 화면·입력 도구 연결 복구, 장시간 자동 조작, 새 자동화 도구 제작을 계속하지 않는다. 별도 요청이 있을 때만 해당 자동화를 진행한다.
- 짧고 관련성이 명확한 기존 자동 검사·컴파일·정적 검사는 보조 수단으로 사용할 수 있다. 자동화에 드는 시간과 난도가 커지면 테스트 명세로 넘기며, 사용자 직접 테스트를 자동 검사 결과로 대체하지 않는다.
- 사용자의 결과가 도착하기 전에는 해당 항목을 `사용자 테스트 대기`로 남긴다. 사용자 확인과 AI 자동 검사 결과를 구분하며, 미검증 항목을 완료로 표시하지 않는다.

테스트 작업 명세에는 다음 내용을 포함한다.

1. **대상과 준비:** 확인할 변경, 씬·실행 파일·빌드 식별 정보, 시작 상태·저장 슬롯, 입력 장치. 기존 저장 데이터 보호가 필요하면 준비 절차도 명시한다.
2. **실행 절차:** 사용자가 순서대로 따라 할 수 있는 조작과 확인 지점. 항목마다 식별자를 붙이고 독립적으로 결과를 남길 수 있게 한다.
3. **기대 결과와 실패 기준:** 진행 조건과 화면·조작 품질을 구체적으로 적는다. 진행 성공 여부와 런타임 오류 유무는 별도로 판정한다.
4. **실패 시 전달 정보:** 실패한 단계, 실제 증상, 입력 장치와 시작 상태, 필요 시 화면·영상·로그 위치. 원인 조사에 필요한 정보만 요청한다.
5. **결과 회신 형식:** `항목 ID / 통과·실패·미수행 / 실제 결과 / 첨부 또는 로그`로 전달할 수 있게 한다. 이미 알려진 실패와 아직 확인하지 못한 위험도 명세에 표시한다.

아래 검증 단계와 범위는 필요한 확인 항목을 정하는 기준이다. 모든 실행을 AI가 자동으로 수행해야 한다는 뜻은 아니며, 위 운영 방식에 따라 사용자가 실행할 항목을 명세에 포함한다.

## 검증 단계 선택

| 단계 | 적용 시점 | 수행 내용 | Windows Player 빌드 |
|---|---|---|---|
| 변경 검증 | 코드·데이터 변경마다 | Unity 컴파일, 관련 EditMode 테스트, 데이터·참조 검사 | 기본적으로 생략 |
| 동작 검증 | 실행 동작·상태·연출 변경 | Editor Play Mode의 관련 자동 테스트 또는 재현 시나리오 | 기본적으로 생략 |
| Player 검증 | 아래의 고위험 변경, 주요 통합·릴리스 | 필요한 Editor 검증 후 Windows 빌드 및 실제 실행 | 필수 |

문서만 수정한 경우 내용·링크·diff를 확인하며 Unity 컴파일과 런타임 테스트는 수행하지 않는다. 일반 코드 수정은 소속 모듈 이름만으로 Player 검증 대상으로 분류하지 않는다.

### 변경별 검증 범위

| 변경 | 기본 검증 |
|---|---|
| 순수 규칙·쿨다운·비용·파티 편성 | Unity 컴파일과 관련 EditMode 테스트 |
| GAS·BT·MotionSet 데이터 | 변경 데이터와 참조하는 액터의 연결 검사, 관련 Editor Play Mode 전투 시나리오 |
| 이동·공격·가드·피격·상태 전이 | 관련 규칙 테스트와 Editor Play Mode 재현; 입력 반응·텔레그래프·히트스톱·캔슬 창 확인 |
| UI·입력 | 관련 화면의 초기 포커스, 게임패드 이동, Cancel, 탭 전환, 트윈과 일시정지 상태 확인 |
| 카메라 내부 동작·어댑터 구현 | 영향받는 소비 모듈 컴파일, 관련 Lock-on·전투·대화·KillCam 등 재현 |
| 퀘스트·FlowGraph·저장 진행 | 관련 데이터 검사와 정상·역순 진행·저장/로드·재진입 시나리오 |
| Editor import·데이터 도구 | 관련 EditMode 검사, 실패 시 Undo 롤백 및 GUID·참조 보존 확인 |

공용 계약이나 공용 데이터가 바뀌면 직접 수정한 파일뿐 아니라 소비 모듈과 참조 에셋까지 범위를 넓힌다. 관련 테스트를 선택할 때는 현재 저장소의 실제 테스트 목록과 의존 관계를 확인하며 문서의 과거 테스트 개수를 기준으로 고정하지 않는다.

### Player 검증이 필요한 경우

- asmdef 참조·플랫폼 포함 조건 등 모듈 경계를 변경한 경우.
- 직렬화 타입의 이름·네임스페이스·어셈블리 이동, SerializeReference 구조 또는 직렬화 호환성을 변경한 경우. 일반 SO 수치 조정은 여기에 해당하지 않는다.
- Player 설정, 스크립팅 백엔드, 코드 스트리핑, 빌드 씬, 빌드 스크립트, 플랫폼 조건부 코드, 네이티브 플러그인을 변경한 경우.
- Addressables 그룹·카탈로그·빌드된 콘텐츠의 로딩 경로 또는 셰이더 포함 정책 등 Editor와 Player 결과가 달라질 수 있는 구성을 변경한 경우.
- Player에서만 발생한 버그를 수정하거나 실제 기기 성능을 판정하는 경우.
- 주요 기능 통합을 마무리하거나 릴리스를 준비하는 경우.

고위험 변경도 중간 수정마다 전체 빌드를 반복하지 않는다. 빠른 검증으로 수정한 뒤 최종 변경 상태에서 필요한 Player 검증을 수행한다. 빌드 성공과 실행 성공은 별도로 기록한다. Boot 빌드만으로 전체 콘텐츠 검증이 끝났다고 판단하지 않으며, 변경 기능이 포함된 씬·콘텐츠를 실제로 실행한다. 릴리스 검증에는 배포할 설정을 사용한다.

주요 통합 시에는 전체 EditMode·Play Mode 회귀 검사와 프로젝트 전체 참조 검사를 수행해 선택 실행의 누락을 보완한다. 기존의 미완료 Play Mode·Player 검증 기록은 이 정책 도입만으로 완료 처리하지 않는다.

## 실행 비용을 줄이는 방법

1. 관련 테스트 어셈블리·이름·카테고리를 선택해 실행한다. 필터 결과가 0개이거나 의도한 테스트가 빠지면 통과로 간주하지 않는다.
2. Editor Play Mode를 우선 사용하고 테스트 대상 플랫폼을 습관적으로 StandaloneWindows64로 지정하지 않는다. 구체 명령은 설치된 Test Framework 버전과 기존 실행 도구를 확인한 뒤 사용한다.
3. 가능한 경우 열린 Editor의 Test Runner를 사용해 재기동 비용을 줄인다. 같은 프로젝트에 두 번째 Unity 프로세스를 강제로 열거나 잠금 파일을 삭제하지 않는다.
4. 기존의 작은 테스트 씬·수직 슬라이스에서 필요한 액터와 서비스만 준비한다. Boot 초기화·씬 전환 검증은 별도 통합 시나리오로 유지한다.
5. 원인 없이 Library나 빌드 캐시를 삭제하거나 Clean Build를 강제하지 않는다. Domain Reload 설정도 속도만을 이유로 변경하지 않는다.
6. 느린 경우 Editor 시작·임포트·컴파일·씬 준비·테스트 실행·Player 빌드 시간을 구분해 기록하고 병목을 줄인다. 측정 없이 절감 시간을 단정하지 않는다.

최신 생성 `.csproj`의 `dotnet build --no-restore`는 빠른 보조 컴파일로 사용할 수 있지만 Unity 컴파일·에셋 임포트·Player 코드 경로를 대체하지 않는다. Unity 밖의 순수 C# 테스트는 이미 독립된 코드에 한해 검토하며, 이번 작업과 무관한 코어 분리를 선행 조건으로 만들지 않는다.

## 데이터 및 테스트 안전 규칙

- 에셋·직렬화 검증은 Unity에서 실제 로드한 결과를 기준으로 한다. 텍스트 검색은 금지 참조나 잔존 문자열을 찾는 보조 수단이다.
- AbilitySet → Payload → MotionKey → MotionSet 및 HitPhase 연결, Missing Script, managed reference, VFX 누락은 관련 기존 검증 도구를 사용한다.
- 컴파일·타입 매핑 오류가 있으면 에셋 저장·일괄 재직렬화를 멈춘다. 검증 전후 diff를 비교하고 검증이 만든 자동 변경만 원복한다. 기존 사용자 변경과 GUID를 보존한다.
- 새 테스트는 재발 가능한 버그와 의미 있는 경계 조건에 집중한다. 단순 문구·문서 수정이나 구현을 그대로 복제하는 테스트는 추가하지 않는다.
- 테스트 간 생성 오브젝트·서비스 등록·전역 상태를 정리한다. 서비스 경고·예외를 숨기거나 실패 테스트를 임의로 제외해 통과시키지 않는다.
- 자동 테스트로 전투 감각·카메라 가독성·UI 조작성까지 확인했다고 간주하지 않는다. 해당 경험이 바뀌면 관련 Play Mode 플레이 확인을 포함한다.

## 검증 산출물 관리

검증이 만든 사본·빌드·캐시는 검증이 끝나면 지운다. 프로젝트 사본은 Library를 포함하면 수십 GB, Player 빌드는 하나에 4~10GB라서 남겨 두면 디스크가 금방 찬다. 다시 만들 수 없거나 문서가 근거로 인용하는 산출물만 보관한다.

| 산출물 | 위치 | 처리 |
|---|---|---|
| 검증용 프로젝트 사본 | 작업마다 정한 임시 위치 | 검증이 끝나면 결과 보고 전에 삭제한다. `Logs/`·`output/` 아래에 남기지 않는다. |
| 보관할 Player 빌드 | `Builds/<목적>_<YYYYMMDD>/` | 문서에 경로와 보관 이유를 적는다. 같은 목적의 새 빌드를 보관하면 이전 빌드는 지운다. |
| 실패·이전 시도 빌드, 보조 컴파일 출력 DLL | — | 결과를 기록한 직후 삭제한다. |
| 패키지·빌드 캐시 (`node_modules`, `.next` 등) | 해당 도구 폴더 | 작업이 끝나면 삭제한다. 추적 중인 잠금 파일(`package-lock.json`)로 복원된다. |
| 작업 전 백업 (씬 사본, 변경 패치) | `output/<작업명>/` | git으로 되돌릴 수 없는 상태(커밋 전 사용자 변경 등)를 지킬 때만 만든다. 작업이 커밋되면 삭제하되, 커밋되지 않은 사용자 변경이 들어 있으면 사용자 확인 없이 지우지 않는다. |
| 텍스트 로그·결과 JSON·소형 캡처 | `Logs/<작업명>/`, `output/<작업명>/` | 유지한다. 용량이 작고 문서가 검증 근거로 인용한다. |

- 지우기 전에 문서가 인용하는 경로인지, 에디터 도구·테스트가 입력으로 읽는 파일인지 확인한다. 해당하면 폴더 구조와 그 파일은 남기고 대용량 파일만 지운다.
- 사본·빌드 폴더를 지우기 전에 원본을 가리키는 정션·심볼릭 링크가 없는지 확인한다.
- Unity가 직접 쓰는 `Logs/` 파일(`AssetImportWorker*.log`, `shadercompiler-*.log`)과 원본 프로젝트의 `Library`·`Temp`는 이 정리 대상이 아니다. 원본 Library 삭제 기준은 위 "실행 비용을 줄이는 방법" 5번을 따른다.
- 도구·테스트가 결과 파일을 쓸 때는 대상 폴더를 직접 만든다(`Directory.CreateDirectory`). 이전 작업의 결과 폴더가 남아 있어야만 동작하는 코드를 만들지 않는다.

## 결과 보고

검증 보고에는 다음 항목을 짧게 남긴다.

- **대상과 선택 이유:** 변경 영역, 영향을 받는 소비자, 실행한 검증 단계.
- **수행 결과:** 컴파일 환경, 테스트·재현 시나리오, 통과·실패·실행 개수, 필요 시 로그·결과 파일.
- **확인 주체와 방식:** 사용자 직접 테스트, AI 자동 검사, 가상 입력, API 저장/로드, 상태 주입, 월드 캡처, 실물 패드, 독립 Player 화면 확인을 구분한다. 사용자 전달 결과는 그 출처를 표시한다.
- **미수행:** 항목과 이유. 정책상 불필요한 Player 빌드와 환경 문제로 못 한 필수 검증을 구분한다.
- **남은 위험:** 필수 검증이 남았다면 구현 반영과 검증 완료를 분리해 보고한다.
- **산출물:** 보관한 빌드·사본의 경로와 크기, 삭제한 항목. 대용량 산출물을 남겼다면 이유를 적는다.

예: “가드 조건 수정. Unity 컴파일과 관련 EditMode·Editor Play Mode 재현 통과. Player 전용 경로 변경이 없어 Windows 빌드는 미수행.” 실제로 확인한 항목만 기재한다.
